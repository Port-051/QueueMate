# 실시간 전달 방식의 장기 운영비 비교

작성·공식 단가 확인: 2026-09-15. 대상: QueueMate의 매칭 알림, 모집 목록 갱신, 파티 상태, WebRTC signaling.

## 판단

**지금은 기존 Spring WebSocket을 유지하면서 재조회와 전체 방송을 줄이는 것이 우선이다.
독립적인 중계 서비스를 새로 선택한다면 성장 단계의 비용 우선 후보는 Cloudflare Workers +
Durable Objects의 WebSocket Hibernation이다.** AppSync Events는 적은 접속 시간·메시지량과
AWS 운영 일원화를 원할 때 유리하다. SSE나 폴링으로 프로토콜만 바꾸는 것은 우선하지 않는다.

이 결론은 현재 코드와 공식 가격표에 기반한 조건부 선택이다. 기존 서버에 남은 용량,
실제 요금·트래픽·운영 인건비를 측정하지 않았으므로 모든 규모에서 절대 최저가라고 확정하지 않는다.
기존 기술을 보존해야 해서 내린 결정이 아니다. 전송료 절감만으로 기존 API·DB·Redis 비용이
사라지지 않고, 교체 개발비의 회수 여부가 달라지기 때문이다.

수행한 것은 코드 조사, 서울 리전 AWS Price List 직접 조회, 공식 Cloudflare 가격 확인,
재현 가능한 비용 계산과 9개 계산 검증이다. AWS/Cloudflare 리소스를 배포하거나
클라우드 지연·처리량을 실측하지 않았다. 원본 프로젝트의 PLAN.md/부하 로그도 이 저장소에는 없다.
사용자가 제공한 보고서는 타 프로젝트의 실험 결과로만 취급한다.

## 현재 코드에서 확인한 비용 원인

| 확인한 사실 | 의미 | 근거 |
|---|---|---|
| 로그인 후 하나의 이벤트 스트림에 여러 구독자가 붙는다 | 기능별로 WebSocket 연결을 추가할 필요가 없다. 탭은 별도 연결이다 | `frontend/src/state/MatchContext.tsx`, `frontend/src/api/ws.ts` |
| 대기 요청/미확정 제안을 3초마다 조회한다 | 연결이 정상이어도 REST·DB 비용이 계속 발생한다 | `MatchContext.tsx`의 `MATCH_POLL_MS`, 두 polling effect |
| 보이는 게시판을 15초마다 갱신한다 | 갱신당 로드한 모든 목록 페이지와 내 모집을 다시 조회한다 | `frontend/src/state/useRecruitmentBoard.ts` |
| 게시판 변경 이벤트가 모든 연결에 방송된다 | 다른 게임 이용자도 재조회할 수 있다. 250ms debounce와 진행 중 요청 병합은 이미 있다 | `RealtimeEventPublisher`, `useRecruitmentBoard` |
| 파티를 15초마다 조회한다 | 파티 이벤트 수신과 별개인 복구 조회 비용이다 | `frontend/src/state/PartySessionContext.tsx` |
| Redis 단일 pub/sub 채널을 모든 노드가 구독한다 | 노드 수만큼 역직렬화·필터 비용이 늘어난다 | `backend/src/main/java/com/queuemate/realtime/event/EventFanout.java` |
| 로컬 전송은 Redis 방송보다 먼저 한다 | Redis 장애 때도 로컬 이벤트는 전달할 수 있다. 원격 전달은 실패할 수 있다 | `RealtimeEventPublisher.java` |
| signal마다 서버가 양측의 파티 소속을 확인한다 | 외부 중계로 옮겨도 이 권한 검증을 보존해야 한다 | `realtime/signal/SignalRelayService.java` |

예를 들어 1,000명이 하루 8시간, 30일 내내 홈에서 매칭 대기한다고 가정하면,
3초 매칭 조회는 월 2.88억 건, 15초 게시판 조회는 한 페이지만 열어도 월 1.152억 API 호출이다.
합계 **4.032억 건**이며 이벤트에 따른 재조회·초기 조회·추가 페이지는 빠져 있다.
이것은 코드 주기를 환산한 시나리오이지 실제 사용량이 아니다. 대기자·게시판 노출 비율에 따라 줄어든다.
WebSocket을 AppSync로 바꾸어도 이 조회 코드를 그대로 두면 절감되지 않는다.

## 동일 기준의 비교

일반 상태 변경은 1초 내 95% 반영을 비교 목표로 둔다. 장애·재연결 구간은 별도로 측정한다.
후보 부족·락 경쟁은 사용자 실패 알림으로 만들지 않는다. 중요한 결과는 DB가 진실이며
서버 이벤트를 받았다는 사실만으로 상태를 확정하지 않는다. 음성 미디어 비용은 따로 계산한다.

| 방식 | 요금 구조 | 현재 제품에서의 판단 |
|---|---|---|
| 기존 Spring WebSocket | 서버·메모리·LB·egress, 재조회·운영 비용 | 서버 여유 용량 안에서는 추가 인스턴스비가 없을 수 있다. 우선 최적화 대상 |
| Spring SSE + REST | 비슷한 연결 자원 + 클라이언트 송신용 REST | 구현은 가능하나 지속 연결을 없애지 못한다. 비용 우위 실측 없음 |
| 주기 폴링 | 조회 횟수 × API·DB·전송 비용 | 낮은 빈도·느슨한 지연 요구에는 가능. 같은 1초 목표에서는 불리한 후보 |
| Lambda SSE | 사용자별 연결 지속시간의 GB-s | 기존 Spring이 있는 상황에서 선택할 비용 근거가 약함 |
| AppSync Events | 발행·수신자별 전달·연결/구독/handler 작업 + 연결 분 + egress | 적은 사용량에서 낮은 시작비. 큰 방송의 수신자별 과금에 주의 |
| API Gateway WebSocket | 메시지 + 연결 분 + egress + 레지스트리·팬아웃 | AppSync와 달리 대상 연결 추적·전송 구현이 남는다. 메시지 크기/사용 패턴에 따라 역전 가능 |
| Cloudflare DO Hibernation | Workers 최소비 + Worker/DO 요청·실행시간 | 큰 방송에서 유리한 계산. 자체 인증·라우팅·복구 구현은 여전히 필요 |
| Ably / Supabase Realtime | 패키지 기본비 + 사용량/최대 연결 등 | 관리 기능을 포함한 대안. 현재 구성에 알림만 더할 때 비용 최소 후보로 우선하지 않음 |

SSE도 장기 연결이다([MDN](https://developer.mozilla.org/en-US/docs/Web/API/EventSource)).
Lambda SSE는 전체 함수 실행시간에 과금된다([AWS](https://docs.aws.amazon.com/lambda/latest/dg/configuration-response-streaming.html)).
Ably Standard는 $29부터([가격](https://ably.com/pricing)), Supabase Pro는 $25부터이며
실시간 연결·메시지 비용이 추가될 수 있다([가격](https://supabase.com/pricing)).
이는 기능·DB까지 같은 전체 서비스 비교가 아니며 무료 플랜은 아래에서 별도로 다룬다.

## 월 비용 계산

`harness/studies/realtime-cost/model.py`와 `rates.json`, `sample-results.json`이 재현 자료다.
기본값은 30일, 표에 적힌 동시 연결 수를 운영 시간 내내 유지, 연결 수명 60분, 구독 2개,
전역 게시판 변경 10초당 1회, 사용자당 시간당 개인 이벤트 6회와 평균 signal 20회,
메시지 1KiB다. 모두 **가정**이며 최대 동접을 평균 동접으로 오해하면 안 된다.

아래는 **전송 계층 월 USD**다. AWS egress allowance가 이미 소진된 경우를 기본으로 한다.
CF는 Workers 유료 기본비 $5 및 AWS에서 CF로 보내는 발행 데이터의 egress까지 포함한다.
Spring·DB·Redis·기존 REST·로그·TURN·세금·인건비는 별도다. CF의 실행시간은 미실측 가정이다.
외부 중계 도입에 필요한 presence lease 갱신과 외부 인증 호출의 추가 비용도 미확정이다.
따라서 아래 금액은 완성된 대체 시스템의 총액이 아니라 전달 계층의 비교값이다.

HTTP API 첫 3억 $1.23/백만, Lambda $0.20/백만 요청·첫 구간 $0.0000166667/GB-s,
서울 internet egress 첫 유료 구간 $0.126/GB. 버전 고정 근거 URL과 SKU는 `rates.json`에 있다.
현재 공개 설명은 [AppSync 가격표](https://aws.amazon.com/appsync/pricing/)와
[API Gateway 가격표](https://aws.amazon.com/api-gateway/pricing/)에서도 확인할 수 있다.

CF는 계정당 최소 $5, Worker 1,000만 요청·3,000만 CPU-ms 포함, DO 100만 요청·400,000 GB-s 포함이다.
DO에서 나가는 WebSocket 메시지와 Workers egress에는 별도 요금이 없지만 처리 자원은 소모한다.
DO의 과금 메모리는 decimal 0.128GB이고 현재 문서대로 초과 사용량을 백만 단위로 올림했다.

동시 1,000명·하루 8시간을 기준으로 한다. 아래 역시 실측이 아닌 입력 변경 계산이다.

| 기본 | $112.45 | $6.66 | 전역 방송이 비용 대부분 |

| 게시판 수신자 10% | $25.35 | $6.66 | 게임/모드별 구독 범위 축소가 유효. CF는 모든 shard 발행 가정 유지 |
| 전역 변경 초당 1회 | $984.27 | $6.90 | 메시지 건별 과금과 처리시간 과금의 차이. CF 처리 가능 여부는 검증 필요 |
| 연결 수명 15분 | $116.05 | $6.81 | 토큰 갱신·재접속 비용 포함 필요 |
| payload 6KiB | $267.08 | $10.46 | AppSync 5KiB 과금 경계와 전송량 증가 |
| CF 사용자당 DO 1개, 처리 100ms | $112.45 | $70.41 | 같은 CF라도 분할·실행 방식에 따라 달라짐 |
| AWS 무료 egress 100GB가 남음 | $101.32 | $5.90 | 기본 표는 공용 allowance를 이미 쓴 경우 |

AppSync의 서버 `ka`가 과금되는지는 가격표의 `ping requests`만으로 단정하지 않았다.
분당 작업 1건을 추가하면 기본 1,000명·8시간은 $126.85다. 이 범위도 최종 청구 검증이 필요하다.
메시지량이 사용자 수에 비례해 증가하면서 전역 방송까지 유지되면 전달량은 N²으로 증가한다.
기본 표는 전역 변경 0.1회/초를 고정했으므로 그런 성장을 이미 포함한 것처럼 해석하지 않는다.

Cloudflare Free도 비교에서 배제하지 않는다. 현재 문서에는 일일 요청 100,000·DO 13,000 GB-s
한도가 있고 초과 시 해당 작업이 실패한다. 모델상 100명·8시간과 1,000명·1시간은 해당 일일 양에
들어가지만 1,000명·8시간은 초과한다. 전자의 CF 플랫폼 요금은 $0일 수 있으나 원본 서버 egress,
실제 JWT 검증 CPU·트래픽 순간 집중·다른 프로젝트의 계정 사용량도 확인해야 한다.
유료 표는 운영 중 한도 초과로 멈추는 무료 플랜에 의존하지 않는 비교다. 유료 포함량도 계정에서 공유된다.

## 직접 운영 비용과 장기 손익분기

직접 운영 WebSocket/SSE에는 메시지당 정해진 가격이 없다. 이미 필요한 Spring 서버의
여유 CPU·메모리·전송 allowance 안에 들어가면 추가 인스턴스비는 $0일 수 있다.
반대로 연결이나 방송 때문에 증설해야 하면 그 증설비가 비교 대상이다.
**1,000명 또는 10,000명을 현재 서버가 처리한다고 실측한 적은 없다.**

가격 단위의 참고로 Lightsail Linux public IPv4 인스턴스는 2GB $12, 4GB $24,
8GB $44/월이며 snapshots는 $0.05/GB-month다. 이 가격은 수용 인원 검증값이 아니다.
서버 2개·로드밸런서·DB/Redis의 별도 장애 도메인·백업이 필요하면 각각 추가된다.
단일 VM의 저가 구성과 관리형 전달 계층의 가용성을 동급으로 비교하지 않는다.
[Lightsail 가격](https://aws.amazon.com/lightsail/pricing/).

36개월 총비용은 다음 식으로 비교한다.

```text
36 × (공통 API/DB/Redis비 + 전달 증분비 + REST 조회 증분비
      + 전송/로그/TURN비 + 월 운영시간 × 시간당 비용)
+ 전환 개발시간 × 시간당 비용
```

공통 비용은 이 표에서는 미확정 변수 B다. 관리형 WebSocket만 도입해도 B는 남는다.
예를 들어 전환에 40시간, 시간당 $25를 가정하면 $1,000이다(견적이 아닌 민감도 입력).
1,000명·8시간에서 AppSync $112.45 → CF $6.66의 차이만 보면 회수는 약 9.5개월,
추가 운영이 월 2시간($50)이면 약 17.9개월이다.
직접 운영의 추가 증설이 실제로 $24이고 CF가 $6.66이라면 같은 전환비 회수는 약 57.7개월이다.
서버 여유로 증설이 필요 없다면 전달료 절감만으로는 전환비를 회수하지 못한다.
반대로 관리형으로 장애 대응 시간을 크게 줄일 수 있다면 그 절감분을 더한다. 인건비를 $0으로 숨기지 않는다.

Lambda로 1초 폴링할 경우 같은 1,000명·8시간에서 512MB·20ms 조회라도
API Gateway+Lambda만 약 $1,311.84/월이다. 100ms는 $1,887.84, 955ms는 $8,043.85다.
DB와 조회 결과 egress는 별도다. 955ms는 사용자 보고서의 값이며 우리 코드의 실행시간이 아니다.
Lambda SSE는 같은 조건에서 연결 유지 실행시간만 약 $7,200이다.
이 계산을 Spring 폴링/SSE 비용으로 옮겨 붙이지 않는다.

## 비용을 줄이는 구현 순서와 전환 설계

1. 정상 연결 때 3초마다 반복하는 매칭 조회를 줄이되 먼저 이벤트 유실 복구를 설계한다.
   Redis pub/sub 유실은 WebSocket 연결이 살아 있는 상태에서도 발생하므로 `connected`만 보고
   폴링을 완전히 끄면 안 된다. 개인 알림의 DB outbox/버전·재전송·클라이언트 중복 제거 또는
   명확한 최대 지연을 가진 reconciliation이 필요하다. 짧은 제안 만료 시간을 보존한다.
2. 모집 알림을 게임/모드 범위로 한정하고 게시판/내 모집의 불필요한 동시 재조회를 분리한다.
   차단 등 사용자별 필터 결과를 공용 캐시에 섞지 않는다. 관련 변경의 즉시 반영과 현재 문서의
   목록 순서 유지 요구를 보존한다. 프론트 미리보기와 실제 서버 성능을 분리한다.
3. 그 후 전달량·DB 조회량·CPU·RSS·egress를 측정해서 직접 운영의 실제 증분비를 산출한다.
   노드 수가 커지면 Redis 전역 팬아웃 비용도 측정한다.
4. 별도 중계를 운영해야 하고 절감액이 전환비를 회수한다면 CF Hibernation을 먼저 검증한다.
   클라이언트 `EventStream`과 서버 이벤트 계약은 어댑터로 유지한다. 매칭 핵심 로직은 Spring에 둔다.

CF 대안의 구체적인 경로는 다음과 같다. 아직 제품에 구현하거나 배포한 것은 아니다.

```text
Spring DB commit → outbox/재시도 → HTTPS 서명 발행 → Worker → 사용자 shard DO → WebSocket
브라우저 signal → Spring REST(인증·파티 소속 확인) → 같은 개인 전달 경로
브라우저 재연결 → 현재 상태/마지막 버전 조회 → 누락 상태 복구
음성/채팅 → 기존 WebRTC / 필요 시 TURN
```

Worker는 사용자 범위 토큰으로 개인 채널 구독을 제한하고 서버 발행 자격 증명을 브라우저에 주지 않는다.
DO는 hibernation attachment로 세션을 복원하고 auto-response heartbeat를 사용한다.
주기 타이머·상주 outbound WebSocket·사용자별 상시 실행 DO를 만들면 비용 전제가 깨진다.
접속 종료/파티 이탈의 현재 의미를 보존하려면 backend presence lease 갱신 경로가 필요하며
그 추가 호출량은 현재 계산에 포함되지 않아 전환 실험에서 별도 측정해야 한다.
클라이언트가 같은 메시지를 여러 번 받아도 결과를 중복 처리하지 않게 한다.
기존 Redis Sentinel은 매칭 때문에 남으며, 이벤트 중계를 바꾸는 것만으로 DB/Redis HA가 해결되지 않는다.

AppSync 대안도 개인 채널 권한, 발행 재시도, 상태 복구, presence 갱신이 필요하다.
managed fanout은 메시지의 영속 저장이나 정확히 한 번 처리를 자동 보장하는 것으로 취급하지 않는다.
CF는 APAC 위치 힌트를 줄 수 있지만 서울 리전 고정을 보장하지 않는다. 한국 사용자 지연을 검증한다.
[DO 위치 문서](https://developers.cloudflare.com/durable-objects/reference/data-location/).
DO당 요청량·CPU·메모리 한도가 있으므로 shard 1,000명은 초깃값이며 실제 검증으로 조정한다.
[DO 한도](https://developers.cloudflare.com/durable-objects/platform/limits/).

## 실제 전환의 통과 조건

- 같은 사용자/이벤트/인증/재접속 시나리오로 Spring WS, Spring SSE, AppSync, CF를 비교한다.
  각 조건 최소 5회, 순서 교대, DB 연결을 초기화하고 준비 실패도 실패율 분모에 포함한다.
- 한국 클라이언트 → commit → 실제 수신까지 시간, 1초 내 비율, 누락·중복,
  DB/REST 호출 수, 서버 CPU/RSS, 실제 provider usage를 기록한다. DO 실행시간 가정을 실측으로 교체한다.
- 동시 100/1,000/10,000명, 1KiB/6KiB, 평균/폭주/느린 수신자, 토큰 갱신,
  전원 재연결, 노드 종료, Redis failover, provider 발행 실패를 각각 실행한다.
- 다른 사용자 채널 구독·파티 외 signal이 거절되어야 한다. 끊긴 동안 성공/실패 상태가 복구되어야 한다.
- 24시간 이상 지속 실험으로 누수·재접속·실제 청구 단위를 확인하고 36개월 TCO를 다시 계산한다.
  현재는 이를 통과했다는 주장을 하지 않는다.

이번 작업의 산출물은 비교 보고서와 계산기다. 요금이 발생하는 리소스 생성,
현재 전송 구현의 제거, 성공/실패 알림 기능 구현은 수행하지 않았다.
