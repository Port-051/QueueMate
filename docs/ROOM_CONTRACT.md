# `room` 계약 가운데 `platform` 에 걸리는 부분 — `room` 의 `contracts/room-api.md` 발췌

## `platform` 에서 이것이 뜻하는 것 (이 절만 `platform` 에서 쓴 글이다. 아래 "발췌 시작"부터는 원본 그대로다)

`platform` 과 `room` 은 서로 호출하지 않는다(docs/11 #15 · D-16). 잇는 것은 **입장권**(이 앱이 내주고 `room` 이 서명만 검증한다 — 형식은 미정)과
**방 키**(`room` 이 쓰고 이 앱이 읽는다) 둘뿐이다. 아래 발췌는 그 가운데 이미 정해지고 구현된 쪽이다. 규칙은 `CLAUDE.md` §3.3 · §7.1.

**읽는 것.**

- **방이 살아 있는가** — 방장 키 `qm:room:{roomId}:host` 하나를 `EXISTS` 한다. **이 키가 있다 = 방이 있다.** 목록을 그릴 때와 입장권을 내줄 때 본다.
- **몇 명인가** — 멤버 SET `qm:room:{roomId}:members` 의 `SCARD`. 방장이 포함된 수이고 정원은 5다. 방장 확정 때 현재 인원도 이 SET 에서 읽는다.
  **이 수는 길어야 수명(600초)만큼 부풀 수 있다** — 말없이 사라진 사람의 이름이 방장의 다음 접속 확인까지 SET 에 남는다.
- 방장 키가 없으면 **방장이 나갔거나 사라진 것**이다 — 방의 수명은 방장의 접속 확인만 늘리므로 명시적 나가기와 연결 끊김이 같은 결과가 된다.
  방장이 나가면 방에 다른 사람이 있어도 방이 통째로 없어진다(방장 확정 전까지). 방장이 말없이 사라진 방은 최대 10분 살아 있는 것처럼 보인다.
- **`room` 은 방이 없어져도 이 앱에 알리지 않는다**(호출도 큐도 없다). 이 앱이 방장 키를 보고 **스스로** 글을 "만료"로 바꾼다(docs/11 D-11 11번 · D-16).
  이 앱이 늦더라도 `room` 쪽에 안전망이 있다 — 없는 방에는 입장이 404 `ROOM_NOT_FOUND` 로 거절된다.

**하지 말 것.**

- **방 키에 쓰지 않는다.** 읽기만 한다("닫힘" 표시를 쓸지는 미정이다 — `CLAUDE.md` §7.1).
- **입장 표시 키 `qm:user:active-room:{userId}` 와 `matching` 의 활성 요청 키 `qm:user:active-request:{userId}` 는 만지지 않는다.** "자동 매칭 대기와 방은 한 번에
  하나만"은 `room` 과 `matching` 이 키 둘로 지킨다(docs/11 D-19) — 이 앱은 관여하지 않는다.
- **키 이름을 따로 적지 않는다.** 구현할 때 접두사는 상수 한 곳에만 두고 원본이 `room` 의 `redisKeys/RoomKeys.java` 임을 주석에 적는다. 어긋나도
  컴파일 · 테스트는 통과하고 목록만 조용히 틀린다.
- **방을 만들려 들지 않는다.** 방은 브라우저가 `room` 의 "방 만들기"를 불러서 생긴다. 입장은 방을 만들지 않는다(없는 방은 404).

**아직 정해야 하는 것.**

- **"아직 안 만들어진 방"과 "사라진 방"을 가리는 법.** 방장이 글을 쓴 직후, 방 만들기를 부르기 **전**에는 방장 키가 없다. 목록을 그리면서
  "방장 키가 없다 → 방이 사라졌다 → 글을 만료로"를 그대로 적용하면 **방금 쓴 글을 만료시킨다.** 방법의 예 — 글 작성 직후 일정 시간은 만료 검사를
  건너뛴다 / 방이 한 번 생긴 적이 있는 글만 검사한다. **정해지지 않았다**(`CLAUDE.md` §7.1).
- **입장권.** 지금 `room` 은 입장권 없이 돈다(`TEMP-NO-PLATFORM`) — 누구나 아무 `roomId` 로 방을 만들고 방장이 되며, 요청의 `userId` 를 그대로 믿는다.
  입장권이 정해지면 방 만들기가 방장임을 입장권으로 확인하고, 그 요청이 그대로 남는지 방장의 첫 입장에 합쳐지는지도 다시 정한다.
  이 앱이 생기면 채워 줘야 하는 자리의 목록은 `../room/START_HERE.md` §2 다.
- **이 앱이 낼 알림**(`PARTY_*` · `FRIEND_*`)의 이름과 `payload`. `room` 은 `PARTY_*` 를 다시 쓰지 않고 `ROOM_*` 로 새 이름을 지었다 — 계약 원본과
  합칠 때 같은 뜻인지 맞춰야 한다.
- **자동 매칭으로 확정된 파티의 방.** 확정된 사용자는 활성 요청 키(`status=PARTY`)가 남아 있어 그대로는 아래 "입장"이 409 `ALREADY_QUEUED` 로 거절된다.
  "방이 닫힐 때 `room` 이 그 키를 지운다"는 가능성은 D-19 로 없어졌다 — 푸는 주체는 `matching` 이나 이 앱 쪽에서 찾아야 한다(`CLAUDE.md` §7).

## Redis 키 — `platform` 이 읽는다 (`CLAUDE.md` §3.4)

**이름과 구조는 두 앱의 약속이다. 이 서비스가 혼자 바꿀 수 없다.** 원본 상수는 `redisKeys/RoomKeys.java` 다.

| 키 | 자료형 | 값 | 뜻 |
|---|---|---|---|
| `qm:room:{roomId}:host` | STRING | 방장의 `userId` | **이 키가 있다 = 방이 있다.** 방을 만들 때 쓰고, 방장이 나가면 방과 함께 지운다 |
| `qm:room:{roomId}:members` | SET | 방에 있는 사람의 `userId`(방장 포함) | `SCARD` 가 현재 인원이다. 정원은 5 |
| `qm:user:active-room:{userId}` | STRING | 들어가 있는 방의 `roomId` | 입장 표시 키. `matching` 도 `EXISTS` 로 본다 (docs/11 D-19) |

- **세 키 모두 수명이 있다**(기본 600초, `ROOM_TTL_SECONDS`). 방장 키와 멤버 SET 은 **방장의 접속 확인만**, 입장 표시 키는 그 사람의 접속 확인이 늘린다(위 "접속 확인").
  그래서 `platform` 이 읽을 때 **방장 키가 없으면 방장이 나갔거나 사라진 것**이다. 멤버 SET 에는 유령이 잠깐 남을 수 있다 — 인원수는 길어야 수명만큼 부풀 수 있다.
- **방장이 나가면 방이 사라진다**(방장 확정 전까지. 방에 다른 사람이 있어도 마찬가지다) — 세 종류의 키가 함께 지워진다: 방장 키, 멤버 SET, **남아 있던 전원의 입장 표시 키.**
  `platform` 은 방장 키가 없으면 그 글을 "만료"로 바꾼다(docs/11 D-11 11번).

## 방 만들기 — `POST /api/v1/rooms/{roomId}?userId={userId}`

요청 본문은 없다. **부른 사람이 방장이 되고, 만들면서 곧바로 그 방에 들어와 있다**(정원 5명에 방장이 포함된다). (2026-09-19 정함)

> **임시 처리(`TEMP-NO-PLATFORM`)** — 지금은 누구나 아무 `roomId` 로 방을 만들고 방장이 된다. 원래는 `platform` 이 글을 쓴 사람에게 내준
> 입장권이 "이 방의 방장은 이 사람"이라고 말해 준다(docs/11 D-16). 입장권이 정해지면 이 요청이 그대로 남는지, 방장의 첫 입장에 합쳐지는지 다시 정한다.

| HTTP | `code` | 언제 | 클라이언트가 할 일 |
|---|---|---|---|
| 201 | — (본문 없음) | 방을 만들었다 | 방 화면으로 |
| 200 | — (본문 없음) | **이미 내가 만든 방이다** — 새로고침 · 재시도. 서버에서 바뀐 것은 없다 | 201 과 같다 |
| 409 | `ALREADY_QUEUED` | 자동 매칭을 돌리는 중이다 (docs/11 D-11 9번 · D-19) | 매칭을 취소해야 만들 수 있다 |
| 409 | `IN_OTHER_ROOM` | 다른 방에 들어가 있다(자기가 방장인 다른 방 포함) | 그 방에서 나와야 한다 |
| 409 | `ROOM_ALREADY_EXISTS` | 이미 다른 사람이 방장인 방이다 | — |

- 거절되면 **서버에는 아무것도 쓰이지 않는다.**
- 구현: `lua/create-room.lua` 의 반환값 ↔ `domain/CreateResult` ↔ `controller/RoomController#create`.

## 입장 — `POST /api/v1/rooms/{roomId}/members?userId={userId}`

요청 본문은 없다. (2026-09-19 정함)

| HTTP | `code` | 언제 | 클라이언트가 할 일 |
|---|---|---|---|
| 201 | — (본문 없음) | 방에 들어왔다 | 방 화면으로. 방에 있는 사람 목록은 목록 조회로 받는다 |
| 200 | — (본문 없음) | **이미 이 방에 들어와 있다** — 새로고침 · 재시도. 서버에서 바뀐 것은 없다 | 201 과 같다 |
| 409 | `ALREADY_QUEUED` | 자동 매칭을 돌리는 중이다 — `matching` 의 활성 요청 키가 있다 (docs/11 D-11 9번 · D-19) | 매칭을 취소해야 들어올 수 있다. 상태는 `matching` 의 `GET /api/v1/match-requests` 로 복구한다 |
| 409 | `ROOM_FULL` | 방이 가득 찼다 — 방장 포함 5명 (D-11 10번) | 목록으로 돌아간다 |
| 409 | `IN_OTHER_ROOM` | 다른 방에 들어가 있다 — 입장 표시 키의 값이 이 방이 아니다 | 그 방에서 나와야 한다 |
| 404 | `ROOM_NOT_FOUND` | 그런 방이 없다 — 만들어진 적이 없거나 **방장이 나가서 사라졌다.** 입장은 방을 만들지 않는다 | 목록으로 돌아간다 |

- 방장은 방을 만들 때 이미 들어와 있으므로 방장이 입장을 부르면 200 이다.
- 거절되면 **서버에는 아무것도 쓰이지 않는다.**
- 짝이 되는 `matching` 쪽 거절 — 방에 있는 사용자가 매칭을 요청하면 `matching` 이 409 `IN_ROOM` 을 준다(`matching/contracts/README.md` A-10).
- 구현: `lua/enter-room.lua` 의 반환값 ↔ `domain/EnterResult` ↔ `controller/RoomMemberController#enter`.

## 접속 확인 — `POST /api/v1/rooms/{roomId}/heartbeat?userId={userId}`

**브라우저가 방에 있는 동안 1분마다 부른다 — "나 아직 이 방에 있다".** 요청 본문은 없다. 방 키와 입장 표시 키에는 **수명(기본 600초, `ROOM_TTL_SECONDS`)**이
걸려 있고 이 요청이 그 수명을 다시 건다. 신호가 끊기면 수명이 다해 **저절로 사라진다** — 나가기를 못 누르고 탭을 닫아도, room 이 죽어 있어도 마찬가지다.
SSE 의 `heartbeat` 이벤트(서버 → 브라우저, `notification` 이 보낸다)와는 **방향도 용도도 다른 것**이다. (2026-09-20 정함)

| HTTP | `code` | 언제 | 클라이언트가 할 일 |
|---|---|---|---|
| 204 | — | 수명을 늘렸다 | 없다. 1분 뒤에 또 보낸다 |
| 403 | `NOT_IN_ROOM` | 이 방에 없는 사람이다 — 신호가 끊겨 있던 동안 수명이 다해 빠졌거나, 이미 나갔다 | **방 화면을 닫는다.** 다시 들어가려면 입장부터 한다 |
| 404 | `ROOM_NOT_FOUND` | 방이 없어졌다 — **방장의 신호가 끊겨 방의 수명이 다했다.** 이 사람의 입장 표시는 이 요청이 지웠다 | 방 화면을 닫는다 |

- **방의 수명(방장 키 · 멤버 SET)은 방장의 신호만 늘린다.** 일반 멤버의 신호는 자기 입장 표시만 늘린다. 그래서 **방장이 말없이 사라지면 방이 저절로 없어진다**
  (방장의 연결 끊김 = 방장이 나간 것. docs/11 D-11 11번). 남아 있던 사람은 자기 다음 신호에서 404 를 받는다 — **이때는 `ROOM_CLOSED` 알림이 가지 않는다.**
  수명이 다하는 순간에는 room 의 코드가 돌지 않고, 그 뒤에는 누가 있었는지(멤버 SET)도 남아 있지 않다.
- **방장의 신호는 유령도 뺀다.** 말없이 사라진 멤버는 입장 표시가 만료된 뒤에도 멤버 SET 에 이름이 남는다(SET 의 원소에는 수명을 걸 수 없다).
  방장의 신호가 입장 표시가 이 방을 가리키지 않는 사람을 SET 에서 빼고, **남은 사람들(방장 포함)에게 그 사람마다 `ROOM_MEMBER_LEFT` 를 보낸다.**
  그래서 유령은 길어야 "수명 + 방장의 신호 주기"만큼 목록과 정원에 남는다.
- 기본값의 대가 — 방장이 말없이 사라진 방은 **최대 10분** 목록에 살아 있는 것처럼 보인다(명시적 나가기는 즉시 닫는다). 줄이려면 `ROOM_TTL_SECONDS` 를 줄인다.
  1분 주기인 이유 — 브라우저는 백그라운드 탭의 타이머를 분당 1회 정도로 늦춘다.

## 알림 — room 이 발행하는 것 (2026-09-19 정함)

| `type` | 언제 | 받는 사람 | `payload` |
|---|---|---|---|
| `ROOM_MEMBER_ENTERED` | 누가 방에 들어왔다(입장 201) | 방에 **이미 있던** 사람들. 들어온 본인은 받지 않는다 | `{"roomId": "...", "userId": "들어온 사람"}` |
| `ROOM_MEMBER_LEFT` | 누가 방에서 나갔다 — 나가기를 눌렀거나, **신호가 끊겨 방장의 접속 확인이 뺐다** | 방에 **남은** 사람들. 나간 본인은 받지 않는다 | `{"roomId": "...", "userId": "나간 사람"}` |
| `ROOM_CLOSED` | 방장이 나가서 방이 없어졌다 | 방에 **있던** 사람들. 방장 본인은 받지 않는다 | `{"roomId": "..."}` |
| `WEBRTC_SIGNAL` | 같은 방의 누가 시그널을 보냈다(위 "시그널 보내기") | 받는 사람 한 명 | `{"roomId", "fromUserId", "signal": 보낸 그대로}` |

- `PARTY_*` 를 다시 쓰지 않고 새 이름을 지은 이유 — 그 7종의 이름과 payload 가 이 컴퓨터의 문서에 없어 같은 뜻인지 확인할 수 없었다. 계약 원본과 합칠 때 맞춘다.
- 강퇴 알림의 이름은 강퇴를 만들 때 정한다.
