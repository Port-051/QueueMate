# `room` 계약 가운데 `platform` 에 걸리는 부분 — `room` 의 `contracts/room-api.md` 발췌

## `platform` 에서 이것이 뜻하는 것 (이 절만 `platform` 에서 쓴 글이다. 아래 "발췌 시작"부터는 원본 그대로다)

`platform` 과 `room` 은 서로 호출하지 않는다(docs/11 #15 · D-16). 잇는 것은 **입장권**(이 앱이 내주고 `room` 이 서명만 검증한다 — 형식은 미정)과
**방 키**(`room` 이 쓰고 이 앱이 읽는다) 둘뿐이다. 아래 발췌는 그 가운데 이미 정해지고 구현된 쪽이다(결정 로그에는 docs/11 D-21 · D-23 으로 남아 있다). 규칙은 `CLAUDE.md` §3.3 · §7.1.

**읽는 것.**

- **방이 살아 있는가** — 방장 키 `qm:room:{roomId}:host` 하나를 `EXISTS` 한다. **이 키가 있다 = 방이 있다.** 목록을 그릴 때와 입장권을 내줄 때 본다.
  **확정한 방에서는 이 키의 값(방장의 `userId`)이 바뀔 수 있다**(docs/11 D-23 — 방장이 나가면 남은 멤버가 넘겨받는다). 이름 · 자료형 · 값의 뜻은 그대로다 — 방 키 약속의 형식은 바뀌지 않았다.
- **몇 명인가** — 멤버 SET `qm:room:{roomId}:members` 의 `SCARD`. 방장이 포함된 수이고 정원은 5다. 방장 확정 때 파티원도 이 SET 에서 읽는다(아래 "방장 확정에서 이 앱이 할 일").
  **이 수는 길어야 수명(600초)만큼 부풀 수 있다** — 말없이 사라진 사람의 이름이 방장의 다음 접속 확인까지 SET 에 남는다.
- **누가 있는가** — 같은 SET 의 `SMEMBERS`(docs/11 D-20). 게시판 목록의 한 줄이 **방 안 사람들의 카드**와 **"찾는 포지션" 가운데 이미 있는 포지션의 강조**를 보여 주기 때문이다.
  순서는 이렇다 — **`SMEMBERS` 로 `userId` 목록을 받는다 → 이 앱의 DB 에서 그 사람들의 프로필(닉네임 · 티어 · 주 포지션 등)을 붙인다 → 요청자와 방 안 전원의 차단 관계를
  대조한다**(어느 방향이든 한 명이라도 걸리면 그 방을 목록에서 뺀다). **입장권을 내줄 때도 같은 대조를 한다.** `room` 은 `userId` 만 안다 — 닉네임 · 티어 · 포지션은 SET 에 없고,
  포지션의 출처는 프로필의 주 포지션이다(입장할 때 고르지 않는다). 유령이 SET 에 남아 있는 동안에는 카드에도 그 사람이 남고, **그 사람과 차단 관계인 사용자에게는
  이미 없는 사람 때문에 방이 잠깐 숨겨질 수 있다.** SET 이라 순서에는 뜻이 없다.
- **아래 발췌의 "방 안 사람 목록"(`GET …/members`)은 이 앱이 쓰는 길이 아니다.** 그 요청은 방 안의 사람만 볼 수 있고(403 `NOT_IN_ROOM`), 이 앱은 `room` 을 호출하지 않는다.
  방 밖에서 방 안을 보는 공개 창구는 이 앱의 목록이다 — 차단을 거르는 곳이 여기라서다.
- 방장 키가 없으면 **방이 없어진 것**이다. **확정하지 않은 방**은 방의 수명을 방장의 접속 확인만 늘리므로 방장의 명시적 나가기와 연결 끊김이 같은 결과가 된다 —
  방에 다른 사람이 있어도 방이 통째로 없어진다. 방장이 말없이 사라진 방은 최대 10분 살아 있는 것처럼 보인다.
- **확정한 방은 방장이 나가도 방이 이어진다(docs/11 D-23 — D-21 의 "확정 뒤에도 방이 통째로 없어진다"를 고쳤다).** 남은 멤버 가운데 한 명이 방장을 넘겨받아 방장 키의 값이 바뀔 뿐이고,
  방장 키는 그대로 있다(아래 발췌 "Redis 키" · "방장 확정" · "접속 확인"). 넘겨받을 사람이 없을 때만 방장 키 · 멤버 SET · 확정 표시 키가 함께 없어진다.
  **그래서 확정된 글을 "방장이 나갔으니 만료"로 다루면 안 된다 — 방장 키가 없어졌을 때가 방이 없어진 것이다.**
- **`room` 은 방이 없어져도 이 앱에 알리지 않는다**(호출도 큐도 없다). 이 앱이 방장 키를 보고 **스스로** 글을 "만료"로 바꾼다(docs/11 D-11 11번 · D-16).
  이 앱이 늦더라도 `room` 쪽에 안전망이 있다 — 없는 방에는 입장이 404 `ROOM_NOT_FOUND` 로 거절된다.

**방장 확정에서 이 앱이 할 일 (docs/11 D-21 · 아래 발췌 "방장 확정").**

- **확정 요청은 `room` 이 받는다**(`POST /api/v1/rooms/{roomId}/confirm` — 방장만 · 2명 이상 · 되돌릴 수 없다). **이 앱은 그 요청을 받지 않는다.** `room` 이 확정 표시 키
  `qm:room:{roomId}:confirmed` 를 쓰고, 그 뒤로 새 사람의 입장을 409 `ROOM_CONFIRMED` 로 거절한다. 확정과 입장이 둘 다 `room` 의 스크립트라 확정 순간에 누가 끼어드는 경쟁도 거기서 막힌다.
- **이 앱은 확정 표시 키와 멤버 SET 을 읽어** 글의 상태를 **"확정"** 으로 바꾸고 **파티원을 기록한다**(DB 에 남기는 일이다 — docs/11 D-16). 확정한 그 순간 방에 있던 전원(방장 포함)이
  파티원이다 — 방장이 고르지 않는다. **확정 표시 키가 있다 = 방장이 확정한 방이다.**
- **`room` 의 키에 쓰지 않는다.** docs/11 D-16 이 가능성으로 적었던 "이 앱이 확정 직전에 '닫힘' 표시를 쓰고 `room` 이 확인한다"는 **받지 않았다** — `room` 의 키는 `room` 만 쓴다(D-19 와 같은 이유).
- **미정 — 브라우저가 `room` 과 이 앱을 어떤 순서로 부르는가.** 이 앱을 만들 때 정한다(2026-09-21 에 검토한 방향이 있다 — 정하지 않았다. `CLAUDE.md` §7.2 (가)). 그때 같이 볼 것 둘(정해진 것이 아니라 계약을 읽다 보인 물음이다) —
  ① 이 앱이 읽는 시점의 멤버 SET 은 확정한 **그 순간**의 것과 다를 수 있다(확정 뒤에도 나가기 · 강퇴는 되고 새 입장만 막힌다). 확정 순간의 전원은 `room` 이 `ROOM_CONFIRMED` 알림의
  `members` 로 브라우저에 보낸 것이다. 확정 뒤에는 **방장도 바뀔 수 있다**(docs/11 D-23 — 방장 키의 값이 글을 쓴 사람과 달라질 수 있다). ② 확정한 방은 방장이 나가도 이어지지만(D-23), 넘겨받을 사람이 없으면
  방장 키 · 멤버 SET · 확정 표시 키가 함께 없어진다 — "방장 키가 없다 → 글을 만료로"(위)를 "확정"인 글에도 그대로 적용하는지.

**하지 말 것.**

- **방 키에 쓰지 않는다.** 읽기만 한다 — **확정 표시도 `room` 이 쓴다**(docs/11 D-21. "닫힘" 표시를 이 앱이 쓰는 방법은 받지 않았다). 이 읽기가 교과서대로면 "DB 공유로 통합하기"라는 것은 알고 감수한다 —
  **읽기 전용 · 키 넷(D-20 때는 셋이었고 확정 표시 키가 더해졌다) · 쓰는 주인 하나(`room`)**로 좁혀 두었다(docs/11 D-20 · D-21 · `CLAUDE.md` §3.3).
- **입장 표시 키 `qm:user:active-room:{userId}` 와 `matching` 의 활성 요청 키 `qm:user:active-request:{userId}` 는 만지지 않는다.** "자동 매칭 대기와 방은 한 번에
  하나만"은 `room` 과 `matching` 이 키 둘로 지킨다(docs/11 D-19) — 이 앱은 관여하지 않는다.
- **키 이름을 따로 적지 않는다.** 구현할 때 접두사는 상수 한 곳에만 두고 원본이 `room` 의 `redisKeys/RoomKeys.java` 임을 주석에 적는다. 어긋나도
  컴파일 · 테스트는 통과하고 목록만 조용히 틀린다.
- **방을 만들려 들지 않는다.** 방은 브라우저가 `room` 의 "방 만들기"를 불러서 생긴다. 입장은 방을 만들지 않는다(없는 방은 404).

**아직 정해야 하는 것.**

- **확정된 글에서 방장 키가 없을 때 어떻게 다루는가.** 확정한 방은 방장이 말없이 사라지면 방장 키가 만료된 때부터 다음 멤버의 접속 확인까지(늦어도 1분) **방장 키만 잠깐 없다** — 멤버 SET 과 확정 표시 키는 있다(docs/11 D-23 "감수하는 것". room 의 스크립트를 읽고 판단한 것이고 실험으로 확인하지는 않았다). 그래서 **확정된 글을 "방장 키가 없다" 하나로 곧바로 만료시키면 안 된다.** 잠깐 없는 것과 방이 정말 없어진 것을 어떻게 가를지(멤버 SET · 확정 표시 키도 같이 보는지 등)는 미정이다.
- **게시판 채널 — 채널 이름의 원본 상수를 어느 서비스에 둘지.** 목록을 F5 없이 갱신하려고 이 앱과 `room` 이 `qm:pubsub:board`(게임을 구분하지 않는 하나 — docs/11 D-22)에 `BOARD_CHANGED`
  (`payload` 는 `{}`)를 발행한다(docs/11 D-20 · D-22. **`room` 의 발행은 구현됐다 — 2026-09-21, D-23.** 이 앱의 발행은 아직 없다 — `CLAUDE.md` §3.2). **"`room` 이 어느 게임의 채널에 발행할지를 어떻게 아는가"는 D-22 로 물음째 없어졌다** — 발행하는 쪽이 게임을 알 필요가
  없어 아래 "Redis 키" 약속도 입장권도 이 때문에 바뀌지 않는다. 남은 것은 채널 이름의 원본 상수를 둘 곳과 프런트가 재요청을 묶는 간격이다.

- **"아직 안 만들어진 방"과 "사라진 방"을 가리는 법.** 방장이 글을 쓴 직후, 방 만들기를 부르기 **전**에는 방장 키가 없다. 목록을 그리면서
  "방장 키가 없다 → 방이 사라졌다 → 글을 만료로"를 그대로 적용하면 **방금 쓴 글을 만료시킨다.** 방법의 예 — 글 작성 직후 일정 시간은 만료 검사를
  건너뛴다 / 방이 한 번 생긴 적이 있는 글만 검사한다. **정해지지 않았다**(`CLAUDE.md` §7.1).
- **입장권.** 지금 `room` 은 입장권 없이 돈다(`TEMP-NO-PLATFORM`) — 누구나 아무 `roomId` 로 방을 만들고 방장이 되며, 요청의 `userId` 를 그대로 믿는다.
  입장권이 정해지면 방 만들기가 방장임을 입장권으로 확인하고, 그 요청이 그대로 남는지 방장의 첫 입장에 합쳐지는지도 다시 정한다.
  이 앱이 생기면 채워 줘야 하는 자리의 목록은 `../room/START_HERE.md` §2 다.
- **이 앱이 낼 알림**(`PARTY_*` · `FRIEND_*`)의 이름과 `payload`. `room` 은 `PARTY_*` 를 다시 쓰지 않고 `ROOM_*` 로 새 이름을 지었다 — 계약 원본과
  합칠 때 같은 뜻인지 맞춰야 한다.
- **자동 매칭으로 확정된 파티의 방.** 확정된 사용자는 활성 요청 키(`status=PARTY`)가 남아 있어 그대로는 아래 "입장"이 409 `ALREADY_QUEUED` 로 거절된다.
  "방이 닫힐 때 `room` 이 그 키를 지운다"는 가능성은 D-19 로 없어졌다 — 푸는 주체는 `matching` 이나 이 앱 쪽에서 찾아야 한다(`CLAUDE.md` §7).

## Redis 키 — `platform` 이 읽는다 (`CLAUDE.md` §3.4)

**이름과 구조는 두 앱의 약속이다. 이 서비스가 혼자 바꿀 수 없다.** 원본 상수는 `redisKeys/RoomKeys.java` 다.

| 키 | 자료형 | 값 | 뜻 |
|---|---|---|---|
| `qm:room:{roomId}:host` | STRING | 방장의 `userId` | **이 키가 있다 = 방이 있다.** 방을 만들 때 쓰고, 방이 없어질 때 함께 지운다. **확정한 방에서는 값이 바뀔 수 있다** — 방장이 나가면 남은 멤버가 넘겨받는다(docs/11 D-23). 이름 · 자료형 · 값의 뜻은 그대로다 |
| `qm:room:{roomId}:members` | SET | 방에 있는 사람의 `userId`(방장 포함) | `SCARD` 가 현재 인원이다. 정원은 5. `platform` 은 `SMEMBERS` 로 `userId` 목록도 읽어 자기 DB 의 프로필을 붙이고 차단을 대조한다(docs/11 D-20). **원소는 `userId` 뿐이다** — 포지션 · 프로필을 담지 않는다 |
| `qm:room:{roomId}:confirmed` | STRING | 그 방의 `roomId` | **확정 표시 키. 이 키가 있다 = 방장이 확정한 방이다.** `platform` 이 방장 확정을 기록할 때 이 키와 멤버 SET 을 읽는다 |
| `qm:user:active-room:{userId}` | STRING | 들어가 있는 방의 `roomId` | 입장 표시 키. `matching` 도 `EXISTS` 로 본다 (docs/11 D-19) |

- **네 키 모두 수명이 있다**(기본 600초, `ROOM_TTL_SECONDS`). 방장 키 · 멤버 SET · 확정 표시 키는 **방장의 접속 확인만**, 입장 표시 키는 그 사람의 접속 확인이 늘린다(위 "접속 확인").
  **확정한 방은 예외다(docs/11 D-23)** — 일반 멤버의 접속 확인도 멤버 SET 과 확정 표시 키의 수명을 늘린다(방장 키는 늘리지 않는다).
  멤버 SET 에는 유령이 잠깐 남을 수 있다 — 인원수는 길어야 수명만큼 부풀 수 있다.
- **확정하지 않은 방은 방장이 나가면 방이 사라진다**(방에 다른 사람이 있어도 마찬가지다. 명시적 나가기든 연결 끊김이든) — 방장 키, 멤버 SET, **남아 있던 전원의 입장 표시 키**가 함께 지워진다.
  그래서 `platform` 이 읽을 때 **방장 키가 없으면 방이 없어진 것**이다. `platform` 은 방장 키가 없으면 그 글을 "만료"로 바꾼다(docs/11 D-11 11번).
- **확정한 방은 방장이 나가도 방이 이어진다(D-23)** — 방장 키의 값이 남은 멤버의 `userId` 로 바뀐다. **"방장 키가 있다 = 방이 있다"는 그대로 성립한다.** `platform` 이 알아야 하는 것은 **확정한 방에서는 방장 키의 값이 바뀔 수 있다**는 것 하나이고,
  방 키 약속의 형식은 바뀌지 않는다. 넘겨받을 사람이 없을 때만 방이 없어진다 — 방장 키 · 멤버 SET · 확정 표시 키가 함께 지워진다.

## 방 만들기 — `POST /api/v1/rooms/{roomId}?userId={userId}`

요청 본문은 없다. **부른 사람이 방장이 되고, 만들면서 곧바로 그 방에 들어와 있다**(정원 5명에 방장이 포함된다). (2026-09-19 정함)

> **임시 처리(`TEMP-NO-PLATFORM`)** — 지금은 누구나 아무 `roomId` 로 방을 만들고 방장이 된다. 원래는 `platform` 이 글을 쓴 사람에게 내준
> 입장권이 "이 방의 방장은 이 사람"이라고 말해 준다(docs/11 D-16). 입장권이 정해지면 이 요청이 그대로 남는지, 방장의 첫 입장에 합쳐지는지 다시 정한다.

| HTTP | `code` | 언제 | 클라이언트가 할 일 |
|---|---|---|---|
| 201 | — (본문 없음) | 방을 만들었다 | 방 화면으로 |
| 200 | — (본문 없음) | **이미 내가 만든 방이다** — 새로고침 · 재시도. 서버에서 바뀐 것은 없다 | 201 과 같다 |
| 409 | `ALREADY_QUEUED` | 자동 매칭을 돌리는 중이다 (docs/11 D-11 9번 · D-19) | 매칭을 취소해야 만들 수 있다 |
| 409 | `IN_OTHER_ROOM` | 다른 방에 들어가 있다(자기가 방장인 다른 방 포함) | 그 방에서 나와야 한다 |
| 409 | `ROOM_ALREADY_EXISTS` | 이미 다른 사람이 방장인 방이다 | — |

- 거절되면 **서버에는 아무것도 쓰이지 않는다.**
- 구현: `lua/create-room.lua` 의 반환값 ↔ `domain/CreateResult` ↔ `controller/RoomController#create`.

## 입장 — `POST /api/v1/rooms/{roomId}/members?userId={userId}`

요청 본문은 없다. (2026-09-19 정함)

| HTTP | `code` | 언제 | 클라이언트가 할 일 |
|---|---|---|---|
| 201 | — (본문 없음) | 방에 들어왔다 | 방 화면으로. 방에 있는 사람 목록은 목록 조회로 받는다 |
| 200 | — (본문 없음) | **이미 이 방에 들어와 있다** — 새로고침 · 재시도. 서버에서 바뀐 것은 없다 | 201 과 같다 |
| 409 | `ALREADY_QUEUED` | 자동 매칭을 돌리는 중이다 — `matching` 의 활성 요청 키가 있다 (docs/11 D-11 9번 · D-19) | 매칭을 취소해야 들어올 수 있다. 상태는 `matching` 의 `GET /api/v1/match-requests` 로 복구한다 |
| 409 | `ROOM_FULL` | 방이 가득 찼다 — 방장 포함 5명 (D-11 10번) | 목록으로 돌아간다 |
| 409 | `IN_OTHER_ROOM` | 다른 방에 들어가 있다 — 입장 표시 키의 값이 이 방이 아니다 | 그 방에서 나와야 한다 |
| 404 | `ROOM_NOT_FOUND` | 그런 방이 없다 — 만들어진 적이 없거나 **방장이 나가서 사라졌다.** 입장은 방을 만들지 않는다 | 목록으로 돌아간다 |
| 409 | `ROOM_CONFIRMED` | **방장이 확정한 방이다.** 새 사람은 못 들어온다 — 자리가 비어 있어도 마찬가지다(아래 "방장 확정") | 목록으로 돌아간다 |

- 방장은 방을 만들 때 이미 들어와 있으므로 방장이 입장을 부르면 200 이다.
- 거절되면 **서버에는 아무것도 쓰이지 않는다.**
- 짝이 되는 `matching` 쪽 거절 — 방에 있는 사용자가 매칭을 요청하면 `matching` 이 409 `IN_ROOM` 을 준다(`matching/contracts/README.md` A-10).
- 구현: `lua/enter-room.lua` 의 반환값 ↔ `domain/EnterResult` ↔ `controller/RoomMemberController#enter`.

## 방장 확정 — `POST /api/v1/rooms/{roomId}/confirm?userId={userId}`

요청 본문은 없다. **방장만** 부를 수 있다. 확정한 **그 순간 방에 있던 전원(방장 포함)이 파티원**이 된다 — 원치 않는 사람은 그 전에 강퇴한다.
**확정되면 새 사람이 못 들어오고, 되돌릴 수 없다.** (2026-09-20 정함)

> **프런트가 할 일** — 되돌릴 수 없으므로 확정 버튼을 누르면 "확정하면 되돌릴 수 없습니다"를 띄우고 **한 번 더 수락을 눌러야** 이 요청을 보낸다.
> 서버는 그 확인을 강제할 수 없다. 서버 쪽 안전장치는 아래의 200 하나다 — 버튼을 두 번 눌러도 아무 일이 없다.

| HTTP | `code` | 언제 | 클라이언트가 할 일 |
|---|---|---|---|
| 204 | — | 확정했다 | 없다. 파티원은 `ROOM_CONFIRMED` 알림의 `members` 로 온다(방장도 받는다) |
| 200 | — | **이미 확정된 방이다** — 재시도 · 두 번 누름. 서버에서 바뀐 것은 없다 | 204 와 같다 |
| 404 | `ROOM_NOT_FOUND` | 방이 없다 | 방 화면을 닫는다 |
| 403 | `NOT_HOST` | 부른 사람이 방장이 아니다(방 밖의 사람 포함). 방장인지는 방장 키와 비교해 스크립트 안에서 본다 | 방장이 아니면 확정 버튼을 보여 주지 않는다 |
| 409 | `NOT_ENOUGH_MEMBERS` | 혼자서는 확정할 수 없다 — 방장 포함 2명 이상이어야 한다 | — |

- **확정된 방.** 입장이 409 `ROOM_CONFIRMED` 로 거절된다 — **멤버가 나가 자리가 비어도**, 나간 파티원이 되돌아오려 해도 마찬가지다. 이미 들어와 있는 사람의 재입장(새로고침)은 그대로 200 이다.
  강퇴 · 시그널 · 일반 멤버의 나가기는 확정 전과 똑같다. **달라지는 것은 방장이 나갔을 때다(docs/11 D-23 — D-21 의 "확정 전과 똑같이 방을 없앤다"를 고쳤다).**
- **확정한 방은 방장이 나가도(또는 말없이 사라져도) 없어지지 않는다 — 방장 자리를 남은 멤버에게 넘긴다.** 방장이 나가기를 부른 경우는 위 "나가기", 말없이 사라진 경우는 아래 "접속 확인"에 있다.
  넘겨받을 사람이 없을 때만 방이 없어진다. 방장이 바뀌어도 방장 키는 늘 있으므로 강퇴 · 방 안 사람 목록 · 유령 빼기는 그대로 동작한다 — 새 방장이 한다.
- **확정은 저절로 풀리지 않는다.** 확정 표시 키에도 수명이 있지만 방장의 접속 확인이 같이 늘린다 — **확정한 방에서는 일반 멤버의 접속 확인도 늘린다**(D-23). 방이 없어질 때 같이 지워진다 — 같은 `roomId` 로 다시 만든 방은 확정돼 있지 않다.
- **확정과 입장은 둘 다 room 의 스크립트라서** 확정하는 순간에 누가 끼어드는 일이 없다. `ROOM_CONFIRMED` 의 `members` 가 곧 확정된 파티원이다.
- **`platform` 은 이 요청을 받지 않는다.** 글의 상태를 "확정"으로 바꾸고 파티원을 DB 에 기록하는 것은 `platform` 의 일이고, 그때 확정 표시 키와 멤버 SET 을 **읽는다**(아래 "Redis 키").
  "`platform` 이 닫힘 표시를 쓰고 room 이 확인한다"는 방법은 받지 않았다 — room 의 키는 room 만 쓴다(docs/11 D-19 와 같은 이유). 브라우저가 room 과 `platform` 을 어떤 순서로 부르는지는 `platform` 을 만들 때 정한다.
- 거절되면 **서버에는 아무것도 쓰이지 않는다.**
- 구현: `lua/confirm-room.lua` ↔ `domain/ConfirmResult` ↔ `service/RoomService#confirm` ↔ `controller/RoomController#confirm`. 입장 쪽은 `lua/enter-room.lua` 의 `KEYS[5]` · `EnterResult.ROOM_CONFIRMED`.

## 접속 확인 — `POST /api/v1/rooms/{roomId}/heartbeat?userId={userId}`

**브라우저가 방에 있는 동안 1분마다 부른다 — "나 아직 이 방에 있다".** 요청 본문은 없다. 방 키와 입장 표시 키에는 **수명(기본 600초, `ROOM_TTL_SECONDS`)**이
걸려 있고 이 요청이 그 수명을 다시 건다. 신호가 끊기면 수명이 다해 **저절로 사라진다** — 나가기를 못 누르고 탭을 닫아도, room 이 죽어 있어도 마찬가지다.
SSE 의 `heartbeat` 이벤트(서버 → 브라우저, `notification` 이 보낸다)와는 **방향도 용도도 다른 것**이다. (2026-09-20 정함. 확정한 방의 예외는 2026-09-21 — docs/11 D-23)

| HTTP | `code` | 언제 | 클라이언트가 할 일 |
|---|---|---|---|
| 204 | — | 수명을 늘렸다 | 없다. 1분 뒤에 또 보낸다 |
| 403 | `NOT_IN_ROOM` | 이 방에 없는 사람이다 — 신호가 끊겨 있던 동안 수명이 다해 빠졌거나, 이미 나갔다 | **방 화면을 닫는다.** 다시 들어가려면 입장부터 한다 |
| 404 | `ROOM_NOT_FOUND` | 방이 없어졌다 — **확정하지 않은 방인데 방장의 신호가 끊겨 방의 수명이 다했다.** 이 사람의 입장 표시는 이 요청이 지웠다. 이때 room 이 게시판 채널 신호를 보낸다(아래 "게시판 채널 신호") | 방 화면을 닫는다 |

- **확정하지 않은 방 — 방의 수명(방장 키 · 멤버 SET)은 방장의 신호만 늘린다.** 일반 멤버의 신호는 자기 입장 표시만 늘린다. 그래서 **방장이 말없이 사라지면 방이 저절로 없어진다**
  (방장의 연결 끊김 = 방장이 나간 것. docs/11 D-11 11번). 남아 있던 사람은 자기 다음 신호에서 404 를 받는다 — **이때는 `ROOM_CLOSED` 알림이 가지 않는다.**
  수명이 다하는 순간에는 room 의 코드가 돌지 않고, 그 뒤에는 누가 있었는지(멤버 SET)도 남아 있지 않다.
- **확정한 방은 예외다 — 방장이 말없이 사라져도 방을 이어 간다(docs/11 D-23).**
  - 확정한 방에 한해 **일반 멤버의 신호도 멤버 SET 과 확정 표시 키의 수명을 늘린다.** 세 키가 방장의 마지막 신호에서 같은 수명을 받으므로, 안 그러면 방장 키가 만료되는 순간 멤버 SET 과 확정 표시 키도 같이 사라져 이어 갈 방이 남지 않는다.
  - **방장 키는 늘리지 않는다** — 방장 키가 만료돼야 다음 사람이 넘겨받는다. 방장 키의 수명은 어느 방에서든 방장의 신호만 늘린다.
  - 방장 키가 만료된 뒤 **처음 접속 확인을 보낸 멤버가 방장이 된다**(`SET 방장 키 EX 수명`). 그 신호는 그대로 방장의 신호로 처리된다 — 방의 수명을 늘리고, 입장 표시가 만료된 옛 방장을 유령으로 빼서
    남은 사람들에게 `ROOM_MEMBER_LEFT` 를 보낸다(바로 아래). 응답은 204 그대로다. 클라이언트는 그 `userId` 가 자기가 알던 방장이면 방 안 사람 목록을 다시 조회한다 — 응답의 `hostId` 가 새 방장이다(위 "나가기").
  - **그 사이에 방장 키가 잠깐 없다.** 방장 키가 만료된 때부터 다음 멤버의 접속 확인까지(늦어도 1분) 멤버 SET 과 확정 표시 키는 있는데 방장 키가 없다 —
    그동안 방 안 사람 목록 · 강퇴 · 확정은 404 로 답한다(다음 접속 확인 뒤에 다시 부르면 된다). 그리고 방장 키가 만료되기 **전까지**는 방장 키의 값이
    이미 사라진 방장이라 강퇴와 유령 빼기를 할 사람이 없다. 스크립트를 읽고 판단한 것이고 실험으로 확인하지는 않았다 (docs/11 D-23 "감수하는 것")
- **방장의 신호는 유령도 뺀다.** 말없이 사라진 멤버는 입장 표시가 만료된 뒤에도 멤버 SET 에 이름이 남는다(SET 의 원소에는 수명을 걸 수 없다).
  방장의 신호가 입장 표시가 이 방을 가리키지 않는 사람을 SET 에서 빼고, **남은 사람들(방장 포함)에게 그 사람마다 `ROOM_MEMBER_LEFT` 를 보낸다.**
  그래서 유령은 길어야 "수명 + 방장의 신호 주기"만큼 목록과 정원에 남는다.
- 기본값의 대가 — 방장이 말없이 사라진 (확정하지 않은) 방은 **최대 10분** 목록에 살아 있는 것처럼 보인다(명시적 나가기는 즉시 닫는다). 줄이려면 `ROOM_TTL_SECONDS` 를 줄인다.
  1분 주기인 이유 — 브라우저는 백그라운드 탭의 타이머를 분당 1회 정도로 늦춘다.

## 알림 — room 이 발행하는 것 (2026-09-19 정함)

| `type` | 언제 | 받는 사람 | `payload` |
|---|---|---|---|
| `ROOM_MEMBER_ENTERED` | 누가 방에 들어왔다(입장 201) | 방에 **이미 있던** 사람들. 들어온 본인은 받지 않는다 | `{"roomId": "...", "userId": "들어온 사람"}` |
| `ROOM_MEMBER_LEFT` | 누가 방에서 나갔다 — 나가기를 눌렀거나, **신호가 끊겨 방장의 접속 확인이 뺐다.** **확정한 방의 방장이 나간 것도 이것이다**(방은 이어지고 방장이 바뀐다 — D-23) | 방에 **남은** 사람들. 나간 본인은 받지 않는다 | `{"roomId": "...", "userId": "나간 사람"}` |
| `ROOM_CLOSED` | 방장이 나가서 방이 없어졌다 — 확정하지 않은 방의 방장이 나갔다(확정한 방은 넘겨받을 사람이 없을 때만 없어지고, 그때는 받을 사람이 남아 있지 않다) | 방에 **있던** 사람들. 방장 본인은 받지 않는다 | `{"roomId": "..."}` |
| `ROOM_MEMBER_KICKED` | 방장이 누군가를 강퇴했다(강퇴 204) | 방에 **남은** 사람들(방장 포함) **+ 강퇴된 본인** | `{"roomId": "...", "userId": "강퇴된 사람"}` |
| `ROOM_CONFIRMED` | 방장이 파티를 확정했다 | 그 순간 방에 있던 **전원(방장 포함)** — 방장의 응답(204)에는 파티원이 없어서 방장도 알림으로 받는다 | `{"roomId": "...", "members": ["h", "u1", …]}` — 이 사람들이 파티원이다 |
| `WEBRTC_SIGNAL` | 같은 방의 누가 시그널을 보냈다(위 "시그널 보내기") | 받는 사람 한 명 | `{"roomId", "fromUserId", "signal": 보낸 그대로}` |

- `PARTY_*` 를 다시 쓰지 않고 새 이름을 지은 이유 — 그 7종의 이름과 payload 가 이 컴퓨터의 문서에 없어 같은 뜻인지 확인할 수 없었다. 계약 원본과 합칠 때 맞춘다.

### 게시판 채널 신호 — 구현됐다 (docs/11 D-20 · D-22 · D-23. 2026-09-20 정함, 2026-09-21 구현)

**위 알림과 채널이 다르다.** 위는 사용자 한 명의 채널이고, 이것은 **게시판 목록을 보고 있는, 누구인지 모르는 다수**에게 알리려는 **게시판 채널**이다.
게시판 목록의 한 줄이 방 안의 인원과 사람들의 카드를 보여 주므로(목록은 `platform` 이 아래 "Redis 키"의 멤버 SET 을 읽어 조립한다), 방의 인원이 바뀌면
보고 있는 화면이 F5 없이 갱신돼야 한다.

| 항목 | 값 |
|---|---|
| 채널 | `PUBLISH qm:pubsub:board` — **게임을 구분하지 않는 하나다**(D-22 가 D-20 의 게임별 세 채널을 고쳤다) |
| 봉투 | 위와 같은 네 칸. **`type` 은 `BOARD_CHANGED`, `payload` 는 빈 객체 `{}`** — `roomId` 도 `game` 도 싣지 않는다 |
| 언제 | 방의 인원이 바뀔 때 — 방 만들기(201) · 입장(201) · 나가기(나갔을 때 · 방이 없어졌을 때) · 강퇴(204) · 방장 확정(204) · 접속 확인이 유령을 뺐을 때(몇 명을 뺐든 한 번) · **접속 확인이 "방이 없어졌다"(404 `ROOM_NOT_FOUND`)를 돌려줄 때**(D-23). **아무것도 안 바뀐 경우에는 보내지 않는다** — 재입장(200) · 거절 |
| 받는 사람 | **`notification` 에 살아 있는 모든 SSE 연결.** `notification` 이 이 채널 하나를 구독해 서버에서 거르지 않고 그대로 보낸다 — **`topics` 파라미터는 없앴다**(D-22). `notification` 쪽은 **구현됐다** |
| 받은 클라이언트가 할 일 | **거르는 것은 클라이언트다** — 게시판 페이지(어느 게임이든)를 보고 있으면 `platform` 의 목록을 `GET` 으로 다시 요청하고, 게시판 페이지가 아니면 무시한다. 다른 게임의 방이 바뀐 신호에도 재요청이 나가므로 **재요청을 묶어서**(예: 몇 초에 최대 1번. 간격은 미정) 한 사람의 재요청이 간격당 1번을 넘지 않게 한다 |

- **이 신호는 "다시 받아라"일 뿐이다.** 데이터와 차단 거르기는 `platform` 의 목록 응답에서 온다. **`roomId` 도 싣지 않는다** — 방송은 사람별로 거를 수 없어서,
  차단 때문에 그 방이 숨겨진 사용자에게 "그 방이 바뀌었다"는 사실이 새어 나간다. room 이 프로필을 몰라도 되는 것도 이 덕이다.
- **room 은 방이 어느 게임의 것인지 몰라도 된다(D-22).** 채널이 하나이고 `payload` 가 `{}` 라서 발행하는 쪽이 게임을 알 필요가 없다 — 아래 "Redis 키"도 위 "방 만들기" · "입장" 요청도 바뀌지 않는다.
  게임을 알려면 방 키를 하나 더 두고(`qm:room:{roomId}:game` 을 검토했다) 방 만들기 API 와 Lua 를 고치고 `platform` 과의 방 키 약속에 키를 하나 더해야 했다.
- **왜 서버에서 거르지 않나(D-22).** 거르려면 `notification` 이 연결마다 주제를 기억하고 `topics` 파라미터 · 주제→연결 맵 · 표기 규칙을 가져야 한다. 클라이언트가 무시하면 전부 필요 없다.
  대가는 둘이다 — 다른 게임의 변화에도 재요청이 나가고(묶기로 상한을 둔다), 게시판을 안 보는 연결(방 안에서 음성 중인 사람 등)에도 작은 이벤트가 간다(인원이 바뀔 때마다 (연결 수)만큼 SSE 쓰기). MVP 규모에서 받아들인다.
  **다시 볼 조건** — 부담이 되면 `payload` 에 `game` 을 싣거나(그러면 room 이 게임을 알아야 한다) `topics` 를 되살린다.
- **`platform` 도 같은 채널에 발행한다** — 글이 생기거나 사라지거나 상태가 바뀔 때다.
- 발행 실패가 입장 · 나가기를 뒤집지 않는다는 것은 위 알림과 같다. 신호는 놓칠 수 있다 — 클라이언트는 SSE 를 (다시) 연결한 직후 목록을 다시 받는다.
- **수명이 다해 없어진 방은 없어지는 순간에는 신호를 내지 못한다** — 그 순간에는 room 의 코드가 돌지 않는다(위 "접속 확인"의 `ROOM_CLOSED` 와 같은 이유). **그 방에 남아 있던 멤버의 다음 접속 확인**(늦어도 1분 뒤)이
  404 를 받을 때 room 이 그것을 처음 알게 되고, **그때 신호를 보낸다(D-23 — D-20 의 "신호를 내지 못한다"를 줄였다).** 남은 사람이 여럿이면 각자 한 번씩 보내게 되지만 해가 없다 — "다시 받아라"일 뿐이고 프런트가 재요청을 묶는다.
  - **남는 한계 — 방장 혼자 있던 방.** 접속 확인을 보낼 사람이 없어 여전히 신호를 못 낸다. 다른 방의 신호나 새로고침으로 목록을 다시 받을 때 `platform` 이 방장 키가 없는 것을 보고 그 글을 뺀다.
  - Redis 키 만료 이벤트로 막는 방법은 받지 않았다 — room 이 구독을 해야 하고, 인스턴스가 여럿이면 중복 발행이 되고, 앱이 죽어 있던 동안의 만료는 놓친다.
- **미정.** "room 이 어느 게임의 채널에 발행할지를 어떻게 아는가"와 `topics` 표기의 미정은 D-22 로 물음째 없어졌다.
  - 채널 이름의 **원본 상수를 어느 서비스에 둘지**(알림 채널 접두사는 `matching` 의 `SharedKeys` 가 원본이다 — 같은 방식으로 갈지 정해지지 않았다. `notification` 은 자기 `redisKeys/BoardChannels.BOARD_CHANNEL` 에, room 은 자기 `redisKeys/SharedKeys.BOARD_CHANNEL` 에 적어 두었다 — **두 값이 같아야 한다**).
  - 프런트가 재요청을 묶는 간격 — room 의 일은 아니다.
- **방 안 사람 목록(`GET …/members`)은 그대로다** — 방 안의 사람만 본다(403 `NOT_IN_ROOM`). 방 밖에서 방 안을 보는 공개 창구는 `platform` 의 목록이다 — 차단을 거르는 곳이 거기라서다.
- 구현: `redisKeys/SharedKeys.BOARD_CHANNEL` · `notification/PushEventType.BOARD_CHANGED` · `notification/PushPublisher`. 보내는 곳은 `service/RoomService`(방 만들기 · 방장 확정)와 `service/RoomMemberService`(입장 · 나가기 · 강퇴 · 접속 확인)다.

| 방 안 사람 목록 — `GET /api/v1/rooms/{roomId}/members` | 방에 있는 사람만 볼 수 있다(`{roomId, hostId, members}`). 알림을 놓친 클라이언트가 상태를 다시 맞추는 조회다 |
| 내 방 찾기 — `GET /api/v1/rooms/me` | 입장 표시 키의 값을 그대로 돌려준다(`{"roomId": …}`, 없으면 `null`) |
