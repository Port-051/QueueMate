# 모집 게시판 구현과 검증

## 실행

- 실제 서버: PostgreSQL/Redis를 실행하고 기존 Spring Boot 실행 절차를 따른다. Flyway V7가 모집 메타데이터와 관측 이벤트 테이블을 추가한다.
- 실제 프런트: `cd frontend && npm run dev`. 배포 빌드는 `VITE_API_MODE=real npm run build`를 사용한다.
- 브라우저 데모: `cd frontend && npm run dev:mock`. 화면에 **체험 모드 · 예시 모집**을 표시하며 실제 사용자와 연결되지 않는다.
- 기존 별도 `mock-server/server.js`는 이전 CRUD 계약 검증용이다. 이번 모집 API 검증에는 Spring Boot 또는 브라우저 데모를 사용한다.

## 구현 범위

홈의 실시간/예약 탭에서 최대 10개의 모집을 조회하고, 같은 원본 요청으로 직접 신청하거나 자동 찾기에 참여한다.
신청 수락은 모집 참가이며, 정원이 찬 뒤 기존 proposal의 전원 수락을 거쳐 Party가 생성된다.
다인 모집 참가자는 자동 매처가 개별로 가져가지 않는다. 그룹의 자동 찾기가 켜져 있으면 빈자리 전체를 채울 수 있을 때 제안을 만든다.

티어는 직접 입력한 값이며 게임 API 인증 값이 아니다. 양방향 티어 범위·포지션·음성·목적 조건을 검사한다.
게임 내 최신 랭크 제한, 숨겨진 MMR, 계정의 실제 현재 티어를 검증하는 Riot API 연동은 포함하지 않는다.
현재의 게임별 정원·역할 중복 규칙, 차단, 시간 교집합, 중복 제안 방어는 계속 적용한다.

최초 생성 시각은 보존한다. BUMP는 5분 쿨다운으로 노출 순서를 갱신하고, 누적 노출과 별도로 갱신 이후의 노출을 비교한다.
추천순은 선호 일치, 현재 노출 회차의 노출 수, 최근 갱신 순서다. 최근 갱신순도 직접 고를 수 있다.
행의 절반 이상이 1초 동안 보일 때 노출을 기록하고 사용자·모집·날짜 단위로 중복을 제거한다.
새 목록은 확인 버튼으로 적용하고 기존 행의 모집 상태는 먼저 갱신한다.

생성/수정/직접 선택과 자동 선발은 PostgreSQL의 게임·모드별 트랜잭션 advisory lock으로 조정한다.
최종 제안은 기존 Redis 원자 claim과 DB active proposal unique 제약으로 보호한다.
자동 매처의 모집 선호 조회는 후보 집합별로 묶어 읽는다. 실서비스 규모의 부하·요금 수치는 아직 측정하지 않았다.

WebSocket은 빈 `RECRUITMENT_UPDATED` 알림을 전달한다. 조건과 신청자 정보를 전체 전송하지 않는다.
권한이 있는 REST 조회가 실제 상태를 결정한다. 이벤트 누락은 포커스 복귀와 15초 조회로 복구한다.
정원이 확정되면 홈에서 준비·음성·채팅을 제공한다. 공통 PartySessionProvider가 다른 메뉴에서도 연결과 대화를 유지한다.
음성 입력은 사용자가 직접 켜며, 저장된 과거 채팅이 아니라 현재 브라우저 세션의 WebRTC 대화다.

## 초기 운영 설정

| Spring 설정 | 기본값 | 의미 |
|---|---:|---|
| `queuemate.recruitment.confirm-minutes` | 10 | 실시간 활동 재확인 안내 |
| `queuemate.recruitment.stale-minutes` | 12 | 미확인 실시간 모집 숨김 |
| `queuemate.recruitment.suggestion-minutes` | 3 | 첫 조건 개선 안내 |
| `queuemate.recruitment.bump-minutes` | 5 | 끌어올림 최소 간격 |
| `queuemate.recruitment.reservation-prompt-minutes` | 30 | 예약 시작 전 확인 안내 |
| `queuemate.recruitment.group-sweep-ms` | 15000 | 다인 모집 빈자리 재탐색 |

운영 설정은 통계에서 추정한 대기시간이 아닌 초기 실험값이다. API의 `timing`이 실제 화면 안내 시각을 결정한다.
예약은 미접속으로 숨기지 않으며 예약 가능 시간이 지난 경우에만 닫힌다. 알림 옵션은 현재 화면의 후보 안내다.

## 관측과 해석

`recruitment_events`에 생성, 노출, 갱신, 확인, 신청, 참가, 조건 변경, 제안, 전원 수락, 전원 준비를 기록한다.
준비 완료는 실제 버튼 상태이며 실제 게임 시작을 뜻하지 않는다. PLAYING 추정도 별도로 취급한다.
`harness/sql/recruitment-funnel.sql`에 모집 기준 10분 내 준비율, 단계별 고유 모집 수, 예약 약속 대비 최초 준비 시각 조회를 제공한다.
검색을 시작한 전체 사용자 기준의 전환율, 이탈 이유, 예약 시각 재접속률, 개선 제안의 인과 효과는 이 기록만으로 확정할 수 없다.

## 검증 명령

```sh
./backend/gradlew -p backend test --console=plain
npm --prefix frontend run e2e
VITE_API_MODE=real npm --prefix frontend run build
```

API 통합 테스트는 PostgreSQL/Redis 컨테이너와 실제 HTTP·JWT·DB 제약을 사용한다.
티어 미입력과 양방향 조건, 차단, 동시 신청 수락의 정원 경쟁, 4인 모집과 자동 빈자리 채우기,
제안 파기 후 복귀, 전원 수락 전 Party 생성 금지, 갱신 제한, 오래된 버전 거부, 실시간 숨김과 예약 유지,
노출 중복 제거와 준비 완료 기록을 검증한다.
브라우저 테스트는 두 매치 흐름, 필터 독립성, 조건 변경의 미리보기/취소/적용, 모집 재사용,
새 목록의 순서 유지, 예약 시간, 접근성, 작은 화면, 메뉴 이동 중 미디어 유지와 기존 WebRTC 통신을 검증한다.

2026-09-13 검증 결과:

- 서버 전체 테스트 565개 통과, 실패·건너뜀 없음. 이 중 모집 API 통합 테스트 12개와 전체 알림의 개인정보 분리 검사 2개를 포함한다.
- 브라우저 E2E 전체 31개 통과. 마지막 조회 오류 처리 보완 후 게시판 4개를 다시 확인했다.
- 실제 API 모드의 TypeScript 검사와 Vite 배포 빌드 통과.
- 별도 PostgreSQL/Redis와 Spring Boot에 브라우저 두 개를 연결해 게임 계정 등록, 예약 생성·종료, 실시간 모집 신청, 방장 수락, 전원 수락, 전원 준비, WebRTC DataChannel 채팅 전달을 확인했다. 두 브라우저 모두 홈에 머물렀고 JavaScript 오류는 없었다.
- 390px 화면의 가로 넘침 없음. 관측 SQL 3개는 실제 테스트 DB에서 실행을 확인했다.

이 검증은 기능과 상태 전이의 확인이다. 실제 이용자의 매칭 시간 단축, 음성 품질 목표, 동시 접속 부하와 서버 비용은 운영 측정이 필요하다.
