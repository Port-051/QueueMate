# 14. Architecture Rationale (matching 발췌본)

> **이 파일은 발췌본이다.** 원문은 queueMate 저장소 `docs/14_ARCHITECTURE_RATIONALE.md`(408줄)에 있다.
> 매칭 엔진과 무관한 절 — 프런트엔드, 소셜/파티 서비스 분리, WebRTC/TURN, 배포 로드맵 — 은 뺐다.
>
> **뺀 절**: §2 API Gateway · §3 DB 개수 · §10 파티 서비스 분리 · §11 큐 소비 프로세스 ·
> §12 Lambda · §14 WebRTC 음성 · §15 TURN · §16 배포 로드맵 · "단계가 바뀌어도 안 바뀌는 것".

> 뺀 절이 필요하면 원문을 봐라.

## 1. 서버를 몇 개로 나눌까

**후보** ① 하나(3-tier 모놀리스) ② 4개 ③ 도메인마다 7개

**선택: ②**

**이유**
- 네 영역은 **재시작 비용이 비대칭**이다. `app:realtime`은 장수명 연결을 들고 있어 재시작이 비싸고, REST 앱은 언제든 교체 가능하다. 한 프로세스에 묶으면 가장 비싼 쪽 기준으로만 배포한다.
- 장애 격리: 한 영역의 OOM/무한루프가 나머지를 죽이지 않는다.
- 독립 배포 주기. 독립 스케일은 Stage 2(Fargate)부터 실현된다.

**기각한 이유**
- ① 배포·장애 반경이 통째로 묶인다. / ③ 스케일 축·재시작 비용이 같으면 나눌 값이 없다. 도메인이 다르다는 것만으로는 프로세스를 쪼갤 근거가 못 된다.

## 4. 서버끼리 어떻게 통신할까

**후보** ① Kafka/RabbitMQ ② Redis Streams ③ AWS SQS FIFO

**선택: ③**

**이유**
- **Redis Streams는 컨슈머 그룹으로 읽는 순간 순서가 깨진다.** `BlockCreated`와 `BlockRemoved`가 역전되면 차단이 해제로 뒤집혀 INV-6이 깨진다. FIFO는 `MessageGroupId` 단위로 순서를 보장한다.
- 재시도·DLQ·적체 알람·가시성 타임아웃 등 직접 짜야 할 것이 6개인데, SQS에선 설정 몇 줄이다.
- 서울 리전 FIFO는 100만 요청당 $0.50이고 **월 100만 건이 무료** → 이 규모에서 **월 $0**.

**기각한 이유**
- ① 브로커를 직접 운영해야 한다(`CLAUDE.md` §3 금지). SQS는 완전관리형이라 그 금지의 취지("직접 운영하지 마라")에 걸리지 않는다. / ② 위 순서 문제.

큐 3개: `ProposalConfirmed.fifo` / `PartyClosed.fifo` / `BlockChanged.fifo`. 각각 DLQ + `maxReceiveCount`.
전달은 at-least-once이므로 **소비자는 반드시 멱등해야 한다.**

## 5. 사용자 알림을 어떻게 보낼까

**후보** ① WebSocket 하나로 전부 ② SSE + 필요한 것만 WS ③ 폴링

**선택: ② (SSE 14종 + WebSocket 1종)**

**이유**
- 이벤트 14종이 전부 **서버→클라 단방향**이다. 단방향에 양방향 프로토콜을 쓸 이유가 없다.
- SSE는 HTTP라 `EventSource` 자동 재연결과 `Last-Event-ID` 재개가 **표준에 들어 있다.** 직접 짤 코드가 줄어든다.
- `WEBRTC_SIGNAL` 1종만 클라→서버 방향이 있어 WebSocket(`/ws`)이 필요하다.

**기각한 이유**
- ① 15종 중 1종 때문에 나머지 14종의 재연결·재개를 직접 구현하게 된다. / ③ 지연이 크고 요청 낭비가 크다.

운영 제약: 프록시 idle timeout(Stage 2 ALB 300초)보다 짧게 **heartbeat 15~30초** 필수.

## 6. 알림을 어느 서버가 보낼까

**후보** ① `app:platform`이 전담 ② 이벤트를 만든 서버가 각자 자기 연결로 ③ `app:realtime` 전담

**선택: ③**

**이유**
- **`app:reservation-batch`는 연결을 들 수 없다.** 외부 요청을 받지 않는 배치라 브라우저가 붙을 대상이 아니다. 그러므로 "발행자가 직접 보낸다"는 애초에 성립하지 않는다.
- 발행 앱과 연결 보유 앱이 다른 이상 fanout 장치(Redis Pub/Sub)는 어차피 필요하다. 그렇다면 연결을 보유하는 서비스를 **1개로 줄이는 쪽**이 낫다.
- sticky session·graceful drain·재전송 버퍼를 **한 벌만** 운영하면 된다. (브로드캐스트 + 로컬 userId 필터라 실제로는 sticky session도 필요 없다.)

**기각한 이유**
- ① `app:platform`은 stateless REST 앱으로 두는 게 배포 자유도를 지킨다. / ② 위 배치 문제 + 연결 운영 부담이 앱 수만큼 복제된다.

## 7. SQS와 Redis Pub/Sub을 왜 둘 다 쓰나

이름은 둘 다 "메시지"지만 **용도가 다르다.** 하나로 합치면 한쪽이 반드시 망가진다.

| | SQS FIFO | Redis Pub/Sub |
|---|---|---|
| 방향 | 서버 → 서버 | 서버 → 브라우저 |
| 하는 일 | **일 시키기** (파티 만들어라, 차단 반영해라) | **소식 알리기** (제안 왔다, 상대가 수락했다) |
| 놓치면 | 데이터가 어긋난다 (파티 미생성, 차단 미반영) | 새로고침하면 복구된다 |
| 필요한 성질 | 내구성 · 재시도 · DLQ · 순서 보장 | 낮은 지연, 가벼움 |

**서로 바꿔 쓰면 안 되는 이유**
- Pub/Sub으로 도메인 이벤트를 보내면: 구독자가 없는 순간 메시지가 **그냥 사라지고** 재시도가 없다. 파티가 안 만들어져도 아무도 모른다.
- SQS로 알림을 보내면: 휘발성 알림에 큐 적체·DLQ·순서 보장이라는 운영 비용을 내고, 이미 화면을 떠난 사용자에게 5분 뒤 알림이 배달된다.

## 8. 예약 매칭을 어떻게 처리할까

**후보** ① 등록 시 즉시 candidate scan ② 주기 배치 ③ 둘 다

**선택: ② (1분 주기 배치 단일 경로)**

**이유**
- 즉시 처리는 **탐욕적(greedy)**이다. 먼저 온 사람이 "그 순간 있던 아무나"와 묶여, 1분만 기다렸으면 더 맞는 사람이 왔을 기회를 날린다.
- 배치는 쌓인 풀 **전체**를 놓고 더 나은 조합을 고른다.
- 예약은 미래 슬롯이라 애초에 즉시성이 요구되지 않는다. 최소 리드타임 **30분** 미만은 `400`으로 거부하고 실시간 매칭이 담당한다.

**기각한 이유**
- ① 위 탐욕 문제. / ③ 같은 매칭 로직에 진입점이 둘이 되어 race 경우의 수와 테스트 조합이 2배가 된다. 예약이 얻는 것(수십 초 단축)이 그 복잡도값을 못 한다.

## 9. 예약 배치를 어디에 둘까

**후보** ① `app:matching` 안에 스케줄러로 ② 별도 + 필요할 때만 기동(RunTask) ③ 별도 + 상시 1개

**선택: ③**

**이유**
- `app:matching`은 큐 depth 따라 **replica가 늘어날 서버**다. 여기에 배치를 넣으면 "늘리면 안 되는 것"과 "늘려야 하는 것"이 한 프로세스에 묶여, **분산 락을 영구히 관리**해야 한다.
- 배치는 스케일 축 자체가 없다. 늘려도 처리량이 아니라 헛일만 는다.
- 단일 인스턴스면 락이 전역 한 줄(`qm:lock:reservation-batch`)로 줄고, 실행이 겹쳐도 atomic claim이 INV-2/INV-7을 지킨다. 겹침은 정합성 사고가 아니라 헛일일 뿐이다.

**기각한 이유**
- ① 위 분산 락. / ② Fargate는 태스크 시작에 30~90초가 걸리고 이미지 pull부터 최소 1분을 과금한다. 1분 주기로 RunTask를 돌리면 **월 과금 1,080시간 > 상시 실행 730시간**이라 상시보다 비싸다.

나눈 것은 **실행 주체**이지 모듈이 아니다. 예약 REST(`/api/v1/reservations` CRUD + INV-9 검증)는 `app:platform`이 서빙한다. `module:reservation`은 라이브러리라 `app:platform`과 `app:reservation-batch` **두 앱에 함께 들어간다.** 역할이 갈릴 뿐이다 — `app:platform` = 예약 **데이터 CRUD**, `app:reservation-batch` = 예약 **짝 찾기**. 그래서 `reservation` 스키마 롤도 두 앱이 함께 쓴다.

배치가 안 도는 것은 조용한 장애이므로 deadman 감시(`reservation_batch_last_success_epoch_seconds`)가 필수다.

## 13. 차단 검사(INV-6)를 어떻게 보증할까

**후보** ① Redis read model만 ② DB만 ③ 2단계(필터는 Redis, 확정 직전은 DB)

**선택: ③**

**이유**
- ①만 쓰면 `social`의 차단 저장과 `matching`의 Redis 반영 사이 **전파 지연 창**이 있고, 그 창에서 claim이 통과하면 방금 차단한 사람과 같은 파티가 된다. 불변식에 확률적 보장은 허용되지 않는다.
- ②만 쓰면 후보 수백 명을 매번 DB로 훑어 hot path가 느려진다.
- 그래서 **필터는 Redis O(1)**(`qm:block:{userId}` Set), **확정 직전에만** `shared_read.blocked_pairs`를 동기 SELECT 한다. 파티 확정은 초당 수 회라 동기 읽기 비용이 무시할 만하다.

**핵심**: 이 SELECT는 proposal 저장과 **같은 트랜잭션** 안에서 일어난다. 검사와 확정 사이에 틈이 없으므로 TOCTOU(검사 후 사용 사이에 값이 바뀌는 문제) 창이 아예 생기지 않는다. REST 재검증으로는 이 성질을 못 얻는다.

**기각한 이유**
- ① 전파 지연 창. / ② hot path 지연.

## 17. 게임 모드 설정을 어디서 읽을까

**후보** ① DB만 매번 조회 ② 앱 메모리 캐시 ③ Redis 캐시

**선택: ③ (DB가 원본, Redis가 캐시)**

**이유**
- ②는 값을 바꾸려면 **전 인스턴스를 재배포**해야 한다. `docs/09` §5가 "대기자가 부족하면 mode를 운영적으로 닫을 수 있어야 한다"고 요구하는데, 재배포가 필요하면 피처 플래그의 의미가 사라진다.
- ③은 DB를 원본으로 두고 Redis를 캐시로 쓴다. 캐시 미스면 DB에서 읽어 채우고, 값 변경 시 키를 지우면 **즉시 반영**된다.
- 매칭 루프가 어차피 Redis를 여러 번 치므로 조회 1회 추가는 무시할 수준이다.
- Redis 장애 시 설정을 못 읽어 매칭이 멈추는데, INV-10이 이미 "Redis 장애 = 새 매칭 중단"이라 일관된다.

**기각한 이유**
- ① 매 사이클 DB 조회라 낭비다. / ② 재배포 없이 못 바꾼다.

**나중에 올릴 수 있는 것**: 앱 메모리 캐시 + Redis Pub/Sub 무효화 신호. 조회 비용이 0이면서 즉시 반영된다. Pub/Sub이 이미 알림 fanout에 쓰이고 있어 도입이 싸다.

## 18. 수락 집계를 어디서 셀까

**후보** ① DB에서 매 수락마다 집계 ② Redis `INCR` 카운터 ③ Redis `SADD` + `SCARD` ④ Redis HASH + Lua 스크립트

**선택: ④**

**이유**
- ①은 수락 5건이면 DB 트랜잭션 5번이다. ④는 전원 수락 시점에 **1번**만 친다.
- ②는 **중복 수락을 못 막는다.** 같은 사용자가 두 번 누르면 카운트가 2 올라, 5명 중 3명만 수락해도 확정될 수 있다 (INV-4 위반).
- ③은 중복은 막지만 **거절을 표현할 수 없다.** 수락 집합만으로는 "아직 안 누름"과 "거절함"이 구분되지 않는다.
- ④는 사용자별 상태(`PENDING`/`ACCEPTED`/`DECLINED`)를 담고, **한 번의 원자 실행으로** 중복 확인 + 제안 생존 확인(INV-5) + 전원 판정 + 상태 전이를 처리한다.
- `docs/03`이 이미 **"`GET → 애플리케이션 판단 → SET`만으로 구현하지 않는다"** 를 요구한다. atomic claim에도 Lua를 쓰므로 방식이 통일된다.
- DB에는 **확정된 제안만** 남아 기록이 깔끔해지고, 만료 제안은 Redis TTL이 정리한다.

**감수하는 것**: Redis 장애 시 진행 중인 수락 상태가 유실된다. 사용자는 타임아웃을 보고 다시 매칭한다. 확정된 것은 DB + outbox에 있어 안전하다.

## 19. 매칭 요청을 어디에 둘까

**후보** ① 전부 DB (`match_requests` 테이블) ② Redis만 두고 **확정된 것만** DB

**선택: ②**

**한 줄 요약: DB는 "성사된 매칭"만 안다.** 시도했다 실패한 요청은 DB를 치지 않는다.

| 무엇 | 어디 |
|---|---|
| 매칭 요청 | Redis만 (`qm:request:{id}` HASH + 큐 ZSET). **`match_requests` 테이블을 만들지 않는다** |
| 진행 중 제안 | Redis (`qm:proposal:{id}` HASH + TTL) |
| 수락 집계 | Redis HASH + Lua (§18) |
| 확정된 것 | DB — `match_proposals` + `proposal_members` + `outbox`, **단일 트랜잭션** |

**이유**
- 대기 중 요청은 큐에서 몇 초~몇 분 살다 사라지는 상태다. 영속 기록으로서의 가치가 낮은데, ①은 요청 접수·큐 이동·거절 후 복귀마다 DB write를 붙인다. 매칭 hot path가 Redis인데 같은 상태를 DB에도 이중으로 유지하면 **두 저장소가 어긋날 지점만 늘어난다.**
- 원자성이 정말 필요한 지점은 **확정 하나뿐**이고, ②에서도 그 하나는 여전히 단일 DB 트랜잭션이다 (`match_proposals` + `proposal_members` + `outbox`). 확정은 사용자에게 "매칭 성공"이라고 알리는 순간이라 어긋나면 티가 나지만, 제안 생성이 어긋나면 재시도하면 그만이다.
- INV-10이 이미 **"Redis 장애 = 새 매칭 fail-closed"** 다. Redis가 죽었을 때 DB로 매칭을 이어갈 계획이 애초에 없다면, DB에 요청을 복제해 둘 이유도 없다.
- §17(설정 = Redis 캐시)·§18(수락 집계 = Redis HASH + Lua)과 같은 방향이다. **진행 중 상태의 source of truth를 Redis 하나로 통일**하면 "어느 쪽이 맞는가"를 물을 일이 없다.

**기각한 이유**
- ① 대기 중 요청까지 DB에 복제해도 INV-10 때문에 그것으로 매칭을 이어갈 수 없다. 이중 기록의 쓰기 비용과 정합성 부담만 남고 얻는 것이 없다.

**감수하는 것**
- **Redis 장애 시 큐를 DB로부터 재구축할 수 없다.** 진행 중이던 요청·제안·수락 상태는 유실되고, 복구 후 **사용자가 다시 요청한다** (`docs/09` §6 Redis outage, `docs/07` §10).
- 매칭 **"시도"** 지표(요청 수, 대기 시간 분포, 실패율)는 **DB 집계가 불가능**하다. Prometheus 메트릭으로만 본다.
- 확정 구간이 두 저장소에 걸친다 (Redis 읽기 → DB 쓰기 → Redis 정리). **DB를 먼저 쓰고 Redis를 정리하는 순서**로 완화한다. 순서가 뒤집히면 확정됐는데 알릴 근거가 없는 상태가 생긴다.
- 요청이 사라지면 **확정된 제안이 어떤 조건으로 만들어졌는지 복원할 수 없다.** `match_proposals.condition_snapshot_json`으로 이 구멍을 막는다 (`docs/06`).
- `proposal_members.acceptance`는 확정된 것만 DB에 남으므로 항상 `ACCEPTED`다. 정보량이 0이라 **컬럼을 제거한다** (`docs/06`).

## 아직 정하지 않은 것 (매칭 관련분만)

원문 "아직 정하지 않은 것" 표에서 매칭 엔진에 걸리는 항목만 옮겼다.

| | 내용 | 재검토 트리거 |
|---|---|---|
| D5 | 배치 주기 1분이 맞는지 | 예약 성사 소요 시간과 배치 1회 실행 시간 실측이 쌓였을 때 |
| D7 | `qm:reservation:slot:*` Redis 슬롯 인덱스 제거 | 배치가 인덱스 걸린 DB 쿼리만으로 목표 시간 안에 도는지 실측했을 때. 돌면 제거 |

- **어뷰징 기록** — 파티 확정 후 즉시 이탈, 반복 거절 등이 기록되지 않는다. 신고 처리의 근거가 되고 매칭 우선순위 조정에 쓸 수 있다.

나머지 미결 항목(D1~D4, D6, `app:admin`, 게임 계정 검증)은 매칭 밖이므로 원문을 봐라.
