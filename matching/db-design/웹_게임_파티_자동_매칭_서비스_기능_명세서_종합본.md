## 0. 기능 분류 기준

본 명세서는 다음 3단계로 기능을 분류한다.

### 대주제

초기 설계가 나눈 5개의 애플리케이션 서비스다. **이 5분할은 현재의 배포 단위가 아니다** — 아래 개정 이력을 보라.
대주제 번호는 소주제 ID 의 뿌리라 그대로 둔다.

1. Core API + SSE 서비스
2. 즉시 매칭 서비스
3. 예약 매칭 RunTask
4. Notification Worker
5. Discord Worker

> 개정 이력: 예전 판은 이 5개를 "아키텍처에 배치된 애플리케이션 서비스"라고 적었다. 2026-09-19 에 고쳤다 —

> `app:reservation-batch` 4개다 (docs/11 #15·#24). 대응은 아래와 같다.
>
> | 옛 대주제 | 현재 |
> |---|---|
> | 1. Core API + SSE | 셋으로 갈렸다. 계정·프로필·게임 계정·파티룸·소셜·예약 REST = `app:platform` / 실시간 매칭 요청·상태 조회·제안 수락·거절 = `app:matching` / SSE 연결 보유 = `app:realtime` |
> | 2. 즉시 매칭 서비스 | `app:matching` |

### 중주제

각 서비스가 담당하는 기능 영역이다.

예를 들어 Core API + SSE 서비스는 다음 기능 영역을 담당한다.

- 사용자 인증 및 계정 관리
- 사용자 프로필 및 Riot 계정 관리
- 매칭 요청 관리
- 파티 제안 및 수락 관리
- 확정 파티 관리
- SSE 실시간 상태 전달

### 소주제

각 중주제 기능을 실제로 구성하는 세부 기능이다.

예를 들어 `매칭 요청 관리`는 다음 세부 기능으로 구성한다.

- 즉시 매칭 요청 생성

- 요청 수정 및 취소
- 시간 중복 요청 차단

# 1. 서비스 범위 및 핵심 정책

## 1.1 서비스 범위

- 서비스는 웹으로만 제공한다.
- 네이티브 모바일 앱은 제공하지 않는다.
- 대상 게임은 리그 오브 레전드, VALORANT, PUBG: BATTLEGROUNDS 셋이다. 넷째 게임을 추가하지 않는다.
- 리그 오브 레전드 한국 서버만 지원한다.
- 시간은 사용자 locale 로 입력받되 서버 저장은 UTC Instant 로 정규화한다.
- 자체 계정으로 회원가입·로그인한다. 인증은 JWT access + refresh token 이다.
- 사용자 id 는 가입할 때 정한 로그인 아이디(문자열)다. uuid 나 별도 일련번호를 사용자 식별자로 두지 않는다.
- 게임 계정을 연결·해제할 수 있다. 외부 API(라이엇 등) 연동 범위는 미정이고, 매칭에 쓰는 티어는 지금 사용자 자기신고다.
- 즉시 매칭과 일회성 예약 매칭을 제공한다.
- 알림은 서비스 화면의 SSE 하나로 제공한다.
- 파티가 최종 확정되면 파티룸에서 자체 WebRTC 음성과 텍스트(DataChannel)를 쓴다. 브라우저 직결이며 서버가 중계·저장하지 않는다.

> 개정 이력: 예전 판은 "대상 게임은 리그 오브 레전드다", "모든 일정과 시간 처리는 한국 표준시를 기준으로 한다",
> "Discord OAuth2 를 서비스 로그인 수단으로 사용한다", "자체 이메일·비밀번호 회원가입은 제공하지 않는다",
> "Riot ID 를 등록해 랭크 정보를 조회한다", "알림은 SSE 와 브라우저 Web Push 로 제공한다",
> "Discord 다이렉트 메시지는 선택 기능", "파티가 최종 확정되면 Discord 전용 비공개 텍스트 채널을 생성한다"고 적었다.
> 2026-09-19 에 위와 같이 바꿨다 — 게임 셋(docs/11 #8, CLAUDE.md §1) / UTC 저장(docs/04 §2) /
> 자체 계정 + JWT(docs/11 #16, docs/00 §5) / 사용자 id = 로그인 아이디(../platform/CLAUDE.md §3.5) /
> 게임 계정 연동 범위 미정(../platform/CLAUDE.md §7, CLAUDE.md §2) / 알림은 SSE 하나(contracts/events.md, docs/11 D-9) /
> WebRTC 음성·텍스트(docs/11 #6·#25, docs/00 §5). "한국 서버만"은 현재 결정에 대응하는 답이 없어 그대로 뒀다.

## 1.2 파티 제안 단계의 대체 충원

파티 정원이 차면 제안(proposal)이 열리고, 전원이 수락해야 확정된다. 거절·무응답·취소가 나오면 **그 제안은 깨지지만
파티는 해체하지 않는다.**

```text
파티 정원이 참 → 제안이 열림 (전원에게 동시에)
→ 일부 수락, 일부 거절·무응답
→ 제안이 깨진다 (수락 기록도 지운다)
→ 거절·무응답자만 큐에서 빠진다. 나머지는 파티에 남아 다시 기다린다
→ 빈자리가 채워져 정원이 다시 차면 새 제안이 열린다
→ 전원이 (다시) 수락
→ 파티 최종 확정
```

- 거절한 본인만 큐에서 빠진다. 수락해 놓고 기다리던 나머지는 파티에 남는다.
- 제안 시한(기본 20초)까지 확정되지 못하면 수락하지 않은 사람만 큐에서 빠진다. 수락한 사람은 파티에 남아 다시 기다린다.
- **옛 수락은 남기지 않는다.** 빈자리가 채워져 제안이 새로 열리면 이미 수락했던 사람도 다시 눌러야 한다.
- 수락한 뒤 같은 제안에 보낸 거절은 받아들이지 않는다(409).
- 제안 도중 한 명이 매칭을 취소해도 그 제안은 깨진다. 남은 사람은 파티에 남는다.
- 확정된 제안은 거절·만료·취소로 뒤집히지 않는다.

> 개정 이력: 예전 판은 "수락한 사용자는 현재 후보에 유지하고 빈 좌석만 대체 후보를 찾아 그 사람에게만 제안한다.
> 이미 수락한 사용자에게 다시 수락을 요구하지 않는다. 전체 충원 제한시간 안에 못 채우면 최종 실패 처리하고
> 기존 수락자는 최초 대기 순서를 유지한 채 재대기한다"고 적었다. 2026-09-19 에 위와 같이 바꿨다 —
> 현재 구현이 그렇게 돌아간다 (CLAUDE.md §4 INV-4·INV-5, contracts/README.md 불일치 표 #6-2).
> 옛 수락을 남기지 않는 이유는 다시 찬 파티가 한 명만 눌러도 확정되는 것을 막기 위해서다(INV-4).
> "전체 충원 제한시간"과 "최초 대기 순서 유지"는 현재 설계에 대응하는 개념이 없다.

## 1.3 최종 확정 이후 정책

파티가 최종 확정된 이후의 정책이다.

- 파티룸에는 나가기가 있다. 파티가 닫히면 `app:platform` 이 `PartyClosed` 를 발행한다. 언제 파티가 닫히는지는 정해지지 않았다.
- 파티 확정 취소 기능을 제공하지 않는다.
- 파티 구성원 추가·제거·교체 기능을 제공하지 않는다.
- 최종 확정 후 빈자리 모집 기능을 제공하지 않는다.
- 실제 게임에 접속하지 않는 사용자에 대한 자동 대체 기능을 제공하지 않는다.
- 실제 플레이 종료 여부를 확인하거나 파티를 완료 상태로 변경하지 않는다.

> 개정 이력: 예전 판은 "파티가 최종 확정된 이후에는 구성원을 변경하지 않는다 / 파티 나가기 기능을 제공하지 않는다"고
> 적었다. 2026-09-19 에 첫 줄을 바꿨다 — 파티룸의 필수 기능에 "나가기"가 있고(docs/00 §5), 닫힌 파티는
> `PartyClosed.fifo` 로 알린다(docs/11 #21, ../platform/CLAUDE.md §3.4). 나머지 줄(확정 취소·구성원 추가/교체·
> 빈자리 모집·자동 대체·완료 상태)은 현재 결정에 대응하는 답이 없어 그대로 뒀다 — 나가기와 어떻게 양립하는지 미정이다.

## 1.4 예약 요청 묶음 정책

**이 절은 폐기됐다.** 지금 예약은 "기존 매칭 조건 + 플레이 가능한 시간(`availableFrom`~`availableTo`, 30분 단위) +
플레이할 양(`ONE_GAME` / `TWO_PLUS`)"이고, 여러 후보 일정을 묶어 내는 개념이 없다 (docs/04 §1·§2, docs/11 #11).
시간이 겹치는 활성 예약은 등록·수정을 거절한다 — 묶음 안이라고 허용하지 않는다 (INV-9, docs/04 §9).
당일 00시 배치가 아니라 1분 주기 배치이고(docs/11 #23), 자동 확정이 아니라 실시간과 같은 제안·수락을 거친다 (docs/04 §8).

# 대주제 1. Core API + SSE 서비스

## 서비스 책임

웹 클라이언트의 요청을 받아 사용자 계정, 프로필, 게임 계정, 매칭 요청, 파티 제안, 수락 상태와 확정 파티를 다루는 기능 묶음이다.

> 개정 이력: 예전 판은 이 전부를 "Core API" 한 서비스의 책임으로 적고, "즉시 매칭 서비스가 만든 후보 파티를
> Core API 가 사용자에게 제안하고, 거절·무응답이 발생하면 대체 충원을 요청한다"고 적었다. 2026-09-19 에 고쳤다 —
> 지금은 배포 단위가 갈려 있다 (docs/11 #15, ../platform/CLAUDE.md §2, ../notification/CLAUDE.md §2).
> 중주제 1.1~1.3 · 1.7 과 예약 REST = `app:platform` / 중주제 1.4~1.6 의 실시간 매칭 요청·상태·제안 수락·거절 =
> `app:matching`(제안을 열고 수락을 집계하고 확정하는 것까지 전부) / 중주제 1.8 = `app:realtime` / 중주제 1.9 = 폐기.

## 중주제 1.1 사용자 인증 및 계정 관리

## 중주제 1.4 매칭 요청 관리

이 기능은 사용자 한 명이 보낸 요청 자체가 서비스 정책과 게임 규칙에 맞는지를 확인한다.

다른 사용자와의 호환 여부는 즉시 매칭 서비스 또는 예약 매칭 RunTask에서 판단한다.

| 소주제 ID | 소주제 | 설명 |
|---|---|---|
| 1.4.1 | 매칭 방식 선택 | 즉시 매칭 또는 일회성 예약 매칭을 선택한다. |
| 1.4.2 | 즉시 매칭 요청 생성 | 게임과 그 게임의 조건 4개(게임 모드·핵심 조건·음성 사용·플레이 목적)로 즉시 요청을 생성한다. 티어를 보는 모드는 티어를 함께 받는다(조건이 아니라 자격이다). 요청은 DB 가 아니라 Redis 에만 둔다. |
| 1.4.3 | 예약 매칭 요청 생성 | 기존 매칭 조건에 플레이 가능한 시간(`availableFrom`~`availableTo`, 30분 단위)과 플레이할 양(`ONE_GAME` / `TWO_PLUS`)만 더해 예약을 생성한다. |
| 1.4.4 | 필수 입력값 검증 | 게임·게임 모드·핵심 조건·음성·플레이 목적의 누락을 검사한다. 티어를 보는 모드에서는 티어도 필수다. |
| 1.4.5 | 입력값 형식 검증 | 잘못된 enum·날짜·시간·플레이시간 값을 거절한다. |
| 1.4.6 | 게임 모드 선택 검증 | 그 게임의 gameconfig 에 있는 게임 모드(modeKey) 하나만 선택하도록 한다. |
| 1.4.7 | 모드별 목표 인원 | 목표 인원은 사용자가 고르지 않는다. 모드가 정해지면 인원도 정해진다 — 인원이 가변인 모드는 modeKey 를 인원별로 쪼갠다. |
| 1.4.8 | 불가능한 인원 차단 | 게임 규칙상 불가능한 인원(예: 자유 랭크 4인)은 그 modeKey 를 아예 만들지 않는 것으로 배제한다. |
| 1.4.9 | 개인 신청 방식 제한 | 친구와 함께 신청하는 기존 파티 단위 요청은 지원하지 않는다. |
| 1.4.10 | 티어 자격 검증 | 사용자는 허용 티어 범위를 고르지 않는다. 같이 갈 수 있는 티어 범위는 gameconfig 의 tier-range 표가 정한다. |
| 1.4.11 | 랭크 모드 이용 자격 검증 | tier-range 표에 줄이 없는 티어와 `SOLO_ONLY` 티어의 요청을 거절한다(400). |
| 1.4.12 | 대체 큐 안내 | 제한된 사용자에게 자유 랭크와 일반 큐를 안내한다. |
| 1.4.13 | 예약 최소 리드타임 검증 | 첫 슬롯 시작(`availableFrom`)까지 30분 미만이면 등록을 거절한다(400). 그 이하 리드타임은 실시간 매칭이 맡는다. 수정에도 같은 규칙을 적용한다. |
| 1.4.14 | (폐기) 예약 마감 검증 | 폐기됐다 — 전날 23시 50분 마감이 없다. 최소 리드타임 30분(1.4.13)이 그 자리를 대신한다. |
| 1.4.15 | 플레이 가능 시간 검증 | 플레이 가능 시간의 시작·끝은 30분 단위만 허용한다. |
| 1.4.16 | 플레이할 양 검증 | 예약의 플레이할 양은 `ONE_GAME`, `TWO_PLUS` 중 하나만 허용한다. |
| 1.4.17 | 시간 중복 예약 차단 | 한 사용자의 활성 예약(`ACTIVE`/`PROPOSED`/`MATCHED`)끼리 시간이 겹치면 생성·수정을 거절한다(INV-9). 실시간 요청은 한 사용자가 1개만 가진다(INV-1). |
| 1.4.18 | 요청 값 정규화 | 시간을 UTC Instant 로 정규화한다. |
| 1.4.19 | 티어 스냅샷 저장 | 요청 생성 시점의 티어 정보를 요청 데이터에 저장한다. |
| 1.4.20 | 신청 전 조건 요약 | 큐·일정·인원·티어·포지션·음성·목적을 신청 전에 요약한다. |
| 1.4.21 | 현재 대기 인원 조회 | 즉시 매칭 조건 화면에 현재 대기 인원을 표시한다. |
| 1.4.22 | 즉시 요청 수정 | 대기 중인 즉시 요청만 수정할 수 있게 한다. |
| 1.4.23 | 즉시 요청 취소 | 대기 중에도, 제안이 열린 뒤에도 취소할 수 있다. 제안 도중 취소하면 그 제안은 깨지고 남은 사람은 파티에 남는다. |
| 1.4.24 | 예약 요청 수정 | `ACTIVE` 예약만 수정할 수 있다. `PROPOSED` 는 수정 금지, `MATCHED` 는 조건 수정 금지다. |
| 1.4.25 | 예약 요청 취소 | `ACTIVE` 예약은 취소할 수 있다. `MATCHED` 는 취소만 가능하며 다른 참가자에게 이벤트를 전달한다. |
| 1.4.26 | (폐기) 예약 자동 확정 안내 | 폐기됐다 — 예약도 실시간과 같은 제안·수락을 거친다. 00시 배치가 아니라 1분 주기 배치다. |
| 1.4.27 | (폐기) 예약 요청 묶음 제출 | 폐기됐다 — 예약 묶음이 없다(§1.4). |
| 1.4.28 | (폐기) 묶음 내 시간 중복 허용 | 폐기됐다 — 시간이 겹치는 활성 예약은 예외 없이 거절한다(INV-9). |
| 1.4.29 | (폐기) 묶음 외 시간 중복 차단 | 폐기됐다 — 1.4.17 로 합쳐졌다. |
| 1.4.30 | (폐기) 묶음 우선순위 지정 | 폐기됐다 — 예약 묶음이 없다(§1.4). |
| 1.4.31 | (폐기) 묶음 단위 수정·취소 | 폐기됐다 — 예약 묶음이 없다(§1.4). |

> "날짜 + 시작 시각 + 시작 가능 범위(정확/±30분/±1시간) + 예상 플레이시간"으로 받아 전날 23시 50분에 마감하며,
> 즉시 요청은 제안 생성 전에만 취소할 수 있다고 적었다. 2026-09-19 에 위와 같이 바꿨다 —
> 조건은 게임당 정확히 4개이고 티어는 조건이 아니라 자격이다(CLAUDE.md §2) / 인원은 modeKey 에 들어 있다(docs/11 #31) /
> 티어 범위는 gameconfig 표가 정한다(CLAUDE.md §4 INV-8, docs/GAME_CONFIG.md) / 실시간 요청은 Redis 에만 둔다(docs/11 #27) /
> 제안 도중 취소가 된다(CLAUDE.md §4 INV-5 cancelled) / 예약 필드·리드타임·수정 정책(docs/04 §2·§6-1·§9·§10, docs/11 #23).
> 1.4.18 의 "상관없음 포지션을 실제 포지션 목록으로 변환한다"는 뺐다 — 요청은 핵심 조건 값을 하나만 싣는다
> (LoL 의 `NONE` 은 "상관없음"이 아니라 포지션 개념이 없는 모드용 값이다).
> 실시간 매칭 요청(1.4.2, 1.4.4~1.4.11, 1.4.23)은 지금 `app:matching` 이 직접 받고, 예약 REST 는 `app:platform` 이 받는다.
> 1.4.9 · 1.4.12 · 1.4.19~1.4.22 는 현재 결정에 대응하는 답이 없어 그대로 뒀다.

## 중주제 1.5 매칭 요청 상태 및 동시 요청 관리

| 소주제 ID | 소주제 | 설명 |
|---|---|---|
| 1.5.1 | 진행 중 요청 조회 | 사용자의 현재 즉시·예약 요청을 조회한다. |
| 1.5.2 | 예약 상태 관리 | 예약은 `ACTIVE` / `PROPOSED` / `MATCHED` / `CANCELLED` / `EXPIRED` / `COMPLETED` 로 관리한다. 예약의 원본은 PostgreSQL 이다. |
| 1.5.3 | 대기 상태 관리 | 즉시 매칭 대기 요청을 `QUEUED` 로 관리한다. 상태는 DB 가 아니라 Redis 에 있다. |
| 1.5.4 | 제안 상태 관리 | 제안이 열린 요청을 `PROPOSED` 로 관리한다. |
| 1.5.5 | (폐기) 대체 충원 상태 관리 | 폐기됐다 — `REFILLING` 상태가 없다. 제안이 깨지면 남은 사람은 파티에 남은 채 `QUEUED` 로 돌아간다(§1.2). |
| 1.5.6 | 확정 상태 관리 | 전원 수락으로 확정된 요청을 `MATCHED` 로 관리한다. |
| 1.5.7 | 취소 상태 관리 | 취소하면 활성 요청을 지운다. 그래서 상태 조회는 `CANCELLED` 가 아니라 `IDLE`(활성 요청 없음)을 돌려준다. |
| 1.5.8 | 만료 상태 관리 | 제안 시한을 넘긴 무응답자의 활성 요청도 지우므로 조회는 `IDLE` 을 돌려준다. `FAILED` 상태는 없다. |
| 1.5.9 | 취소·제안 경합 처리 | 확인과 쓰기를 Redis Lua 한 번의 원자 실행으로 묶는다. `GET → 애플리케이션 판단 → SET` 으로 만들지 않는다. |
| 1.5.10 | 최신 상태 반환 | 이전 상태를 기준으로 요청한 경우 현재 최신 상태를 반환한다. |
| 1.5.11 | 중복 API 요청 방지 | 생성·수정·취소 요청이 반복돼도 한 번만 반영한다. |
| 1.5.12 | 확정 뒤 활성 요청 유지 | 확정된 사용자의 활성 요청은 지우지 않고 `status=PARTY` 로 남겨, 그 사용자가 새 매칭을 걸 수 없게 한다. 이 상태를 누가 언제 푸는지는 미정이다. |
| 1.5.13 | (폐기) 묶음 단일 성립 보장 | 폐기됐다 — 예약 묶음이 없다(§1.4). |
| 1.5.14 | (폐기) 묶음 잔여 요청 종결 | 폐기됐다 — 예약 묶음이 없다(§1.4). |

> 개정 이력: 예전 판은 즉시·예약 요청을 한 상태 집합(`RESERVED`/`QUEUED`/`PROPOSED`/`REFILLING`/`CONFIRMED`/`CANCELED`/`FAILED`)으로
> DB 에서 관리한다고 적었다. 2026-09-19 에 위와 같이 바꿨다 — 실시간 상태는 Redis 에만 있고(docs/11 #27) 값은
> `IDLE`/`QUEUED`/`PROPOSED`/`MATCHED`(+ 자리만 있는 `CANCELLED`/`EXPIRED`)다(docs/03 §2, contracts/README.md 불일치 표 #4-1,

## 중주제 1.9 비동기 작업 발행

**이 중주제는 폐기됐다.** Web Push 구독, 알림 작업 큐, Discord 명령이 없다. 사용자 알림은 각 앱이 Redis Pub/Sub
`qm:pubsub:push:{userId}` 에 publish 하고 `app:realtime` 이 SSE 로 배달한다 — 봉투는 `{type, eventId, occurredAt, payload}`
이고 `eventId`(매번 새 UUID)가 클라이언트의 중복 제거에 쓰인다(contracts/events.md). 앱 사이의 작업 지시는
transactional outbox + SQS FIFO 다 — `ProposalConfirmed.fifo`, `PartyClosed.fifo` (docs/11 #21, ../platform/CLAUDE.md §3.4).
Web Push 는 "나중에 보완으로" 미뤄져 있을 뿐 정해진 설계가 없다(docs/WHY_SPRING_BOOT.md §5-3).
예약 리마인더(옛 1.9.7)는 현재 결정에 대응하는 것이 없다.

# 대주제 2. 즉시 매칭 서비스

## 서비스 책임

실시간 매칭 요청을 받아 조건이 같은 사용자를 한 파티로 모으고, 정원이 차면 제안을 열어 전원 수락으로 확정한다.
지금의 `app:matching` 이다.

> 개정 이력: 예전 판은 "대기열에서 호환되는 요청을 골라 파티 후보를 구성하고, 거절·무응답자가 발생하면 기존 수락자를
> 유지한 상태에서 빈 좌석에 들어갈 대체 후보를 탐색한다"고 적었다. 2026-09-19 에 고쳤다 — 대기열과 후보 탐색이
> 없어졌다. 대기 상태는 "큐에 줄 선 사람"이 아니라 **"아직 안 찬 파티"**이고(docs/11 #32), 파티를 "아직 필요한 핵심 조건
> 값"으로 역색인해 탐색 자체를 없앴다(#33). 진행 중 상태는 전부 Redis 에만 있다(#27). 요청 접수·제안·수락 집계·확정·
> 알림 발행까지 이 앱이 한다(CLAUDE.md §3·§4). 세 게임(LoL · VALORANT · PUBG) 모두 구현돼 있다.

## 중주제 2.3 음성채팅 호환 규칙 관리

**이 중주제는 폐기됐다.** "가능"(`OPTIONAL`) 값이 제거돼 호환 규칙이 필요 없다. 음성 값은 `REQUIRED` / `NO_VOICE` 둘뿐이고
값이 같은 사람끼리만 모인다 — "매칭 전에 답이 정해지지 않는 조건은 조건이 아니다"
(CLAUDE.md §2, `domain/condition/VoicePreference.java` 클래스 주석). 이 제거는 되돌리지 않는다.

## 중주제 2.4 결정적 파티 후보 구성

**이 중주제는 폐기됐다.** 요청을 신청 순서로 정렬해 기준 요청을 고르고 후보를 순차 탐색하는 방식이 없어졌다. 지금은
대기 중인 혼자도 1인 파티이고, 새로 온 사람은 "내 핵심 조건 값이 아직 비어 있는 파티"의 색인에서 맨 앞 하나에 **한 번에
한 명씩** 들어간다 — 후보 N-1명을 모아 한 번에 선점하고 실패하면 전체를 되돌리는 경로가 없다(docs/11 #32·#33).
제품 정의는 "호환되는 후보군 안에서 자동 랜덤 배정"이다(docs/00 §2). 다음 둘은 지금도 같다 — 정원이 차기 전에는 제안을
열지 않는다(옛 2.4.5, INV-4) / 유사도·신뢰도 점수를 쓰지 않는다(옛 2.4.8 — QueueMate 는 추천 목록을 주는 서비스가 아니다,
docs/03 §1). "동일 입력 동일 결과"(옛 2.4.10)는 현재 결정에 대응하는 요구가 없다.

## 중주제 2.5 포지션 배정

**이 중주제는 폐기됐다.** 시스템이 포지션을 배정하지 않는다. 사용자가 요청에 핵심 조건 값 **하나**(LoL 희망 포지션 /
VALORANT 선호 역할군 / PUBG 플랫폼)를 싣고, 그 값이 비어 있는 파티에만 들어간다. 주·부 포지션 개념이 없다(CLAUDE.md §2).
중복 금지(옛 2.5.2)는 모드의 `positionUniqueness` 설정을 따르고 Lua 가 처리한다 — 칼바람처럼 포지션 개념이 없는 모드는
중복을 허용한다(docs/GAME_CONFIG.md, CLAUDE.md §4 INV-8). 참가자는 파티 HASH 에 `member:{userId} = keyValue` 로
기록된다(docs/11 #35).

## 중주제 2.6 파티 후보 원자적 선점

| 소주제 ID | 소주제 | 설명 |
|---|---|---|
| 2.6.1 | 사용자 단일 파티 | 한 사용자는 동시에 한 파티에만 속한다. proposal 이 곧 party 이므로 이것이 "하나의 활성 제안에만 속한다"(INV-2)를 지킨다. |
| 2.6.2 | 사용자 중복 배정 방지 | 같은 사용자가 한 파티에 두 번 들어갈 수 없다 — 참가자가 HASH 필드라 구조적으로 불가능하다(INV-7). |
| 2.6.3 | Redis Lua 원자 처리 | 후보 확인과 선점을 하나의 원자적 작업으로 처리한다. |
| 2.6.4 | 다중 인스턴스 경합 제어 | "파티 찾기"와 "합류" 두 스크립트 사이의 틈은 후보 풀 락(Redisson `RLock`)이 막는다. 그 사이에 차단 검증(자바)이 끼기 때문에 둘로 나뉘어 있다. |
| 2.6.5 | 취소와 선점 경합 처리 | 취소와 선점 중 먼저 상태 변경에 성공한 처리를 적용한다. |
| 2.6.6 | 목표 정원 초과 방지 | 후보 파티가 목표 인원을 초과하지 않게 한다. |
| 2.6.7 | 실패 시 선점 해제 | 선점만 하고 배정 전에 죽으면 60초 뒤 선점이 저절로 풀린다(claim TTL). 배정에 성공하면 그 만료를 뗀다. |

> 개정 이력: 예전 판은 "후보 N명을 한 번에 선점하고 제안 저장에 실패하면 선점을 되돌린다"는 모델이었다.
> 2026-09-19 에 2.6.1 · 2.6.2 · 2.6.4 · 2.6.7 을 바꿨다 (CLAUDE.md §4 INV-1·INV-2·INV-3·INV-7 과 "Lua 스크립트 목록" 절).
> Lua 원자 처리(2.6.3)라는 원칙은 그대로다 — `GET → 애플리케이션 판단 → SET` 으로 불변식을 지키지 않는다.
> 2.6.3 · 2.6.5 · 2.6.6 은 그대로 뒀다.

## 중주제 2.7 최초 파티 제안 생성

## 중주제 2.8 제안 단계 대체 후보 충원

**이 중주제는 폐기됐다.** 빈 좌석만 골라 대체 후보를 찾아 그 사람에게만 제안하는 절차가 없다. 제안이 깨지면 파티가
needs 색인에 되돌아오고, 새로 온 사람이 일반 배정 경로로 합류해 정원이 다시 차면 새 제안이 **전원에게** 열린다
(§1.2, CLAUDE.md §4 INV-5). 예전 판의 "공개 게시판 형태의 빈자리 모집은 제공하지 않는다"는 **자동 매칭의 제안 단계에 한해서는**
지금도 같다 — 제안이 깨진 자리를 게시판으로 채우지 않는다. 다만 게시판 자체는 이제 금지가 아니다. 파티 모집 게시판이
자동 매칭과 **별개의 두 번째 경로**로 들어왔고 `app:platform` 의 일이다(docs/11 D-11).

# 대주제 3. 예약 매칭 RunTask

## 서비스 책임

예약 매칭의 짝 찾기를 맡는다 — 지금의 `app:reservation-batch` 다. **1분 주기 배치 단일 경로**로만 실행하며 상시 1개만
띄우고 스케일아웃하지 않는다. 예약 데이터의 등록·조회·수정·취소는 `app:platform` 의 REST 가 맡고, 등록 직후에는
짝을 찾지 않는다. 예약도 실시간과 같은 제안·수락을 거친다.

> 개정 이력: 예전 판은 "매일 한국 표준시 00시에 실행되어 당일 예약 요청을 조회하고, 별도의 제안·수락 절차 없이 자동
> 확정한다"고 적었다. 2026-09-19 에 고쳤다 (docs/11 #23·#24, docs/04 §6·§6-2·§8). 이 앱은 아직 어느 폴더에도 없다.

---

## 중주제 3.1 예약 배치 실행 및 대상 선정

**이 중주제는 폐기됐다.** 하루 한 번 00시에 당일 예약을 모아 처리하는 배치가 아니다. 상시 떠 있는 인스턴스 1개가 내부
1분 주기로 돈다(`queuemate.reservation.batch.interval-ms: 60000`). 진입점은 `runOnce()` 코어 + `BATCH_MODE=daemon|oneshot`
이다 (docs/11 #23·#24, docs/04 §6-2). EventBridge → RunTask 방식은 기각됐다 — 시작에 30~90초가 걸려 상시 실행보다
비싸다(docs/11 #26). 옛 3.1.7 의 "같은 날짜 중복 실행 검증" 자리는 전역 락 `qm:lock:reservation-batch` 한 줄이 대신한다 —
단일 인스턴스라 실행이 겹쳐도 atomic claim 이 정합성을 지키고, 겹침은 헛일일 뿐이다(docs/11 #24).
배치가 어떤 예약을 대상으로 집는지의 세부(옛 3.1.2~3.1.6)는 문서에 없다.

## 중주제 3.3 예약 파티 자동 확정

**이 중주제는 폐기됐다.** 예약은 자동 확정하지 않는다. 실시간과 같은 제안·수락 모델을 쓴다 — 전원 수락이면 `MATCHED`,
거절·만료면 그 예약을 `ACTIVE` 로 되돌리거나 취소 정책에 따라 종료한다(docs/04 §8). 시작 시각은 호환되는 모든 사용자의
플레이 가능 시간 교집합에서 가장 이른 30분 slot 을 후보로 정한다(docs/04 §5). `RESERVATION_*` 알림의 발행 주체는
`app:reservation-batch` 다(docs/11 #24). Discord 전용방 생성 명령(옛 3.3.9)은 폐기됐다.
예상 플레이시간으로 종료 예정 시각을 계산한다는 서술(옛 3.3.5)은 대응하는 것이 없다 — 예약은 예상 플레이시간이 아니라
플레이할 양(`ONE_GAME` / `TWO_PLUS`)을 받는다.

## 중주제 3.4 예약 미성립 처리

**이 중주제는 폐기됐다.** 배치가 1분마다 돌므로 "하루 한 번 돌고, 미성립이면 `FAILED` 로 바꾸고, 당일에는 다시 돌리지
않는다"가 성립하지 않는다(docs/11 #23). 예약 상태에는 `FAILED` 가 없고 `EXPIRED` 가 있다(docs/04 §3). 남은 시간이 줄수록
tier 를 넓혀 성사를 우선한다(docs/04 §6-1). 언제 `EXPIRED` 가 되는지, 그때 알림을 보내는지는 문서에 없다.

## 중주제 3.5 배치 멱등성 및 중복 배정 방지

| 소주제 ID | 소주제 | 설명 |
|---|---|---|
| 3.5.1 | 동일 입력 동일 결과 | 같은 요청 집합에서 같은 파티 구성이 나오도록 한다. |
| 3.5.2 | 배치 재실행 중복 방지 | RunTask 재실행 시 같은 파티를 중복 생성하지 않는다. |
| 3.5.3 | 실행 겹침 제어 | 인스턴스는 상시 1개이고 스케일아웃하지 않는다. 전역 락 `qm:lock:reservation-batch` 한 줄을 두며, 실행이 겹쳐도 atomic claim 이 중복 배정을 막는다. |
| 3.5.4 | 요청 단일 파티 보장 | 하나의 예약 요청은 하나의 파티에만 포함되게 한다. |

| 3.5.7 | (폐기) 묶음 단일 파티 보장 | 폐기됐다 — 예약 묶음이 없다(§1.4). |

> 3.5.6 을 바꿨다 (docs/11 #24, docs/04 §6-2). 실행 결과를 DB 에도 남기는지는 문서에 없다.
> 3.5.1 · 3.5.2 · 3.5.4 는 그대로 뒀다 — 3.5.1(결정론)은 현재 결정에 대응하는 요구가 없다.

# 대주제 4. Notification Worker

## 서비스 책임

**이 대주제는 폐기됐다.** SQS 알림 큐를 소비해 Web Push 를 보내는 워커가 없다. 알림은 SSE 하나다 — 각 앱이 Redis Pub/Sub
`qm:pubsub:push:{userId}` 에 publish 하고, `app:realtime`(=`notification`)이 그 메시지를 **해석하지 않고 그대로** 사용자의
SSE 연결로 흘려보낸다. 알림 이력을 저장하지 않고 놓친 알림을 재전송하지 않는다 — 재접속한 사용자는 상태 조회로 복구한다
(contracts/events.md, ../notification/CLAUDE.md §2, docs/11 #22·D-9·D-10). 알림은 휘발성이라 SQS 로 옮기지 않는다(docs/11 #22).

Web Push 는 "나중에 보완으로" 미뤄져 있을 뿐 정해진 설계가 없다(docs/WHY_SPRING_BOOT.md §5-3). "알림 실패로 제안이나 확정을
취소하지 않는다"(옛 4.2.7)는 원칙은 지금도 같다 — 발행은 어떤 예외도 밖으로 내보내지 않는다(CLAUDE.md §3).
예약 리마인더(옛 4.3.10~4.3.13)는 현재 결정에 대응하는 것이 없다. 중주제 4.1~4.4 의 옛 본문은 git 이력에 있다.

# 대주제 5. Discord Worker

## 서비스 책임

**이 대주제는 폐기됐다.** Discord 연동(로그인, 파티 전용 채널, DM)이 전부 없다. 확정된 파티의 소통은 파티룸의 자체
WebRTC 음성 + 텍스트 DataChannel 이다. 브라우저 직결이라 서버가 중계하지도 저장하지도 않는다(docs/11 #6·#25, docs/00 §5).
시그널링은 보내기 = `app:platform` 의 REST `POST`(같은 파티원인지 확인한 뒤 상대 채널에 발행), 받기 = SSE 의
`WEBRTC_SIGNAL` 이고 WebSocket 은 어느 앱에도 없다(docs/11 D-9, contracts/events.md). TURN 은 Cloudflare 관리형으로 정해져
있으나(docs/11 #25) 나중 일이고, 지금은 공개 STUN 으로 개발한다(../platform/CLAUDE.md §2). 시그널 `POST` 의 경로와
`WEBRTC_SIGNAL` 의 payload 는 미정이다. "대화 내용을 서비스 데이터베이스에 저장하지 않는다"(옛 5.5.6)는 지금도 같다.
중주제 5.1~5.6 의 옛 본문은 git 이력에 있다.

# 6. 핵심 상태 구조

## 6.1 즉시 매칭 요청 상태

```text
QUEUED
  → PROPOSED
  → MATCHED
```

그 밖의 전이:

```text
QUEUED → CANCELLED
PROPOSED → QUEUED       (거절·만료·취소로 제안이 깨지고 요청은 남을 때)
PROPOSED → CANCELLED
```

- 상태는 DB 가 아니라 Redis 에 있다. 상태 조회는 여기에 `IDLE`(활성 요청 없음)을 더해 돌려준다.
- 취소·만료되면 활성 요청 자체를 지우므로 조회는 `CANCELLED` / `EXPIRED` 가 아니라 `IDLE` 을 돌려준다.
- `MATCHED` 가 된 사용자의 활성 요청은 `status=PARTY` 로 남는다. 이것을 누가 언제 푸는지는 미정이다.

> 개정 이력: 예전 판은 `CREATED → QUEUED → PROPOSED → REFILLING → CONFIRMED` 와 `FAILED` 분기를 적고 "`CONFIRMED` 이후에는
> 사용자에 의한 상태 변경을 제공하지 않는다"고 적었다. 2026-09-19 에 바꿨다 (docs/03 §2, contracts/README.md 불일치 표 #4-1,
> `domain/MatchRequestStatus.java`, CLAUDE.md §4 INV-2, ../platform/CLAUDE.md §7).

## 6.2 제안 상태

```text
(제안 없음) → PENDING → CONFIRMED
              PENDING → (제안 없음)     거절·만료·취소
```

- 제안 상태는 별도 레코드가 아니라 파티 HASH 의 `status` / `expiresAt` 이다(proposal 이 곧 party 다).
- 거절·만료·취소로 제안이 깨지면 `DECLINED` 같은 값을 남기지 않고 `status` 를 **지운다.** 남기면 그 파티가 다시 찼을 때
  새 제안을 열 수 없는 좀비 파티가 된다.
- 참가자별로는 "수락했다 / 아직 아니다"만 있다. 거절·무응답자는 파티에서 빠지므로 상태로 남지 않는다.
- `CONFIRMED` 는 되돌릴 수 없다.

> 개정 이력: 예전 판은 참가자 상태를 `PENDING` / `ACCEPTED_LOCKED` / `DECLINED` / `TIMED_OUT` 으로 적고 "수락자는 확정되거나
> 최종 실패할 때까지 현재 후보에 유지된다"고 적었다. 2026-09-19 에 바꿨다 (CLAUDE.md §4 INV-4·INV-5). 참고 — docs/11 #28 과
> docs/03 §3 은 참가자별 HASH(`PENDING|ACCEPTED|DECLINED`)를 적고 있으나 현재 구현은 수락자 SET 이다. 여기서는 구현을
> 적은 CLAUDE.md §4 를 따랐다.

## 6.3 제안 좌석 상태

**이 절은 폐기됐다.** 좌석 개념이 없다. 빈자리는 "그 파티가 아직 필요로 하는 핵심 조건 값"의 색인으로 표현된다
(docs/11 #33, 중주제 2.5·2.8).

## 6.4 예약 요청 상태

```text
ACTIVE
PROPOSED
MATCHED
CANCELLED
EXPIRED
COMPLETED
```

- 전원 수락이면 `MATCHED`, 거절·만료면 `ACTIVE` 로 되돌리거나 취소 정책에 따라 종료한다.
- `ACTIVE` 는 수정·취소 가능, `PROPOSED` 는 수정 금지, `MATCHED` 는 조건 수정 금지이고 취소만 가능하다.

> 개정 이력: 예전 판은 `RESERVED → MATCHING → CONFIRMED / FAILED` 와 예약 마감 전 `RESERVED → CANCELED`, 그리고 묶음 종결
> 규칙을 적었다. 2026-09-19 에 바꿨다 (docs/04 §3·§8·§10). 예약 묶음은 폐기됐다(§1.4).

# 7. 서비스별 책임 요약

| 배포 단위 | 핵심 책임 |
|---|---|
| `app:platform` | 계정(가입·로그인·JWT)·프로필·게임 계정 / 파티(`ProposalConfirmed` 를 소비해 DB 에 파티 생성, 파티룸) / 소셜(친구·차단·신고·최근 함께한 사람) / 예약 REST / WebRTC 시그널 `POST` 받기 / 파티 모집 게시판(모집 글이 곧 파티방이다 — docs/11 D-11). stateless REST |
| `app:matching` | 실시간 매칭 요청 접수·파티 배정·제안·수락 집계·확정, gameconfig, `MATCH_*` 알림 발행. 진행 중 상태는 Redis 에만 |
| `app:realtime` (폴더 이름 `notification`) | SSE 연결 보유. Redis Pub/Sub 으로 들어온 알림을 해석하지 않고 그대로 배달 |
| `app:reservation-batch` | 예약 매칭 짝 찾기. 상시 1개, 1분 주기 |

> 개정 이력: 예전 판은 Core API + SSE / 즉시 매칭 서비스 / 예약 매칭 RunTask / Notification Worker / Discord Worker 의
> 5분할을 적었다. 2026-09-19 에 현재 배포 단위로 바꿨다 (docs/11 #15·#24, ../platform/CLAUDE.md §2,
> ../notification/CLAUDE.md §2, CLAUDE.md §3). 옛 대주제와의 대응은 §0 에 있다.

# 8. 최종 포함 및 제외 기준

## 포함
