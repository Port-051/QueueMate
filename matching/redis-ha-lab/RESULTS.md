# 실험 결과 — Redis Sentinel HA (2026-09-09)

`app:matching` 은 진행 중인 매칭 상태를 Redis 하나에만 둔다 (`CLAUDE.md` §3).
**그 Redis 한 대가 죽으면 매칭 전체가 멈춘다.** 이 폴더는 "Sentinel 을 붙이면
그게 몇 초가 되는가" 를 노트북에서 실제로 재 본 기록이다.

절차와 해석은 `EXPERIMENTS.md`, 이 문서는 **결과만** 담는다.
숫자는 전부 실행 결과에서 읽은 값이고, 재지 않은 것은 "미측정 / 미실행" 으로 적었다.

**측정 환경**

| | |
|---|---|
| Redis | `redis:7-alpine` — master 1 + replica 2 + Sentinel 3 |
| Sentinel | `quorum=2`, `down-after=5000`, `failover-timeout=60000` |
| 앱 | Spring Boot 4.1.1, Redisson 3.52.0, Lettuce |
| 장애 주입 | `docker kill`(SIGKILL). `t0` = kill 시각 |
| 호스트 | WSL2(Ubuntu 22.04) on Windows 11 |

## 1. 실험별 한 줄 결론

| 실험 | 상태 | 한 줄 결론 | 핵심 수치 |
|---|---|---|---|
| **1. 베이스라인** | 실행 완료 | Sentinel 은 6.43초 만에 새 master 를 세운다. **그중 79% 가 감지 시간이다** | 쓰기 불가 **6.43초** / `+switch-master` t0+6,270ms |
| **2. 클라이언트 토폴로지** | 실행 완료 | 클라이언트는 다운타임을 늘리는 변수가 아니라 **유한과 무한을 가르는 스위치**다 | 판 C **6.04초** / 판 A **복구 없음** / 판 B **조용한 유실 202건** |
| **3. 감지 시간 튜닝** | 실행 완료 | 3.42초로 줄일 수 있다. **줄이지 않기로 했다** | −3.01초 vs **3초 정지에 오탐** |
| **4. 락 유실 재현** | **미실행** | 결론이 자명하고, 피해를 재려면 임계 구역(INV-4/5/6)이 먼저 필요하다 | — |

| **6. 재시도·서킷** | 실행 완료 | 장애는 복구하지만 **설정 실수는 못 고친다.** 대신 보이게 만든다 | 죽은 서버 호출 **1,554건 → 13회(0.84%)** / 큐 **419건 전량 재배정 성공** |

## 2. 실험 1 — 6.43초는 어디로 갔나

앱 없이 Redis 레벨만 쟀다. 호스트에서 200ms 마다 "Sentinel 에 master 를 묻고 → 그 주소에
`SET`" 하는 프로브(`scripts/redis-write-probe.py`)를 돌렸다.

| | 실측 |
|---|---|
| t0 이전 마지막 성공 | `t0 − 85ms` |
| t0 이후 첫 성공 | `t0 + 6,347ms` (승격된 6381) |
| **쓰기 불가 구간** | **6.43초** |
| 실패 유형 | `Connection refused` 30회 + `Connection reset by peer` 1회 |
| `READONLY` | **0회** |

### 구간 분해

```
t0 ─────────── 5.08초 (79%) ──────────► +sdown
                                          │ 0.18초 (3%)
                                          ▼
                                     +elected-leader
                                          │ 1.02초 (16%)
                                          ▼
                                     +switch-master
                                          │ 0.077초 (1%)
                                          ▼
                                     첫 쓰기 성공  (t0+6,347ms)
```

| 구간 | 경계 | 시간 | 비중 | 무엇이 정하나 |
|---|---|---|---|---|
| ① 감지 | `t0` → `+sdown` | **5.08초** | **79%** | `down-after-milliseconds=5000` |
| ② 합의·선출 | `+sdown` → `+elected-leader` | 0.18초 | 3% | `quorum` + Sentinel 과반 리더 선출 |
| ③ 승격 | `+elected-leader` → `+switch-master` | 1.02초 | 16% | `REPLICAOF NO ONE` + 역할 변경 확인 왕복 |
| ④ 클라이언트 인지 | `+switch-master` → 첫 성공 | 0.077초 | 1% | 클라이언트 |

Sentinel 이벤트 (t0 기준 ms): `+sdown` 5,075 → `+odown` 5,148 (quorum 3/2) →
`+try-failover` 5,148 → `+elected-leader` 5,252 → `+selected-slave` 5,312 (6381) →
`+promoted-slave` 6,196 → `+switch-master` 6,270 → `+failover-end` 6,973.

**replica 선정**: 6380 / 6381 중 6381 이 뽑혔다. 죽기 직전 복제 오프셋이
**6952 vs 6523** 으로 6381 이 앞섰다 — `replica-priority` 가 같을 때 오프셋이 큰 쪽을
고른다는 규칙과 일치한다.

> **이 6.43초는 하한선이다.** 프로브가 매 tick Sentinel 에 새로 묻는 "이상적 클라이언트"
> 라서 캐시된 죽은 주소를 붙들지 않는다. 실제 앱이 얼마나 더 나쁜지가 실험 2 다.

## 3. 실험 2 — 판 A / B / C

같은 조건: 단일 스레드 프로브, 200ms 간격, 60초, `t0 = +10초` 에 kill.
**지표를 셋으로 나눠 잰 것이 핵심이다** — HTTP 응답 / 실제 배정(Redis 상태) / 둘의 차이.

| | **판 A**<br>둘 다 단일 노드 | **판 B**<br>Lettuce 만 Sentinel | **판 C**<br>둘 다 Sentinel |
|---|---|---|---|
| 총 요청 | 66건 | **278건** | 269건 |
| HTTP 201 | 41건 (62.1%) | 241건 (86.7%) | **266건 (98.9%)** |
| HTTP 503 | 25건 (37.9%) | 37건 (13.3%) | 3건 (1.1%) |
| 실제 배정 성공 | 41건 | 39건 (14.0%) | **266건** |
| 유실 | 25건 | **239건 (86.0%)** | 3건 |
| **HTTP 성공인데 배정 실패** | **0건** | **202건 (72.7%)** | **0건** |
| t0 이후 복구 | **없음** (50초 뒤에도 영구 장애) | HTTP 만 복구 | **t0+6,203ms** |
| 앱 레벨 다운타임 | ∞ | ∞ (배정 기준) | **≈ 6.04초** |

### t0 기준 구간별

| 구간 | 판 A (요청/201/배정) | 판 B (요청/201/배정) |
|---|---|---|
| t0 이전 | 41 / 41 / 41 | 39 / 39 / 39 |
| t0 ~ +10초 | 5 / 0 / 0 | 41 / 4 / **0** |
| +10 ~ +30초 | 10 / 0 / 0 | **99 / 99 / 0** |
| +30초 ~ | 10 / 0 / 0 | **99 / 99 / 0** |

### 읽는 법

**판 A** — Sentinel 을 띄워도 클라이언트를 안 고치면 아무 일도 안 일어난다.
t0 이후 복구가 0건이다. 총 요청이 66건뿐인 것도 지표다 — 판 C 의 269건 대비 **약 1/4**
로, 실패 요청이 `timeout: 2s` 만큼 매달려 처리량이 무너졌다.

**판 B — 가장 건강해 보이는 판이 가장 망가진 판이었다.**
처리량 278건으로 세 판 중 1위, 201 비율 86.7%. 그런데 t0 이후 배정은 **0건**이고
201 을 받은 **202건이 조용히 사라졌다**(첫 건 t0+9,360ms ~ 끝 건 t0+49,764ms).
`claim`(Lettuce)은 복구돼서 201 이 나가고, 배정(Redisson)은 죽은 노드만 보는데
그 예외가 `@Async` 뒤에서 삼켜지기 때문이다.
앱 로그: `비동기 작업 실패` 101건, `Redis 장애로 매칭 요청을 거절한다` 37건.
> 로그 101건과 유실 202건의 불일치는 **미확인**이다 (`matchingExecutor` 큐에 쌓인 채
> 실행되지 않은 작업이 있는 것으로 보인다).

**판 C** — Redis 기준선에 그대로 붙는다.

| t0+ | |
|---|---|
| 159ms | 첫 503 |
| 2,193ms | 503 (직전 요청 **2,034ms**) |
| 4,198ms | 503 (**2,005ms**) |
| **6,203ms** | **201 복구** |
| 7,302ms | 요청 간격 201ms 로 정상화 |

실패 요청의 소요 시간이 정확히 2,034 / 2,005 / 2,005ms 다 —
**`timeout: 2s` 가 실제로 걸린다.** 그리고 60초에 300건이 나가야 하는데 269건이다.
**부족한 31건이 6초 구간에 삼켜진 처리량**이다.

### 가설은 틀렸다

원래 가설은 "실제 다운타임을 지배하는 것은 클라이언트다" 였다.
**판 C 의 6.04초는 Redis 기준선 6.43초와 사실상 같다.** 클라이언트 몫은
실험 1 의 ④ 구간, 즉 **0.077초**뿐이었다.

틀린 방향이 중요하다. 클라이언트는 다운타임을 **몇 배로 늘리는 연속 변수가 아니라
유한이냐 무한이냐를 가르는 스위치**였다. 제대로 붙이면 Redis 기준선에 딱 붙고,
하나라도 빠뜨리면 무한으로 돌아간다 — **그리고 그때 모든 겉보기 지표는 정상보다 좋다.**

## 4. 실험 3 — 감지를 빠르게 만들 수 있지만, 만들지 않는다

오탐 유발은 `docker pause`(SIGSTOP)로 했다. **`DEBUG SLEEP` 은 Redis 7 부터
`enable-debug-command` 기본값이 `no` 라 못 쓴다** (`CONFIG SET` 으로도 못 바꾼다).
`pause` 는 프로세스만 멈추고 TCP/포트는 유지되므로 Sentinel 입장에서 같은 자극이다.

### 오탐 — 같은 3초 정지에 판이 갈린다

| 판 | `down-after` | 정지 | 오탐 | 근거 |
|---|---|---|---|---|
| **A1** | 5000 | 3초 | **없음** | Sentinel 이벤트 **0건** |
| **A2** | 5000 | 8초 | **발생** | `+sdown` 5,069 / `+odown` 5,239 / `+switch-master` 6,405 / `+failover-end` 6,719 |
| **B1** | **2000** | **3초** (A1 과 같은 조건) | **발생** | `+sdown` 2,193 / `+odown` 2,896 / `+switch-master` 4,013 / `+failover-end` 5,022 |

### 트레이드오프

| | `down-after=5000` (현재) | `down-after=2000` |
|---|---|---|
| 진짜 장애 시 쓰기 불가 | 6.43초 | **3.42초** (−3.01초) |
| `+sdown` / `+odown` | t0+5,075 / t0+5,148 | t0+2,053 / t0+2,192 |
| 3초 정지에 오탐 | **없음** | **발생** |
| `claim` TTL 60초 대비 | **11%** | 6% |

### 왜 안 바꾸기로 했나

**이 프로젝트의 시간 예산은 `claim-request.lua` 의 TTL 60초다.**
claim 이 성립한 요청은 60초 안에 배정되면 사용자 입장에서 아무 일도 없던 것이 된다.
6.43초는 예산의 11%, 3.42초는 6% — **둘 다 넉넉히 들어간다.**

**3초를 아껴서 얻는 것이 없고, 대신 정상 운영 중 반복되는 3초짜리 정지**
(RDB fork, 큰 키 `DEL`, 무거운 Lua, swap)**마다 오탐 페일오버를 사게 된다.**

오탐 1회의 값:

| 비용 | |
|---|---|
| 다운타임 6.43초 | 오탐도 진짜 페일오버와 같은 절차를 밟는다 |
| 미복제 데이터 유실 위험 | 승격되는 replica 가 못 받은 쓰기는 사라진다 |
| 구 master 가 자기를 master 로 믿는 창 **약 2초** | 실측. 복귀 시 Sentinel 이 `REPLICAOF` 로 강등시킬 때까지 |

→ **`down-after=5000` 유지.**
**측정해서 얻은 답이 "안 바꾼다" 인 것도 결과다.**

## 5. 실험 6 — 재시도·서킷은 무엇을 했나

동시 10스레드 프로브, 50초, `t0 = +10초` 에 kill.

### 판 C (정상 설정) — OFF ↔ ON

| | **OFF** | **ON** |
|---|---|---|
| 총 요청 | 2,070건 | 2,320건 |
| HTTP 201 | 2,040건 (98.6%) | 1,960건 (84.5%) |
| HTTP 503 | 30건 (1.4%) | 360건 (15.5%) |
| 배정 성공 | 2,034건 | 1,960건 |
| 유실 | 36건 | 360건 (전부 503) |
| **HTTP 성공인데 배정 실패** | **6건** (t0−2ms ~ t0+3ms) | **0건** |
| `비동기 작업 실패` 로그 | 7건 | **0건** |
| 서킷 | (기능 없음) | **한 번도 안 열림. 큐 0건** |

**0건은 재시도의 공이 아니다.** 서킷이 열린 적이 없고 큐도 비었다 —
배정 단계 실패 자체가 없었다. **정상 설정에서는 Redis 가 죽으면 claim(1단계)이 먼저
fail-closed 로 막아 503 을 내므로, 재시도 큐가 노리는 "claim 성공 + 배정 실패" 가
거의 생기지 않는다.**

여기서 확인된 것 하나: 로그에 `[failover] +switch-master 수신` /
`복구 신호 수신 source=pubsub` 이 찍혔다. **Sentinel pub/sub 구독이 실제로 작동한다** —
`docs/failover-retry-guide.md` 가 "실기로 검증하지 못했다" 로 남겨 뒀던 항목이 해소됐다.

> **재검증에서는 이 판에서도 서킷이 열렸다.** `failover` 패키지를 5개 파일로 통합한 뒤
> 같은 절차를 다시 돌렸더니, 부하 타이밍 덕에 장애 구간에 요청이 더 많이 들어가
> **배정 실패 419건**이 발생했다. 그래서 전 경로가 처음으로 끝까지 돌았다:
> `CLOSED → OPEN`(연속 3회) → `+switch-master` 수신(`source=pubsub`) →
> **프로브 1회 실패 → OPEN 복귀** → `open-timeout` 재프로브 성공 → `HALF_OPEN → CLOSED` →
> **큐 419건 전량 배출(재배정 성공 419 / 버림 0 / 유실 0)**, `deadMasterAttempts` 7회.
> `HTTP 성공인데 배정 실패` 와 `비동기 작업 실패` 는 여전히 **0건**이었다.
> 위 표(정리 전)보다 어려운 조건에서 같은 결론을 얻은 셈이고,
> **"큐에 쌓였다가 전량 복구되는" 완전한 사이클은 이때 처음 관측됐다.**

### 판 B (반쪽 설정) + ON — 결정적 검증

재시도가 노리는 상황을 실제로 만들려면 판 B 가 필요했다.

| | 값 |
|---|---|
| 총 요청 | 2,050건 |
| HTTP 201 / 503 / 연결실패 | 1,681건 (82.0%) / 360건 (17.6%) / 9건 |
| 배정 성공 | 400건 (19.5%) |
| 유실 | 1,650건 (80.5%) |
| HTTP 성공인데 배정 실패 | 1,281건 (62.5%) — t0+9,296ms ~ t0+39,848ms |
| **큐 등록** | **1,290건** |
| **`deadMasterAttempts`** | **28회** |
| **재배정 성공** | **0건** |
| 재시도 상한 초과로 버림 | 1건 (`attempts=6 age=76,137ms`) |
| `비동기 작업 실패` 익명 ERROR | **0건** (플래그 OFF 였던 실험 2 판 B 에서는 101건) |

> **위 수치는 `failover` 패키지를 11개 파일 → 5개로 통합하기 전 실행분이다.**
> 통합 후 같은 절차로 재검증했고 결론은 동일했다. 재검증 실측:
> 큐 등록 **1,554건** / `deadMasterAttempts` **13회(0.84%)** / 재배정 성공 **0건** /
> 버림 1건(`attempts=6 age=89,085ms`) / `비동기 작업 실패` **0건**.
> 절대값 차이는 앱 콜드스타트로 t0 이전 표본이 줄어든 것이 원인이고, 서킷 전이 순서와
> 로그 형식은 그대로였다.

**읽어야 할 두 줄.**

1. **1,290건 → 28회.** 큐에 들어온 1,290건 중 실제로 죽은 Redis 를 때린 것은 28회뿐이다.
   서킷이 나머지를 전부 막았다.
2. **재배정 성공 0건.** 판 B 에서는 Redisson 이 끝까지 죽은 노드만 본다.
   몇 번을 재시도해도 배정은 성공할 수 없다.

> **재시도·서킷은 장애를 복구하지만 설정 실수는 고치지 못한다.
> 대신 "조용한 실패" 를 "진단 가능한 실패" 로 바꾼다.**

**미측정**: `drainMs` / `withinTtl` / `drained` / `Δ_signal`, 그리고 원래 계획했던
복구 계기 3판(T / T-fast / E) 비교. 판 C 는 큐가 비었고 판 B 는 성공이 0 이라
비율이 정의되지 않는다.

> 그 뒤 **`drainMs` / `withinTtl` / `drained` / `dropped` 지표는 코드에서 제거했다**
> (`[failover] 배출 완료` 로그와 `request-ttl-seconds` 프로퍼티도 같이). 잴 판이 없는
> 지표를 코드에 남겨 둘 이유가 없었다. 다시 재려면 로그를 새로 붙여야 한다 —
> `docs/failover-retry-guide.md` §4.

## 6. 실험 중에 발견한 것들

**계획에 없던 것들이다.** 대부분 "실험을 하려다 막혀서" 찾았다.

| 발견 | 어떻게 찾았나 | 지금 상태 |
|---|---|---|
| **`@Async` 예외 삼킴이 실재한다** — 페일오버 중 배정이 통째로 실패해도 HTTP 는 전부 201 | HTTP 결과와 Redis 상태를 **따로 재서 차이를 냈다**(`verify-assign.py`). 판 B 에서 **202건 (72.7%)** | 문서화 (`docs/lock-safety-analysis.md` §1-4-a). 코드 수정은 사용자 판단 |
| **동시성 테스트 2개가 빈 결과 위에서 자동 통과하고 있었다** | 실험 준비로 테스트를 돌리다 파티가 0개 생성되는 것을 봤다. `PartyJoinConcurrencyTest` 가 claim 없이 배정만 불러 배정 Lua 가 `-2`(active-request 없음)를 반환 → 파티 0개 → **3개 중 2개가 빈 목록 위에서 "중복 없음" 으로 통과** | **수정 완료.** `blocks` 스키마 누락(`findBlockedUserIds` 실패)도 함께 고쳐 14개 테스트 전부 통과 (플래그 OFF) |
| **`application.yaml` 에 `spring.data.redis.sentinel` 블록을 두면 Sentinel 없이 앱이 안 뜬다** | 판 A 를 만들려고 `nodes` 를 비웠더니 `Cannot build a RedisURI. One of the following must be provided Host, Socket or Sentinel` 로 죽었다. Boot 4.1.1 의 `DataRedisConnectionConfiguration#determineMode()` 가 `getSentinelConfig() != null` 만 보고 `nodes` 가 비었는지는 안 본다 | **수정 완료.** `application-sentinel.yaml` 프로파일로 분리. 분리 후 오류가 `Connection refused: localhost/127.0.0.1:6379`(단일 노드 정상 동작)로 바뀌는 것을 확인 |
| **`TimeoutOptions.enabled()` 는 Boot 4.1.1 이 이미 기본으로 넣는다** | `spring-boot-data-redis-4.1.1.jar` 의 `createClientOptions()` 를 바이트코드로 확인. 판 C 에서 실패 요청이 정확히 2,034 / 2,005 / 2,005ms 걸린 것으로 **실측 재확인** | 문서 정정. "이걸 켜면 빨라진다" 는 **Boot 3.x 기준 서술**이었다 |
| **`DEBUG SLEEP` 이 Redis 7 에서 막혀 있다** | 오탐 실험을 돌리려다 `ERR DEBUG command not allowed`. `enable-debug-command` 기본값이 `no` 이고 `CONFIG SET` 으로도 못 바꾼다 | **도구 교체.** `docker pause`(SIGSTOP)로 같은 자극을 만든다 (`false-positive-test.sh`) |
| **`SentinelRecoveryWatcher` 가 락 클라이언트와 같은 프로퍼티를 읽는다 (설계 결함)** | 판 B 를 만들려고 `QUEUEMATE_LOCK_SENTINEL_NODES=""` 로 비웠더니 `[failover] Sentinel 노드가 없어 +switch-master 구독을 건너뛴다` 가 찍혔다. **Lettuce 는 Sentinel 에 붙어 있는데 감시자만 눈을 감았다** | 문서화 + 고치는 스니펫 제시 (`docs/failover-retry-guide.md` §6 (A) / §8-8). **코드는 안 고쳤다** — 사용자 판단 |
| **Sentinel 폴링(복구 신호의 백업 경로)이 한 번도 안 돌았다** | 4회 실행 전부 기동 로그가 `Sentinel 폴링 시작 ... 현재master=null` 이었고 `폴링이 master 변경을 감지했다` 는 **0건**. `readMasterAddress()` 가 항상 null 을 돌려줘 `poll()` 이 늘 조기 return 했다 | **제거 완료.** 폴링 코드 / `sentinel-poll-interval-ms` 프로퍼티 / yaml 줄을 걷어내고 근거를 코드 주석과 `docs/failover-retry-guide.md` §6 (C) 에 남겼다 |
| **`lib.sh` 의 공백 버그** | `docker` 가 인자를 엉뚱하게 받았다. `COMPOSE_FILES` 문자열을 따옴표 없이 펼쳐서 경로의 공백(`OneDrive/바탕 화면/...`)에서 단어가 쪼개졌다 | **수정 완료.** `COMPOSE_ARGS` 배열로 변경 |
| **구 master 가 복귀 직후 약 2초간 자기를 master 로 믿는다** | 죽인 노드를 `docker start` 로 되살리다 관측. 자기 설정 파일 때문이고 Sentinel 이 `REPLICAOF` 로 강등시킨다 | **실험 5(스플릿 브레인)의 축소판을 우연히 본 것.** 실험 5 를 건너뛴 근거 중 하나 |
| **zsh 에서는 `for s in $SENTINELS` 가 단어 분리를 안 한다** | 셸에서 `lib.sh` 를 `source` 해서 쓰다 발견 | lab 스크립트는 전부 `#!/usr/bin/env bash` 라 무관. 문서에 주의로 남김 |

### 측정 도구도 실험 중에 만들어졌다

계획에 있던 k6 프로브 대신 python 프로브를 새로 만들었다.
이유는 하나씩 다 "그렇게 안 하면 못 재는 것" 이 있었기 때문이다.

| 도구 | 왜 필요했나 |
|---|---|
| `redis-write-probe.py` | 앱을 섞으면 "Redis 가 못 받은 시간" 과 "클라이언트가 몰라서 못 보낸 시간" 이 한 숫자에 섞인다. 기준선에는 클라이언트 변수가 없어야 한다 |
| `verify-assign.py` | **HTTP 만 보면 판 B 를 절대 못 찾는다.** 실제 배정 여부는 Redis 상태로 봐야 안다 |
| `http-probe-concurrent.py` | 단일 스레드로는 장애 구간에 요청 하나가 2초씩 매달려 몇 건 못 보낸다. 그러면 "배정 단계 실패" 가 안 생겨 재시도 큐를 검증할 수 없다 |
| `false-positive-test.sh` | `DEBUG SLEEP` 이 막혀서 |

## 7. 결론

> **Sentinel 은 가용성 도구다. 붙이면 무한 장애가 6초가 된다 — 단, 클라이언트를 하나라도
> 빠뜨리면 다운타임이 무한으로 돌아가면서 모든 지표는 정상으로 보인다.
> 감지를 더 빠르게 만드는 건 가능하지만 우리 시간 예산(claim TTL 60초)에서는 하지 않는 게
> 맞다. 그리고 재시도·서킷은 장애를 복구하지 설정 실수를 고쳐주지 않는다 —
> 대신 보이게 만든다.**

### 이 실험으로 정해진 것

| 결정 | 근거 |
|---|---|
| `down-after=5000` **유지** | 실험 3. 3.01초를 아끼려고 3초 정지에 오탐을 살 이유가 없다 |
| **판 C(Lettuce·Redisson 둘 다 Sentinel) 말고는 답이 없다** | 실험 2. 판 B 는 매칭이 하나도 안 되면서 모든 겉보기 지표가 1위다 |
| `+switch-master` 구독은 **실제로 작동한다** | 실험 6 판 C. `source=pubsub` 확인 |

### 아직 안 정해진 것

| 남은 것 | 왜 |
|---|---|
| 락을 Redis 에 둘 것인가 | 실험 4·5 미실행. 피해를 재려면 INV-4/5/6 이 먼저 구현돼야 한다 |
| `min-replicas-to-write` 를 켤 것인가 | **가용성 비용 미측정.** 락 유실과 무관하게 지금도 잴 수 있다 (`EXPERIMENTS.md` 실험 4 의 "지금 당장 할 수 있는 조각") |
| 복구 계기를 타이머로 둘 것인가 `+switch-master` 로 둘 것인가 | 실험 6 에서 축을 흔들 판을 만들 수 없었다 |
| `SentinelRecoveryWatcher` 의 프로퍼티 결합을 끊을 것인가 | 코드 수정이 필요하다. 스니펫만 제시했다 (`docs/failover-retry-guide.md` §6 (A) / §8-8) |
| `assigner` 콜백을 `PartyAssigner` 빈으로 뺄 것인가 | 프로덕션에 새 클래스가 생겨 "failover 폴더만 지우면 원복" 제약이 깨진다 (`docs/failover-retry-guide.md` §6 (B)) |
