# Lua 선점과 Redis 분산 락 비교 결과

이 문서는 전환 전 실험과 당시 판단의 기록이다. 이후 사용자가 유지보수성을 우선한
분산 락 전환을 명시적으로 선택했다. 현재 채택 결정은
[분산 락 선점 설계](../../../docs/21_REDIS_CLAIM_LOCK.md)에 기록하며 아래 측정값은 변경하지 않는다.

2026-09-14, 기준 커밋 `57e2b3981fbdf4c85b11848cc659daac6541f8d4`의 작업 트리에서 실행했다.
기존 사용자 변경을 유지했으며, 제품 코드는 바꾸지 않았다. 실제 실행 명령과 비교 구현은
[README](README.md), 회차별 원시 통계는 [sample-results.json](sample-results.json),
환경은 [sample-environment.json](sample-environment.json), 장애 주입 확인 항목은
[sample-correctness.json](sample-correctness.json)에 있다.

## 결론

이번 실험은 **Lua 선점이 병목이라 Redis 분산 락으로 바꾸면 성능이 개선된다는 가설을 지지하지 않았다.**
실험한 분산 락 구현은 Lua보다 처리량이 낮고, 선점 p99와 요청당 Redis CPU 비용이 높았다.
따라서 제품의 Lua 선점을 이 구현으로 교체하지 않았다. 비교 가능한 분산 락 구현은 하네스에 남겼다.

이것은 모든 분산 락 구현이 느리다는 결론이 아니다. Java 검증과 전원 쓰기 보장을 갖춘
이번 구현에 대한 측정이다. 유지보수성을 우선해 비용을 감수하는 결정과, 부하테스트로
성능 개선이 입증됐다는 주장은 분리해야 한다.

## 조건과 성공 기준

실제 JVM 4개 × 각 8개 연결/스레드, 로컬 Redis 1개에서 선점만 비교했다.
양쪽 전략에 같은 Lettuce 클라이언트와 입력을 사용했다. 제품 Lua는 리소스 그대로 로드했다.
분산 락은 `SET NX PX → WATCH/MGET → Java 검증 → MULTI/EXEC → 소유권 확인 해제`다.
락 해제용 짧은 Lua는 남아 있다. 전체 Redis 서버 블로킹을 없앤 구현은 아니다.

각 전략 2,000건 예열 후, 파티 크기 2명·5명 × 참가자 경합 유무 × 전략 2개 × 3회 × 4,000건,
총 96,000건을 실행했다. 전략별 순서는 회차마다 바꿨다. 경합 상황은 JVM 4개가 동일 참가자 한 명을
서로 다른 동료들과 선점하려는 경우이며, 각 묶음에서 하나만 성공해야 한다. 별도 재시도는 없다.

96,000건 중 60,000건 성공, 36,000건은 예상된 선점 충돌이었다. 실행 오류와 중복 선점은 없었다.
각 성공의 참가자 집합·소유자·TTL, 실패한 제안의 부분 쓰기 부재, 큐 제거, mutex 해제를 모두 확인했다.
성능 수치에는 fixture 생성과 이 사후 검증을 포함하지 않는다.

## 성능

각 셀은 동일 조건 3회 측정값의 중앙값이다. p99 열은 회차별 p99의 중앙값이며,
전체 표본을 합친 p99가 아니다. 처리량은 충돌 응답까지 포함한 시도 수/초다.
경합에서는 시도의 25%만 성공하므로 성공 처리량은 해당 값의 1/4이며 원시 JSON에도 따로 기록했다.

| 파티 인원 | 참가자 경합 | 방식 | 시도/초 | 선점 p99(ms) | Redis CPU(μs/시도) | 별도 PING p99(ms) |
| --- | --- | --- | ---: | ---: | ---: | ---: |
| 2 | 없음 | Lua | 18,969 | 3.106 | 34.80 | 3.269 |
| 2 | 없음 | 분산 락 + Java | 4,590 | 10.646 | 101.99 | 2.085 |
| 2 | 있음 | Lua | 32,278 | 1.560 | 20.54 | 1.867 |
| 2 | 있음 | 분산 락 + Java | 6,799 | 8.886 | 64.91 | 1.759 |
| 5 | 없음 | Lua | 18,645 | 2.864 | 50.65 | 2.686 |
| 5 | 없음 | 분산 락 + Java | 3,270 | 13.325 | 154.84 | 1.865 |
| 5 | 있음 | Lua | 28,892 | 1.787 | 30.16 | 1.682 |
| 5 | 있음 | 분산 락 + Java | 4,190 | 11.971 | 130.76 | 1.719 |

분산 락의 처리량은 Lua 대비 약 15~24%, 선점 p99는 약 3.4~6.7배였다.
요청당 Redis CPU 비용도 약 2.9~4.3배였다. 연산을 Java로 옮겨도 여러 mutex 획득과
WATCH·트랜잭션·해제 명령이 추가되기 때문에 전체 Redis 작업이 줄었다고 볼 수 없다.
네트워크 왕복과 클라이언트 실행 비용도 있으므로 지연 전체를 서버 CPU만으로 설명하지 않는다.

별도 PING은 일부 조건에서 분산 락 쪽이 낮았다. 그러나 한 회차의 Lua 측정 구간은 더 짧고
PING 표본도 37~61개인 반면 락 방식은 188~430개였다. 양쪽이 같은 도착률의 부하를 받는 실험도
아니므로 이 값만으로 다른 기능의 지연 개선을 입증했다고 하지 않는다. 고정 도착률·충분한 시간의
별도 실험이 필요하다.

Lua 선점의 1ms 이상 SLOWLOG 기록은 전체 본 측정에서 1건(1.072ms)이었고, 락 해제 Lua는 0건이었다.
이 수치는 Redis 안의 스크립트 실행시간이며 클라이언트 선점 p99와 다르다. 짧은 로컬 실행의 관측이고,
운영에서 긴 Lua가 절대 없다는 보장은 아니다. 현재 코드에는 선점 외에 후보 조회 Lua도 있지만
이번 실험에 포함하지 않았다.

## 정합성과 장애 주입

성능 비교와 별도로 다음 검증이 통과했다.

- 두 전략: 참가자 한 명이 이미 배정되어 있으면 전체 실패, 활성 요청 ID가 바뀌면 실패.
- 분산 락: 일부 mutex만 획득하고 실패하면 자기 mutex만 해제.
- 분산 락: Java 검증 후 임대가 만료되면 EXEC 거부, 새 소유자의 mutex는 보존.
- 분산 락: Java 검증 후 활성 요청이 교체되면 EXEC 거부.
- 분산 락: EXEC 전 예외는 쓰기를 폐기하고 mutex 해제.
- 분산 락: EXEC 전 연결 종료는 쓰기를 적용하지 않으며 남은 mutex는 임대 만료로 제거.

임대 만료 경합은 PEXPIRE로 만든 결정적 장애 주입이다. 네트워크 분할이나 Sentinel master 장애를
재현한 것이 아니며 DB 저장, 예약 경로, 전체 모집 API의 안전성을 검증한 것도 아니다.
WATCH/MULTI/EXEC 역시 Redis 런타임 명령 오류를 자동 롤백하지 않는다.

## 설명에 사용할 수 있는 내용

> Lua 블로킹과 업무 로직의 유지보수 비용을 검토해, 참가자별 Redis 분산 락과 Java 검증을 사용하는
> 대안을 구현했다. JVM 4개에서 96,000건을 비교한 결과 중복 선점은 두 방식 모두 없었지만,
> 이 워크로드에서는 분산 락의 처리량과 지연이 악화됐다. 따라서 성능 개선을 이유로 한 전환은
> 보류하고 기존 Lua를 유지했다. 락 만료 및 부분 실패의 추가 처리 비용도 실험으로 확인했다.

"Lua 병목을 부하테스트로 찾아 분산 락으로 해결했다"거나 "분산 락으로 Sentinel의 기록 유실을
해결했다"는 설명은 이번 결과로 뒷받침할 수 없다.
