# 모드별 잠금 경합 실험 결과

2026-09-14, `test/backend-integration`, 기준 커밋 `433ead393acf00563b40795acb0d7de9ed3af12b`에서 실행했다.
작업 트리에 있던 사용자 변경을 유지한 상태다. 실행 코드와 재현 명령은 [README](README.md), 원시 수치는 [sample-results.json](sample-results.json), 환경은 [sample-environment.json](sample-environment.json)에 있다.

## 실제로 확인한 동작

매처가 모드 잠금을 보유하면 같은 모드의 신규 모집 등록도 기다린다.
`BoardService.create`와 `RealtimeMatcher.tryMatchAround`가 모두 `BoardStore.lock`을 호출하고,
이 메서드는 게임·모드를 키로 PostgreSQL 트랜잭션 advisory lock을 획득한다.
따라서 비동기 이벤트로 매처를 실행해도 등록 API와 매처의 DB 작업은 같은 모드에서 직렬화된다.

실제 잠금을 획득한 매처를 테스트 게이트로 일시 정지시킨 별도 검증에서:

- 다른 모드 등록은 매처를 풀어주기 전에 HTTP 201로 완료됐다.
- 같은 모드 등록은 완료되지 않았고 DB에서 미획득 advisory lock 1개가 관측됐다.
- 매처를 풀어주자 같은 모드 등록도 HTTP 201로 완료됐다.

이 검증은 대기 관계를 재현한다. 게이트로 늘린 시간을 정상 서비스 지연으로 해석하지 않는다.

## 비교 측정

한 JVM, Java 21.0.11, PostgreSQL 16 및 Redis 7 Testcontainers, 매처 스레드 4개,
Hikari 최대 연결 10개에서 실제 HTTP 요청을 보냈다. 각 회차는 100명, 최대 동시 요청 32개다.
한 모드에는 COMPETITIVE 100명, 두 모드에는 COMPETITIVE·UNRATED 각각 50명을 넣었다.
두 모드는 모두 동일한 5인 파티 규칙을 사용한다. 구성별 20명 예열 후 3회씩 순서를 번갈아 실행했다.

각 행의 p95는 해당 회차 100건의 95번째 백분위다. 시간 단위는 ms다.

| 회차 | 모드 수 | 등록 응답 p95 | 제안 관측 p95 | 등록 잠금 호출 p95 | DB 잠금 대기 최대 | 연결 풀 대기 최대 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| round-1 | 1 | 405.9 | 1175.7 | 209.8 | 9 | 26 |
| round-1 | 2 | 195.8 | 542.7 | 79.5 | 8 | 26 |
| round-2 | 2 | 209.1 | 539.5 | 80.0 | 8 | 26 |
| round-2 | 1 | 317.2 | 981.5 | 149.8 | 9 | 26 |
| round-3 | 1 | 306.9 | 932.0 | 144.7 | 9 | 26 |
| round-3 | 2 | 196.5 | 447.1 | 55.5 | 8 | 26 |

한 모드의 등록 p95는 306.9~405.9ms, 두 모드는 195.8~209.1ms였다.
제안 관측 p95는 각각 932.0~1175.7ms, 447.1~542.7ms였다.
측정한 600건 모두 등록에 성공했고 120개의 5인 제안이 만들어졌다. 중복 참가자, 잘못된 제안 인원,
남은 QUEUED 요청은 없었다. 사용자 수락과 파티 확정은 이 실험의 대상이 아니다.

## 해석과 한계

같은 모드에 요청이 몰렸을 때 잠금 경합과 더 긴 지연이 함께 관측됐다.
서로 다른 모드는 별도 잠금을 사용하므로 이 결과는 모드별 분산의 효과와 일치한다.
다만 연결 풀 대기도 두 구성에서 최대 26개였으며, 지연 전체를 advisory lock 하나의 비용으로 환산할 수는 없다.
잠금 호출 시간에는 SQL 실행 비용도 포함된다.

제안 지연은 클라이언트 HTTP 호출 시작부터 DB의 PROPOSED 상태를 처음 읽기까지다.
약 10ms 간격의 관측 오차와 HTTP 비용을 포함하고 클라이언트 작업 실행 대기는 제외한다.
WebSocket 전달 시간이나 파티 확정 시간이 아니다. Mockito 계측과 DB 관측 부하도 포함한다.
로컬의 짧은 반복 실험이므로 운영 최대 처리량, 다중 서버의 안전성, 기존 틱 방식 대비 개선율은 알 수 없다.

다음 개선 실험의 후보는 등록 트랜잭션과 매처가 같은 모드 잠금을 보유하는 구간을 줄이는 것이다.
잠금 제거는 중복 제안 방지와 취소·재등록 경합의 안전성을 별도로 검증해야 하므로 이번에는 제품 코드를 변경하지 않았다.

검증 명령 `matchingContentionStudy`는 최종 실행에서 성공했다(테스트 1개, 실패 0개).
