> 본문이 인용하는 명세 번호(1.4.17 등)는 같은 폴더의 기능 명세서 소주제 ID 다. 그 명세서도 같은 날 개정됐다.

## 결론

**RDB, 그중 PostgreSQL + 또 하나의 축으로서 Redis**

- **확정된 것의 저장소(Source of Truth): PostgreSQL** — 계정, 프로필, 게임 계정, 확정된 매칭(`match_proposals` + `proposal_members`), 파티, 친구·차단·신고·최근 함께한 사람, 예약, outbox
- **진행 중인 실시간 매칭 상태의 저장소(Source of Truth): Redis** — 매칭 요청, 아직 안 찬 파티, 진행 중 제안, 수락 집계, Lua 원자 처리, 게임 모드 설정, 사용자 알림 Pub/Sub

> 개정 이력: 예전 판은 "주 저장소(Source of Truth)는 PostgreSQL — 매칭 요청, 제안/좌석, Discord 상태, 알림 발송 이력까지",
> "Redis 는 휘발성/경합 처리용 보조"라고 적었다. 2026-09-19 에 위와 같이 바꿨다 — 진행 중 매칭 상태는 Redis 에만 두고
> 확정된 것만 DB 에 쓴다. `match_requests` 테이블을 만들지 않는다 (docs/11 #27·#28, CLAUDE.md §3). Discord 연동은 폐기됐고
> Web Push 는 나중 일로 미뤄졌다. 제목의 "LoL"도 뺐다 — 게임은 셋이다(docs/11 #8). 배포 기준은 현재 Stage 1(단일 EC2 +
> Docker Compose, PostgreSQL·Redis 도 컨테이너)이고 RDS / ElastiCache 는 Stage 2 의 일이다(docs/11 #20).

## 1. 왜 NoSQL이 아니라 RDB인가

| 요구 | RDB가 필요한 이유 |
|---|---|
| 파티 최종 확정 (명세 1.6.25) | 확정 순간에 **`match_proposals` + `proposal_members` + `outbox`** 를 한 트랜잭션으로 묶어야 한다. transactional outbox 는 트랜잭션 없는 저장소로는 성립하지 않는다 |
| 중복 방지 | `UNIQUE` 제약 하나로 DB 레벨에서 보장된다 — 예: "같은 사람을 두 번 차단할 수 없다"는 `social.blocks(blocker_id, blocked_id)` UNIQUE |
| 시간이 겹치는 활성 예약 금지 (INV-9, 명세 1.4.17) | 사용자별 시간 구간의 겹침을 exclusion constraint 로 강제한다. 키-값 조회로는 표현이 안 된다 |
| 서비스 경계 | 스키마별 DB 롤로 크로스 스키마 접근을 코드 리뷰가 아니라 런타임 `permission denied` 가 막는다 |
| 전 영역 | 친구·차단·파티 멤버·게임 계정이 전부 다대다 관계다. 참조 무결성을 앱에서 재구현할 이유가 없다 |

**데이터 규모도 근거다.** 이 서비스는 로그 분석 플랫폼이 아니라 매칭 서비스다. DB 에 남는 것이 "확정된 것"뿐이라 DB 에 요구되는 성질이 처리량이 아니라 **정확성**으로 좁혀진다 — 파티 확정은 초당 수 회다. 수평 확장을 위해 NoSQL을 택할 이유가 없고, 오히려 **정합성이 서비스의 핵심 가치**(중복 배정·이중 확정·정원 초과가 곧 버그)라 트랜잭션을 포기하는 비용이 크다.

> 개정 이력: 예전 판의 표에는 "수정·취소 경합을 `SELECT ... FOR UPDATE` / 낙관적 락으로 처리(명세 1.5.9)", "당일 예약 조회
> `WHERE play_date = ? AND status = 'RESERVED'`(3.1.2)", "매칭 실패 사유 분석용 애드혹 집계(2.9)", "user → request → proposal →
> seat → party → discord_channel 의 FK 체인"이 있었다. 2026-09-19 에 뺐다 — 실시간 매칭의 경합은 DB 락이 아니라 Redis Lua
> 원자 실행으로 처리하고(CLAUDE.md §4 "원자성 규칙"), 매칭 "시도"는 DB 에 남지 않아 DB 집계가 불가능하며(docs/11 #27),
> 예약 배치는 00시 일괄이 아니라 1분 주기이고(docs/11 #23), request · seat · discord_channel 테이블은 없다.
> 남긴 줄과 새로 적은 줄의 근거는 docs/WHY_POSTGRESQL.md 결론 · §1~§4 다.

### NoSQL을 택했을 때 무너지는 지점

#### DynamoDB
- 트랜잭션이 `TransactWriteItems` 100개 아이템 제한 + 조건부 쓰기 조합으로만 가능하다. 확정 트랜잭션을 묶는 건 가능하지만, 제약·FK·스키마별 권한을 전부 수작업으로 구현해야 한다
- 시간 겹침 검사(INV-9)처럼 **범위가 걸린 제약**을 저장소가 강제해 주지 않는다

#### MongoDB
- 4.x 이후 멀티 도큐먼트 트랜잭션은 되지만, 그럴 거면 RDB를 쓰는 게 낫다
- 스키마 유연성이라는 장점을 이 도메인은 필요로 하지 않는다

> 개정 이력: 예전 판은 DynamoDB 항목에서 "1.5.9 경합 처리를 전부 수작업 구현", "2.9 실패 사유 분석에 GSI 를 계속 늘려야 함",
> "결정적 매칭(2.4.1 전순서)을 하려면 전량 스캔"을 들었고, MongoDB 항목에서 "enum 과 컬럼이 명세에 이미 전부 고정돼 있다"를
> 들었다. 2026-09-19 에 뺐다 — 앞의 셋은 매칭 요청을 DB 에 두던 설계의 논거이고(지금은 Redis, docs/11 #27·#32·#33),
> 현재 `platform` 테이블의 컬럼은 아직 정해지지 않았다(../platform/CLAUDE.md §7).

## 2. RDB 중 PostgreSQL인 이유 (vs MySQL)

MySQL로도 만들 수 있지만, **PostgreSQL 고유 기능으로 앱 코드가 통째로 사라지는 지점**이 여러 개 있다.

| 기능 | PostgreSQL | MySQL 8 | 쓰임 |
|---|---|---|---|
| `tstzrange` + `EXCLUDE USING gist` | O | X | **시간이 겹치는 활성 예약 금지(INV-9)**를 DB 제약으로 강제. 경합 상황에서도 절대 안 뚫림 |
| 부분 유니크 인덱스 (`WHERE` 절) | O | X | "부분 조건에 유니크를 건다" — 예: 활성 예약, 대기 중인 친구 요청 |
| `jsonb` + GIN 인덱스 | O | JSON은 있으나 약함 | 확정된 매칭의 조건 스냅샷(`match_proposals.condition_snapshot_json`) |
| 스키마별 롤 / `GRANT` | O | 개념이 다름 | schema-per-service 경계를 런타임이 막는다 |
| `FOR UPDATE SKIP LOCKED` | O | O (8.0+) | Outbox → SQS 발행 relay |
| `timestamptz` | O (타임존 정확) | `TIMESTAMP` 처리 애매 | 시간을 UTC Instant 로 저장 |

특히 아래 하나만으로도 충분한 이유가 된다.

```sql
CREATE EXTENSION btree_gist;

-- 사용자별 시간 점유에 겹침 금지 제약을 거는 기법의 예 (옛 설계의 테이블이다. 현재 스키마가 아니다)
CREATE TABLE user_time_slot (
  id           bigserial PRIMARY KEY,
  user_id      bigint NOT NULL REFERENCES app_user(id),
  source_type  text   NOT NULL,        -- 'REQUEST' | 'PARTY'
  source_id    bigint NOT NULL,
  period       tstzrange NOT NULL,
  EXCLUDE USING gist (user_id WITH =, period WITH &&)
);
```

이 한 줄(`EXCLUDE`)이 "시간이 겹치는 구간을 두 번 점유할 수 없다"를 동시성 하에서도 완벽하게 처리한다. MySQL이면 애플리케이션 락 + 조회 후 삽입으로 구현해야 하고 TOCTOU 경합이 남는다.

> 개정 이력: 예전 판은 이 절의 쓰임 열을 옛 명세 번호로 채웠다 — 부분 유니크 = "사용자당 진행 중 요청 1건(1.5.1)",
> `jsonb` = 티어 스냅샷·실패 사유 데이터, 네이티브 `ENUM`, 배열 타입 = 부 포지션 목록, `timestamptz` = "KST 통일 · 00시 배치
> 경계". 2026-09-19 에 바꿨다 — "사용자당 활성 요청 1건"(INV-1)은 지금 DB 인덱스가 아니라 Redis Lua 가 지키고(CLAUDE.md §4),
> 부 포지션이 없고, 시간은 UTC 로 저장하며(docs/04 §2), enum 대신 varchar + CHECK 를 쓴다(docs/WHY_POSTGRESQL.md §4-3).
> **위 SQL 예시는 기법을 보이려고 그대로 뒀다.** 테이블 자체는 옛 설계다 — `app_user(id) bigint` 는 없고(사용자 id 는 로그인
> 아이디 문자열이다, ../platform/CLAUDE.md §3.5), 실시간 요청은 DB 에 점유 구간을 남기지 않는다. INV-9 를 실제로 어느 테이블에
> 어떻게 걸지는 `reservation.reservations` 의 컬럼이 정해질 때 정한다(docs/WHY_POSTGRESQL.md §1-1 참고).
> 예전 판의 "ERD 팁"(요청과 확정 파티의 시간 점유를 통합 테이블로 승격하라)은 뺐다 — 전제가 사라졌다.

## 3. Redis의 역할 (경계선)

Redis는 캐시나 작업 메모리가 아니라 **진행 중인 실시간 매칭 상태의 source of truth**다. DB 는 확정된 것만 안다.
**Redis 장애 시에는 새 매칭을 fail-closed 하고(INV-10), 큐를 DB 로부터 재구축하지 않는다** — 재구축의 입력이 될 데이터가
DB 에 없다. 복구 후 사용자가 다시 요청한다.

| Redis 담당 | 키 |
|---|---|
| 사용자당 활성 요청 1개 선점 (INV-1) | `qm:user:active-request:{userId}` HASH |
| 아직 안 찬 파티 (대기 상태 그 자체) | `qm:party:{partyId}` HASH — 메타데이터 + `member:{userId} = keyValue` |
| "아직 필요한 핵심 조건 값"별 파티 역색인 | `qm:party:open:{game}:{mode}:{voice}:{purpose}:needs:{keyValue}` ZSET |
| 진행 중 제안과 수락 집계 | 파티 HASH 의 `status`/`expiresAt`, `qm:proposal:accepts:{partyId}`, `qm:proposal:pending` |
| 게임 모드 설정 · 티어 사다리 · 티어 허용 범위 표 | `qm:gameconfig:*` (앱은 읽기만 한다. 지금은 시드 파일 `seed/gameconfig.redis` 가 사실상의 원본이고, DB 를 붙이면 `gameconfig` 스키마가 원본이 된다 — docs/GAME_CONFIG.md) |
| 후보 풀 락 | `qm:lock:pool:*` (Redisson) |
| 사용자 알림 fanout | Pub/Sub 채널 `qm:pubsub:push:{userId}` |

**반대로 Redis에 두지 않는 것**: 확정된 매칭, 파티, 계정, 소셜, 예약. 예약은 PostgreSQL 이 원본이고 Redis 는 claim 용이다.
앱 사이의 도메인 이벤트도 Redis 가 아니라 outbox → SQS FIFO 로 보낸다.

> 개정 이력: 예전 판은 "Redis 는 저장소가 아니라 매칭 엔진의 작업 메모리다. Redis 가 통째로 날아가도 Postgres 상태로 복구
> 가능해야 한다", "Redis 에 두면 안 되는 것: 제안/좌석/수락 상태 — 이건 Postgres 가 원본"이라고 적었다. 2026-09-19 에 정반대로
> 바꿨다 (docs/11 #27·#28·#29, CLAUDE.md §3 · INV-10). 키 표도 옛 것(대기열 Sorted Set, 대기 인원 카운터, 멱등 키 TTL,
> Riot 조회 single-flight 락)을 현재 키로 바꿨다 — 키 문자열의 단일 출처는 `redisKeys/SharedKeys.java` 다(CLAUDE.md §3).
> 예약(docs/04 §6), 도메인 이벤트(docs/11 #21).

## 4. 최종 구성

```
브라우저 ──REST──▶ app:platform          ──▶ PostgreSQL (account · party · social · reservation 스키마)
        ──REST──▶ app:matching          ──▶ Redis (진행 중 매칭 상태 · Lua · gameconfig)
                                         └─▶ PostgreSQL — 확정된 매칭만 쓴다 (matching 스키마, 아직 미구현)
                                                          + social.blocks SELECT (INV-6)
        ◀──SSE─── app:realtime          ◀── Redis Pub/Sub  qm:pubsub:push:{userId}
                  app:reservation-batch ──▶ PostgreSQL (reservation) · Redis (claim)

app:matching ──outbox──▶ SQS ProposalConfirmed.fifo ──▶ app:platform   (DB 에 파티를 만든다)
app:platform ──outbox──▶ SQS PartyClosed.fifo       ──▶ app:platform   (recent_players 를 만든다)
```

- PostgreSQL 인스턴스는 **1개**이고 **schema-per-service** 로 나눈다 — `account` `gameconfig` `matching` `reservation` `party` `social`. 크로스 스키마 FK·JOIN 금지, 스키마별 DB 롤. 유일한 예외는 `matching` 롤에 준 `social.blocks` SELECT 다.
- **현재 배포 기준은 Stage 1(단일 EC2 + Docker Compose)** 이다. PostgreSQL 과 Redis 도 컨테이너다. RDS + ElastiCache 는 Stage 2(ECS Fargate)의 구성이다.

> 개정 이력: 예전 판의 그림은 "Core API (ECS) — PostgreSQL 16 (RDS, Multi-AZ) / Redis 7 (ElastiCache) / SQS
> (notification-events · discord-commands)", "즉시 매칭 서비스 — 위 Postgres + Redis 공유", "예약 RunTask — batch_run 테이블 +
> UNIQUE(play_date)"였고 RDS vs Aurora 비교와 버전(16 이상)을 적었다. 2026-09-19 에 현재 배포 단위와 큐로 바꿨다
> (docs/11 #15·#17·#20·#21·#24·D-1, docs/AWS_ARCHITECTURE.md, ../platform/CLAUDE.md §1·§3.4·§3.5). `BlockChanged.fifo` 는
> 2026-09-19 에 폐기됐고 `PartyClosed.fifo` 의 소비자는 `app:platform` 하나다(../platform/CLAUDE.md §3.4).
> 스키마 목록에서 `shared_read` 는 뺐다(docs/11 D-1). RDS Multi-AZ / Aurora / PostgreSQL 버전은 현재 결정에 답이 없어
> 옮기지 않았다 — docs/AWS_ARCHITECTURE.md 의 Stage 2 그림은 "RDS PostgreSQL Primary 단일 인스턴스"라고 적는다.
> 위 그림에서 outbox 발행과 SQS 소비는 아직 어느 앱에도 구현돼 있지 않다.

## 5. ERD 작성 전 확정해야 할 것

**이 절은 폐기됐다.** 예전 판이 물은 세 가지는 다음과 같이 끝났다.

1. `matching_request` 를 즉시/예약 통합 테이블로 둘지 — **테이블 자체를 만들지 않는다.** 실시간 요청은 Redis 에만 있고
   (docs/11 #27), 예약은 `reservation.reservations` 다(docs/WHY_POSTGRESQL.md §3).
2. `party_proposal` / `proposal_seat` / `seat_response` 의 분리 수준 — **좌석·충원 회차 개념이 없어졌다.** 진행 중 제안은
   Redis 의 파티 HASH 위에 있고, DB 에는 확정된 것만 `match_proposals` + `proposal_members` 로 들어간다(docs/11 #27·#28).
3. Outbox 테이블 도입 여부 — **도입한다.** 앱 간 도메인 이벤트는 transactional outbox + SQS FIFO 다(docs/11 #21).
   다만 용도가 바뀌었다 — 옛 판의 outbox 는 알림·Discord 명령용이었고, 지금은 `ProposalConfirmed` / `PartyClosed` 용이다.
   사용자 알림은 outbox 를 타지 않고 Redis Pub/Sub 으로 간다(docs/11 #22).
