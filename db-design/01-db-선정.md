# DB 선정 결과 — LoL 파티 매칭 서비스

> 작성일: 2026-08-22
> 대상: 기능 명세서 대주제 1~5 (Core API + SSE / 즉시 매칭 / 예약 RunTask / Notification Worker / Discord Worker)

---

## 결론

**RDB, 그중 PostgreSQL (Amazon RDS for PostgreSQL) + 보조로 Redis(ElastiCache)**

- **주 저장소(Source of Truth): PostgreSQL** — 계정, 프로필, Riot 스냅샷, 매칭 요청, 제안/좌석, 확정 파티, Discord 상태, 알림 발송 이력
- **휘발성/경합 처리: Redis** — 즉시 매칭 대기열, Lua 원자적 선점, SSE 인스턴스 간 pub/sub, 멱등 키 TTL

명세 1.8.14에 이미 "재연결 시 **RDS**의 현재 상태를 기준으로 복구"라고 적혀 있고, 2.6.3에 "Redis Lua 원자 처리"가 명시돼 있다. 명세 자체가 이 구조를 전제하고 있으므로 이 선택은 명세와 정합적이다.

## 1. 왜 NoSQL이 아니라 RDB인가

| 명세 요구 | RDB가 필요한 이유 |
|---|---|
| 1.5.9 수정·취소 경합 처리 / 1.5.10 최신 상태 반환 | 상태머신 전이에 `SELECT ... FOR UPDATE` 또는 낙관적 락(version 컬럼)이 필요. "먼저 성공한 처리를 적용"은 조건부 UPDATE + 영향 행 수 검사로 구현 |
| 1.6.25 파티 최종 확정 | 확정 순간에 **party 생성 + seat 확정 + 모든 참가자 request 상태를 CONFIRMED로 전이 + outbox 이벤트 적재**를 한 트랜잭션으로 묶어야 함. 5~6개 테이블 다중 행 ACID |
| 1.5.11 / 1.6.9 / 4.4.1 / 5.6.7 중복 방지 | `UNIQUE(event_id)`, `UNIQUE(proposal_id, user_id)` 같은 제약 하나로 멱등성이 DB 레벨에서 보장됨 |
| 1.4.17 / 2.2.10 시간 중복 차단 | 사용자별 점유 시간 구간에 대한 범위 질의. 키-값 조회로는 표현이 안 됨 |
| 3.1.2 당일 예약 조회 | `WHERE play_date = ? AND status = 'RESERVED' AND created_at < ?` — 복합 조건 스캔 |
| 2.9 매칭 실패 사유 분석 | 조건별 후보 감소량 계산 = 애드혹 집계 질의. 접근 패턴이 사전에 고정되지 않음 |
| 전 영역 | user → request → proposal → seat → party → discord_channel 의 명확한 FK 체인. 참조 무결성을 앱에서 재구현할 이유가 없음 |

**데이터 규모도 근거다.** 이 서비스는 로그 분석 플랫폼이 아니라 매칭 서비스다. 하루 파티가 수만 건이어도 Postgres 단일 인스턴스에서 여유롭다. 수평 확장을 위해 NoSQL을 택할 이유가 없고, 오히려 **정합성이 서비스의 핵심 가치**(중복 배정·이중 확정·좌석 초과가 곧 버그)라 트랜잭션을 포기하는 비용이 크다.

### NoSQL을 택했을 때 무너지는 지점

#### DynamoDB
- 트랜잭션이 `TransactWriteItems` 100개 아이템 제한 + 조건부 쓰기 조합으로만 가능. 파티 확정 시 5명 x (request, seat, party, outbox)를 묶는 건 가능하지만, 락 없이 조건부 쓰기로 상태머신을 직접 짜야 함 → 1.5.9 경합 처리를 전부 수작업 구현
- 1.4.17 시간 중복 검사, 2.9 실패 사유 분석처럼 **접근 패턴이 유동적인 질의**에 GSI를 계속 늘려야 함. 단일 테이블 설계의 전제(모든 질의를 사전에 안다)가 깨짐
- 정렬 기반 결정적 매칭(2.4.1 신청 시각 + 요청 ID 정렬 전순서)을 하려면 결국 전량 스캔

#### MongoDB
- 4.x 이후 멀티 도큐먼트 트랜잭션은 되지만, 그럴 거면 RDB를 쓰는 게 낫다
- 스키마 유연성이라는 장점을 이 도메인은 필요로 하지 않음 — enum과 컬럼이 명세에 이미 전부 고정돼 있음(1.2.2~1.2.8, 1.4.4~1.4.16)

## 2. RDB 중 PostgreSQL인 이유 (vs MySQL)

MySQL로도 만들 수 있지만, 이 명세는 **PostgreSQL 고유 기능으로 앱 코드가 통째로 사라지는 지점**이 여러 개 있다.

| 기능 | PostgreSQL | MySQL 8 | 이 명세에서의 쓰임 |
|---|---|---|---|
| `tstzrange` + `EXCLUDE USING gist` | O | X | **1.4.17 시간 중복 요청 차단**을 DB 제약으로 강제. 경합 상황에서도 절대 안 뚫림 |
| 부분 유니크 인덱스 (`WHERE` 절) | O | X | "사용자당 진행 중 요청 1건"을 인덱스로 강제 (1.5.1) |
| `jsonb` + GIN 인덱스 | O | JSON은 있으나 약함 | 티어 스냅샷(1.4.19), 합의 조건 스냅샷(1.7.6), 실패 사유 데이터(2.9.3) |
| 네이티브 `ENUM` / `CHECK` | O | ENUM 있으나 변경 비용 큼 | 큐·포지션·음성·목적·상태 전부 enum |
| 배열 타입 | O | X | 부 포지션 목록(1.2.7) |
| `FOR UPDATE SKIP LOCKED` | O | O (8.0+) | Outbox → SQS 발행 워커 |
| `timestamptz` | O (타임존 정확) | `TIMESTAMP` 처리 애매 | KST 통일(1.4.18), 00시 배치 경계(3.1.3) |

특히 아래 하나만으로도 충분한 이유가 된다.

```sql
CREATE EXTENSION btree_gist;

-- 사용자별 시간 점유 통합 테이블 (요청/확정파티 공통)
CREATE TABLE user_time_slot (
  id           bigserial PRIMARY KEY,
  user_id      bigint NOT NULL REFERENCES app_user(id),
  source_type  text   NOT NULL,        -- 'REQUEST' | 'PARTY'
  source_id    bigint NOT NULL,
  period       tstzrange NOT NULL,
  EXCLUDE USING gist (user_id WITH =, period WITH &&)
);
```

이 한 줄(`EXCLUDE`)이 명세 **1.4.17(시간 중복 요청 차단)** 과 **2.2.10 / 3.2.9(시간 겹치는 확정 파티 보유자 제외)** 를 동시에, 그리고 동시성 하에서도 완벽하게 처리한다. MySQL이면 애플리케이션 락 + 조회 후 삽입으로 구현해야 하고 TOCTOU 경합이 남는다.

> **ERD 팁**: 위처럼 요청과 확정 파티의 시간 점유를 **별도 통합 테이블로 승격**시킬 것. request 테이블과 party 테이블에 각각 시간을 두면 두 테이블에 걸친 중복 검사를 제약으로 걸 수 없다.

## 3. Redis의 역할 (경계선)

Redis는 **저장소가 아니라 매칭 엔진의 작업 메모리**다. Redis가 통째로 날아가도 Postgres 상태로 복구 가능해야 한다(1.8.14).

| Redis 담당 | 명세 |
|---|---|
| 즉시 매칭 대기열 (Sorted Set, score = 신청시각) | 2.1.2, 2.4.1 |
| 요청/사용자 선점 Lua 스크립트 | 2.6.1~2.6.7, 2.8.14 |
| SSE 인스턴스 간 Pub/Sub | 1.8.15 |
| 현재 대기 인원 카운터 | 1.4.21, 2.1.9 |
| 멱등 키 TTL 캐시 | 1.5.11, 1.6.9 |
| Riot 조회 single-flight 락 | 1.3.13 |

**반대로 Redis에 두면 안 되는 것**: 제안/좌석/수락 상태(1.6.11). 이건 Postgres가 원본이고 Redis는 선점 여부만 안다. 그래야 재연결 복구(1.8.14)와 Core API 다중 인스턴스가 성립한다.

## 4. 최종 구성

```
Core API (ECS)  ──┬── PostgreSQL 16 (RDS, Multi-AZ)   ← 원본 데이터
                  ├── Redis 7 (ElastiCache)            ← 대기열/선점/SSE pubsub
                  └── SQS (notification-events / discord-commands)
                          ↑ Outbox 테이블 → 발행 워커 (SKIP LOCKED)

즉시 매칭 서비스 ──┴── 위 Postgres + Redis 공유
예약 RunTask     ──── 위 Postgres (3.5 멱등성은 batch_run 테이블 + UNIQUE(play_date))
```

- **RDS vs Aurora**: 이 규모라면 **RDS for PostgreSQL Multi-AZ**로 충분하다. 비용이 Aurora의 절반 수준이고, 읽기 부하가 확실히 문제될 때 Aurora로 옮겨도 늦지 않다.
- 버전: PostgreSQL 16 이상 (17도 무방)

## 5. ERD 작성 전 확정해야 할 것

1. **`matching_request` 하나로 즉시/예약을 통합할지, 분리할지**
   - 상태 집합(1.5.2~1.5.8)이 겹치므로 단일 테이블 + `match_type` 판별 컬럼 + CHECK 제약 권장

2. **`party_proposal` / `proposal_seat` / `seat_response`의 분리 수준**
   - 대체 충원 반복(2.8.19)이 있으므로 좌석에 "회차" 개념이 필요
   - 좌석 1개에 응답 N개(거절 → 재개방 → 새 후보)가 쌓이는 구조

3. **Outbox 테이블 도입 여부**
   - 1.9.9(메시지 식별자 생성)와 4.4.1(중복 방지)을 보면 Outbox 패턴이 사실상 요구사항
   - 파티 확정 트랜잭션 안에서 이벤트를 적재해야 "확정됐는데 알림이 안 감" 또는 "알림 갔는데 확정 롤백됨"이 사라짐
