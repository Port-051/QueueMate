서비스끼리 어떻게 말을 거는가

통신 설계의 큰 틀은 맞다. SQS와 Redis를 나눠 쓴 판단도, 큐를 둘로 쪼갠 것도 적절하다. 통신 경로 13개를 전수로 봤고 7개를 고쳐야 한다. 그중 4개는 서비스끼리 주고받는 방식 문제고, 3개는 외부 API 호출과 내부 스케줄링에 있다. 한 개는 네가 정해야 결정된다.

배선도

화살표 하나가 서비스 간 통신 하나다. 빨강은 방식이 틀렸거나 없는 것, 주황은 없어도 되는 것.

Service-to-service links

1 웹 클라이언트 ↔ Core API 정상 동기 HTTP · SSE 그대로
2 Core API → 즉시 매칭 방식 틀림 동기 HTTP Redis 대기열에 직접 push

서비스가 서로에게 말을 거는 방식의 문제. 위 배선도의 ②④⑦⑧에 해당한다.

2 방식 틀림

Core API가 즉시 매칭을 동기 HTTP로 부른다

증상
매칭 서비스가 배포 중이거나 죽어 있으면 매칭 신청 API 자체가 실패한다. Core API는 멀쩡한데도.
이유
가용성이 두 서비스의 곱이 된다. 응답을 안 기다리게 바꿔도, 그 순간 상대가 죽어 있으면 요청이 조용히 사라진다 — 에러조차 안 나서 더 나쁘다.
수정
Core API가 Redis 대기열에 직접 넣고, 매칭 서비스는 그 대기열만 폴링한다. 부를 대상 자체가 사라진다.
Core API → Redis 대기열 → 즉시 매칭 ↑ 매칭이 죽어도 여기 그대로 쌓임
7 링크 없음

Discord Worker가 Core API에 말을 걸 수 없다

증상
채널을 만들고 나서 “다 됐다”를 알릴 방법이 없다. 아키텍처 그림에서 Discord Worker를 빠져나가는 화살표는 Discord API 방향뿐이다.
근거
명세 5.2.8 생성 완료 이벤트 발행, 1.8.12 Discord 연결 상태 SSE 전달 — 둘 다 이 링크를 전제로 쓰여 있다.
수정
링크 3과 같은 Redis Pub/Sub을 쓴다. 목적이 같으니 메커니즘도 같아야 한다 — 새 통신 방식을 늘리지 않는 게 핵심.
Discord Worker ① party_discord_channel INSERT ② PUBLISH sse:party:{partyId} ↓ Core API 구독 → SSE로 파티원 전원
8 일관성 깨짐

예약 RunTask만 Outbox를 건너뛴다

증상
Core API는 outbox_event를 거치는데 RunTask만 SQS로 직접 쏜다. DB 커밋과 메시지 발행이 따로 논다.
이유
party 저장은 됐는데 발행이 실패하면 채널도 알림도 영영 안 온다. 반대면 없는 파티의 알림이 나간다. 둘을 한 트랜잭션으로 묶을 방법은 없다.
수정
RunTask도 outbox_event INSERT까지만 하고 끝낸다. 발행은 릴레이가 맡는다. 발행 경로가 한 곳으로 모이고 재시도·DLQ도 한 번만 만들면 된다.
4 불필요

대기 만료를 굳이 매칭 서비스가 통보한다

증상
매칭 서비스가 만료를 발견해 Core API에 알리고, Core API가 상태를 바꾼다. 왕복이 한 번 돈다.
이유
만료는 requested_at + max_wait_minutes만 보면 된다. 남과 비교할 필요가 없는 판단이라 매칭 서비스가 알 이유가 없다.
수정
Core API가 10초마다 직접 스캔한다. 명세 1.4 도입부의 “혼자 판정 가능한 건 Core API” 원칙 그대로. 같은 이유로 대기 인원 집계도 Core API가 Redis에서 바로 센다.
UPDATE match_request SET status = 'FAILED' WHERE status = 'QUEUED' AND requested_at + max_wait < now();

배선도 밖 — 고칠 것 셋

서비스 사이가 아니라 바깥으로 나가는 호출과 서비스 안에서 스스로 돌리는 작업에 있는 문제. 배선도에는 안 그려지지만 요청 방식 문제인 건 같다.

검토 범위 서비스 간 링크 8· 외부 API 호출 3· 내부 예약 작업 2 =13개 경로
A 외부 API 막힘

채널 삭제 예약을 SQS로 하려 하면 아예 막힌다

증상
명세 5.5.2는 “삭제 예정시각에 실행할 작업을 등록한다”인데 어디에 등록하는지가 없다.
함정
SQS 지연 메시지의 최대값은 900초, 즉 15분이다. 필요한 지연은 파티 종료 + 24시간. 애초에 불가능하다 — 모르고 시작하면 하루를 버린다.
수정
DB 폴링. party_discord_channel에 delete_after와 deleted_at이 이미 있다. 1시간 주기면 충분하다 — 24시간 뒤 삭제인데 1시간 오차는 의미가 없다.
SELECT * FROM party_discord_channel WHERE delete_after < now() AND deleted_at IS NULL AND status = 'CREATED';
B 외부 API 격리 없음

Riot API를 사용자 요청 한가운데서 동기로 부른다

증상
Riot이 5초 걸리면 사용자도 5초를 기다린다. Riot이 느려지는 순간 매칭 신청 API 전체가 같이 느려진다.
이유
명세 1.3.12에 “장애 시 저장된 정보를 쓴다”는 폴백은 있는데, 무엇을 장애로 볼지 — 즉 타임아웃 기준이 없다. 그러면 폴백이 발동을 안 한다.
수정
타임아웃 2초를 넘으면 즉시 캐시로 폴백. 연속 실패가 쌓이면 서킷 브레이커로 호출 자체를 건너뛴다. 1.3.13 동시 조회 통합은 Redis 락으로 처리.
C 유실 대비 복구 경로 없음

Redis Pub/Sub은 아무도 안 듣고 있으면 그냥 사라진다

증상
매칭이 제안을 발행한 순간 Core API가 배포로 재시작 중이면 메시지가 증발한다. 사용자는 제안 화면을 못 보고, 아무도 응답하지 않은 채 만료된다.
절반은 막혀 있음
제안은 match_offer에 남아 있어서 SSE를 재연결하면 1.8.14로 복구된다. 문제는 연결이 멀쩡할 때다 — 재연결 트리거가 없어 영영 모른다.
수정
클라이언트가 대기·제안 상태일 때만 30초마다 현재 상태를 재조회한다. 코드 10줄이면 되고, Pub/Sub을 Stream으로 갈아엎는 것보다 훨씬 싸다.

네가 정해야 하는 것 하나

파티 제안을 RDS에 쓰는 주인이 누구인가

매칭 서비스가 RDS를 읽을 이유는 없다는 건 정리됐다. 요청 조건을 Core API가 정제해서 넘겨주니까. 남은 건 match_offer·offer_participant를 누가 INSERT 하느냐다. 이게 정해져야 링크 ③의 성격이 확정된다.

안 1 · 매칭 서비스가 직접 쓴다
  • 명세 2.7 그대로라 수정 불필요
  • 매칭에 RDS 커넥션과 스키마 지식이 필요
  • 선점 실패 시 롤백을 매칭이 처리 (2.6.7)
안 2 · Core API가 쓴다 권장
  • 매칭 서비스의 RDS 커넥션이 0개가 된다
  • 매칭 담당자가 DB 스키마를 몰라도 됨
  • 매칭 엔진이 입력→출력 순수 함수 — 2.4.10 “동일 입력 동일 결과”가 단위 테스트로 바로 증명됨
  • 대신 명세 2.7을 “이벤트 발행만”으로 고쳐야 함

대신 생기는 리스크

통신의 절반이 Redis를 탄다

Redis가 죽으면 대기열이 증발하고 Pub/Sub이 끊긴다. ElastiCache 레플리카가 30초~1분 안에 페일오버하지만, 그동안 매칭은 멈춘다. Core API가 QUEUED 요청을 대기열에 다시 채워 넣는 복구 경로만 있으면 데이터는 하나도 잃지 않는다 — 원본은 항상 RDS에 있으니까.

다만 배치 자체는 잘 잡혔다. 잃으면 안 되는 것은 SQS(관리형이라 사실상 안 죽는다), 빨라야 하는 것은 Redis(죽어도 다시 채우면 된다). 반대로 놨다면 그게 진짜 문제였을 것이다.
