## 1. 🔴 Discord 채널 삭제 — 실행 방법이 안 정해져 있고, 명세와 그림이 어긋난다

### 문제 1 — "예약한다"의 방법이 빈칸이다

명세 5.5.1이 "파티 종료 예정 시각 + 24시간"에 채널을 삭제하라고 한다.
5.5.2는 **"삭제 예정시각에 실행할 채널 삭제 작업을 등록한다"**인데, **어디에 어떻게 등록하는지가 안 적혀 있다.**

구현자가 이 문장만 보고는 아무것도 못 만든다.

### 문제 2 — 명세와 아키텍처 그림이 서로 다르다

| 출처 | 내용 |
|---|---|
| 명세 5.1.2 | "전용방 생성·**삭제**·선택적 DM 명령을 구분한다" → 삭제도 큐를 탄다 |
| 명세 5.1.1 | "**discord-commands 큐**에서 Discord 작업 명령을 가져온다" |
| 아키텍처 그림 | `Amazon SQS · discord-commands` — **"CREATE_DISCORD_ROOM 전용"** |

**그림은 생성 전용인데 명세는 삭제도 같은 큐로 온다고 한다.** 둘 중 하나를 고쳐야 한다.

### 알아둘 것 — SQS 지연 메시지는 답이 될 수 없다

혹시 "SQS에 24시간 뒤 배달 메시지를 던진다"를 고려한다면 미리 알아둬야 한다.

```
SQS DelaySeconds 최대값 = 900초 = 15분
필요한 지연            = 24시간
```

**애초에 불가능하다.** 이 방향으로 설계하면 코드를 다 짜고 나서 막힌다.

### 권장 — DB 폴링

`party_discord_channel`에 필요한 컬럼이 **이미 다 있다.**

```sql
-- Discord Worker가 1시간마다 실행
SELECT * FROM party_discord_channel
WHERE delete_after < now()
  AND deleted_at IS NULL
  AND status = 'CREATED'
LIMIT 100;
```

- **주기는 1시간이면 충분하다.** 24시간 뒤 삭제인데 1시간 오차는 의미가 없고, 폴링 부하도 사실상 0이다.
- `delete_after`는 파티 확정 시점에 `end_at + 24시간`으로 계산해서 넣어둔다.
- 이렇게 하면 5.5.3(삭제 대상 확인)과 5.6.9(중복 삭제 방지)가 `deleted_at IS NULL` 조건 하나로 같이 해결된다.
- **SQS는 생성 명령 전용으로 남는다** → 아키텍처 그림 그대로다.

> 다른 선택지인 EventBridge Scheduler 일회성 스케줄도 가능하긴 하다.
> 다만 파티마다 스케줄을 만들고 지워야 해서 관리 대상이 늘어난다. 컬럼이 이미 있는 지금은 DB 폴링이 훨씬 싸다.

### 고칠 곳
- [ ] 명세 5.5.2 문구를 "삭제 예정시각을 `delete_after`에 기록한다"로 변경
- [ ] 명세 5.1.2에서 "삭제" 명령을 빼거나, 반대로 그림의 큐 설명을 "생성·삭제"로 넓히거나 — 둘 중 하나로 통일
- [ ] Discord Worker에 삭제 스캔 스케줄러 추가

## 2. 서비스 간 통신 구조

> 통신 경로 13개(서비스 간 8 + 외부 API 3 + 내부 예약 2)를 전수 검토한 결과.
> 시각 자료: `review/comm-wiring.html`

### 2-1. 🟡 Core API → 즉시 매칭이 동기 HTTP다

**증상** — 매칭 서비스가 배포 중이거나 죽어 있으면 **매칭 신청 API 자체가 실패한다.** Core API는 멀쩡한데도.

**왜** — 가용성이 두 서비스의 곱이 된다(99% × 99% = 98%).
응답을 안 기다리게 바꿔도, 그 순간 상대가 죽어 있으면 요청이 **조용히 사라진다.** 에러조차 안 나서 오히려 더 나쁘다.

**어떻게**

```
Core API  →  Redis 대기열에 push  →  즉시 매칭이 폴링해서 가져감
                   ↑
          매칭이 죽어 있어도 여기 그대로 쌓임
```

부를 대상 자체가 사라진다. 서비스 디스커버리도 필요 없어진다.

- [ ] 아키텍처 그림에서 `Core API → 즉시 매칭` 화살표를 `Core API → Redis`로 변경

---

### 2-2. 🟡 Discord Worker → Core API 링크가 아예 없다

**증상** — 채널을 만들고 나서 **"다 됐다"를 알릴 방법이 없다.** 아키텍처 그림에서 Discord Worker를 빠져나가는 화살표는 Discord API 방향뿐이다.

**근거** — 명세 5.2.8(생성 완료 이벤트 발행)과 1.8.12(Discord 연결 상태 SSE 전달)가 **둘 다 이 링크를 전제로 쓰여 있다.**

**어떻게** — 즉시 매칭이 제안을 알릴 때 쓰는 것과 **같은 Redis Pub/Sub**을 쓴다. 목적이 같으니 방식도 같아야 한다. 새 통신 방식을 늘리지 않는 게 핵심.

```
Discord Worker
  ① party_discord_channel INSERT (status = CREATED)
  ② PUBLISH sse:party:{partyId}
        ↓
  Core API 구독 → SSE로 파티원 전원에게 전달
```

> Notification Worker에는 굳이 안 보내도 된다. 파티 확정 알림이 이미 나간 상태에서 몇 초 뒤에 "채널도 준비됐어요" 푸시를 또 보내는 건 알림 스팸이다.

- [ ] 아키텍처 그림에 `Discord Worker → Redis Pub/Sub → Core API` 화살표 추가

---

### 2-3. 🟡 예약 RunTask만 Outbox를 건너뛴다

**증상** — Core API는 `outbox_event`를 거치는데 RunTask만 SQS로 직접 쏜다.

**왜** — DB 커밋과 메시지 발행을 한 트랜잭션으로 묶을 방법이 없다.

```
party INSERT 성공 → SQS 발행 실패  =  확정 파티인데 알림도 채널도 영영 안 옴
SQS 발행 성공 → party INSERT 롤백  =  없는 파티의 알림이 나감
```

**어떻게** — RunTask도 `outbox_event` INSERT까지만 하고 끝낸다. 발행은 릴레이가 맡는다.
그러면 outbox → SQS 경로가 한 곳으로 모이고, 재시도·DLQ도 한 번만 만들면 된다.

- [ ] 아키텍처 그림에서 `RunTask → SQS` 화살표 제거

---

### 2-4. 🟡 대기 만료 통보 링크는 아예 없애도 된다

**증상** — 매칭 서비스가 만료를 발견해서 Core API에 알리고, Core API가 상태를 바꾼다. **왕복이 한 번 돈다.**

**왜** — 만료는 `requested_at + max_wait_minutes`만 보면 되는, **남과 비교할 필요가 없는 판단**이다.
명세 1.4 도입부의 원칙 그대로다: *"혼자 판정 가능한 것은 Core API, 남과 비교해야 하는 것은 매칭 서비스."*

**어떻게** — Core API가 10초마다 직접 스캔한다.

```sql
UPDATE match_request SET status = 'FAILED'
WHERE status = 'QUEUED'
  AND requested_at + (max_wait_minutes * interval '1 minute') < now();
```

같은 이유로 **대기 인원 집계(2.1.9)도 Core API가 Redis `ZCARD`로 직접 센다.**

이렇게 하면 즉시 매칭 서비스의 책임이 **"후보 구성 + 포지션 배정 + 선점"으로만** 좁혀진다.

- [ ] 명세 2.1.7 / 2.1.8 / 2.1.9를 대주제 2에서 대주제 1로 이동

### 2-5. 🟡 Riot API에 타임아웃 기준이 없다

**증상** — Riot이 5초 걸리면 사용자도 5초를 기다린다. Riot이 느려지는 순간 매칭 신청 API 전체가 같이 느려진다.

**왜** — 명세 1.3.12에 "장애 시 저장된 정보를 쓴다"는 **폴백은 있는데**, 무엇을 장애로 볼지가 없다. 그러면 폴백이 발동을 안 한다.

**어떻게**

| 항목 | 내용 |
|---|---|
| 타임아웃 | 2초. 넘으면 즉시 캐시 폴백 |
| 서킷 브레이커 | 연속 실패가 쌓이면 호출 자체를 건너뛰고 바로 캐시 |
| 동시 조회 통합 (1.3.13) | Redis 락으로 같은 계정 조회를 1건으로 |

> 참고: Riot 개인 개발자 키는 20 req/s, 100 req/2min 제한이 있다.

### 2-6. 🟡 Redis Pub/Sub 유실에 대비가 없다

**증상** — Redis Pub/Sub은 **구독자가 없으면 메시지가 그냥 사라진다.** 매칭이 제안을 발행한 순간 Core API가 배포로 재시작 중이면 증발한다. 사용자는 제안 화면을 못 보고 그대로 만료된다.

**절반은 이미 막혀 있음** — 제안은 `match_offer`에 저장되니까, SSE를 **재연결하면** 1.8.14로 복구된다.
문제는 연결이 멀쩡할 때다. 재연결 트리거가 없어서 영영 모른다.

**어떻게** — 클라이언트가 **대기·제안 상태일 때만** 30초마다 현재 상태를 재조회한다.

```js
setInterval(() => {
  if (state === 'QUEUED' || state === 'PROPOSED') {
    fetch('/api/me/current-state').then(sync);
  }
}, 30_000);
```

**코드 10줄이면 된다.** Pub/Sub을 Stream으로 갈아엎는 것보다 훨씬 싸고, SSE 자체의 잔버그도 같이 커버된다.

- [ ] 명세 1.8에 소주제 추가: *"상태 폴백 동기화 — SSE 이벤트 유실에 대비해 클라이언트가 주기적으로 현재 상태를 재조회한다."*

### 2-7. 정리 — 수정 후 남는 통신 방식은 셋

| 패턴 | 방식 | 쓰는 곳 | 왜 |
|---|---|---|---|
| 작업 지시 | Redis 자료구조 | Core API → 즉시 매칭 | 순서 필요 + 유실 불가 + 폴링 소비 |
| 실시간 통보 | Redis Pub/Sub | 즉시 매칭 → Core API<br>Discord → Core API | 저지연 + 팬아웃 + 복구 가능하니 유실 허용 |
| 외부 부수효과 | Outbox → SQS | Core API · RunTask → Worker | 유실 불가 + 재시도 + DLQ |

**서비스 간 동기 HTTP가 하나도 안 남는다.**
동기 호출은 클라이언트 ↔ Core API와 Worker → 외부 API에만 남는다.

이러면 서비스 하나가 죽어도 다른 게 안 죽고, 아무 때나 배포해도 되고, 서로 주소를 알 필요도 없다.

### 남는 리스크 — Redis가 단일 장애점

Redis가 죽으면 대기열이 증발하고 Pub/Sub이 끊긴다. ElastiCache 레플리카가 30초~1분 안에 페일오버하지만 그동안 매칭은 멈춘다.

- [ ] **Core API에 "`QUEUED` 요청 재적재" 경로 추가** (기동 시 1회 + 주기적 정합성 체크)

원본은 항상 RDS에 있으니 이 경로만 있으면 데이터는 하나도 안 잃는다.

> 배치 자체는 잘 잡혔다. **잃으면 안 되는 것은 SQS**(관리형이라 사실상 안 죽는다), **빨라야 하는 것은 Redis**(죽어도 다시 채우면 된다). 반대로 놨다면 그게 진짜 문제였을 것이다.

## 3. 결정해야 하는 것 둘

### 3-1. 🟡 `match_offer`를 누가 INSERT 하나

매칭 서비스가 RDS를 **읽을** 이유가 없다는 건 정리됐다. Core API가 요청 조건을 정제해서 넘겨주니까
(1.4.18 ANY 포지션 전개 + 1.4.19 티어 스냅샷이 정확히 그 목적이다).

남은 건 `match_offer` / `offer_participant`를 **누가 쓰느냐**다.

| | 안 1 · 매칭이 직접 쓴다 | 안 2 · Core API가 쓴다 **(권장)** |
|---|---|---|
| 매칭의 RDS 커넥션 | 필요 | **0개** |
| 매칭이 스키마를 알아야 함 | 예 | 아니오 |
| 명세 2.7 | 그대로 | "이벤트 발행만"으로 수정 필요 |
| 선점 실패 롤백 | 매칭이 처리 (2.6.7) | Core API 응답으로 처리 |

**안 2를 권하는 이유**
- 매칭 담당자가 **DB 스키마를 몰라도 개발할 수 있다** → 따로 개발할 때 맞출 게 거의 없어진다
- 매칭 엔진이 **입력 → 출력 순수 함수**가 된다 → 2.4.10 "동일 입력 동일 결과"가 단위 테스트로 바로 증명된다
- RDS 쓰기 주인이 Core API 하나로 모여서 트랜잭션 경계가 단순해진다

- [ ] 안 1 / 안 2 결정

### 3-2. 🟢 거절한 사용자의 요청은 무슨 상태로 끝나나

## 5. 아키텍처 그림 손볼 곳

- [ ] 🟡 **Outbox 릴레이 주체 표시** — `outbox_event`를 읽어 SQS로 밀어주는 주체가 그림에 없다.
      권장: Core API 안의 `@Scheduled(fixedDelay=1000)` 폴러. 박스 설명에 "Outbox 릴레이" 한 줄 추가로 끝난다.
- [ ] 🟡 `Core API → 즉시 매칭` 화살표를 `Core API → Redis`로 변경 (2-1)
- [ ] 🟡 `Discord Worker → Core API` 화살표 추가 (2-2)
- [ ] 🟡 `RunTask → SQS` 화살표 제거 (2-3)
- [ ] 🟡 **CloudFront에 API origin 추가** — `/api/*`와 `/events/*`를 ALB로 보내면 앱과 API가 같은 도메인이 되어 CORS가 통째로 사라지고 SSE 인증에 쿠키를 그냥 쓸 수 있다.
      ※ SSE behavior는 **캐싱 비활성 + 응답 버퍼링 off** 필수. 안 그러면 이벤트가 버퍼에 갇힌다.
- [ ] 🟢 **NAT 각주 수정** — 리전당 1개로 바꿨으므로 각주 ①의 "AZ별로 두어 한쪽 AZ 장애 시에도 아웃바운드가 유지된다"가 사실과 다르다.
- [ ] 🟢 **워커 태스크 수 조정 (선택)** — Notification / Discord Worker는 `desiredCount 1` + 2 AZ 서브넷으로 충분하다.
      AZ 장애 시 ECS가 다른 AZ에 자동 재기동하고(30초~2분), 그동안 SQS 메시지는 큐에 그대로 남는다. 태스크 4개 → 2개.

### 참고: SSE 인증이 왜 걸리는가

브라우저 `EventSource`는 **커스텀 헤더를 못 붙인다.** `Authorization: Bearer ...`를 쓸 수 없다.

인증이 필요한 건 **연결을 맺는 그 첫 GET 요청 1회뿐**이다(연결 유지 중에는 불필요).
서버가 그 요청의 주인을 모르면 어떤 사용자의 이벤트를 이 연결로 보낼지 정할 수 없고,
`/events?userId=123` 식으로 하면 아무나 남의 파티 정보를 실시간으로 훔쳐본다(1.6.2 위반).

재연결(1.8.13)이 자주 일어나므로 **브라우저가 자동으로 붙여주는 쿠키**가 가장 편하다.
→ CloudFront로 도메인을 합치면 이게 그냥 해결된다.

## 6. 🟢 나중에 — 매칭 서비스를 여러 대로 늘릴 때

### 지금 구조로는 인스턴스를 늘려도 처리량이 안 는다

명세 2.4가 "전체를 신청 순서로 정렬 → 앞에서부터 기준 요청 선정 → 순차 탐색"이라,
인스턴스 A와 B가 **같은 대기열을 같은 규칙으로 보면 항상 같은 답을 낸다.**
2.4.10(동일 입력 동일 결과)이 요구하는 바니까 버그가 아니라 설계대로다.

```
A: 요청 1,2,3,4,5로 파티! → Lua 선점 → 성공
B: 요청 1,2,3,4,5로 파티! → Lua 선점 → 실패, 계산 전부 폐기
```

**인스턴스 2개 = 처리량 2배가 아니라, 처리량 1배 + CPU 2배.**

### 임의로 반씩 나누면 매칭률이 떨어진다

A가 요청 1~500, B가 501~1000을 보면, 5인 파티인데 A 구간에 4명 B 구간에 1명 있는 조합이 영원히 안 잡힌다.
**매칭은 전역 최적화 문제라 아무렇게나 못 쪼갠다.**

### 자연 경계로 샤딩하면 손실 없이 나뉜다

매칭 조건 중 **완전 일치**를 요구하는 것들이 그 경계다.

| 조건 | 판정 | 파티션 키로 쓸 수 있나 |
|---|---|---|
| 2.2.1 큐 일치 | 완전 일치 | ✅ |
| 2.2.2 목표 인원 일치 | 완전 일치 | ✅ |
| 2.2.8 플레이 목적 일치 | 완전 일치 | ✅ |
| 2.2.7 음성 조건 | 호환 규칙 (필수↔가능) | ❌ |
| 2.2.4 양방향 티어 | 범위 겹침 | ❌ |
| 2.2.3 플레이시간 | 교집합 | ❌ |

앞의 셋이 다르면 **절대 같은 파티가 될 수 없으므로**, 이걸로 나누면 매칭률 손실이 0이다.

```
파티션 키 = queue × targetSize × purpose

솔로듀오(2인) + 자유랭크(2,3,5인) + 일반(2,3,4,5인) = 8조합
× 플레이 목적 4종
= 32개 파티션 → 인스턴스 32대까지 확장 가능
```

Redis 키가 이미 `mq:{queue}:{targetSize}`라 절반은 돼 있다. `purpose`만 붙이면 된다.

### 지금 해둘 것 — 코드 모양만 잡아두기

```java
for (Partition p : partitionAssigner.myPartitions()) {
    matchEngine.run(p);   // 이 안은 파티션 하나만 본다
}
```

```
MVP    : myPartitions() → 전체 32개 반환   (인스턴스 1개)
확장 후 : myPartitions() → 자기 몫만 반환   (인스턴스 N개)
```

**매칭 엔진 코드는 한 줄도 안 바뀌고 함수 하나만 갈아끼우면 확장된다.**

### Lua 선점은 그대로 둔다

샤딩해도 안전망으로 계속 필요하다.
- 배포 중 구/신 인스턴스가 잠깐 같은 파티션을 본다
- 스케일 아웃/인 순간 할당표가 흔들린다
- 2.6.5 취소와 선점 경합 (인스턴스 수와 무관)

역할이 "평상시 충돌 처리"에서 **"예외 상황 안전망"**으로 바뀔 뿐이다.

- [ ] 매칭 엔진을 처음부터 파티션 루프 구조로 작성

## 7. 🟢 나중에 — 예약 매칭 붙일 때

### 이미 명세에 반영 완료

예약 요청 묶음 정책은 명세서에 반영해뒀다.

| 위치 | 내용 |
|---|---|
| 1.4 (신설) | 예약 요청 묶음 정책 — 흐름도 + 규칙 |
| 1.4.27~31 | 묶음 제출, 묶음 내 시간중복 허용, 묶음 외 차단, 우선순위, 묶음 단위 수정·취소 |
| 1.5.13~14 | 묶음 단일 성립 보장, 확정 시 나머지 `FAILED` 종결 |
| 3.2.13~14 | 배치의 묶음 중복 배정 방지, 우선순위 적용 |
| 3.5.7 | 묶음 단일 파티 보장 |
| 6.4 | 묶음 종결 상태 전이 |

핵심 규칙 네 가지를 다시 확인해두면:

1. 묶음에서 **하나가 확정되면 나머지는 자동 `FAILED`**
2. **묶음 안에서는 시간 중복을 허용해야 한다** — 그래야 "21시도 되고 21시 30분도 됨"을 제출할 수 있다
3. 배치가 파티를 구성할 때 **같은 묶음의 다른 요청이 이미 배정됐으면 제외**
4. 여러 개가 동시에 성립 가능하면 **제출 순서가 앞선 것** (3.5.1 결정론 유지)

### 대체 충원을 붙일 때

Core API → 매칭 서비스로 충원 요청을 보내야 하는데(2.8.1),
**링크 2-1과 똑같은 패턴으로 간다.**

```
Core API → Redis의 refill 큐에 push
즉시 매칭 → 대기열 폴링할 때 refill 큐도 같이 폴링
```

Core API → 매칭은 **항상 Redis 경유**로 통일한다. 새 통신 방식을 늘리지 않는다.

## 부록 · 명세서에서 잘한 점

고칠 것만 적어두면 나중에 왜 이 구조로 갔는지 잊어버리니까 같이 남긴다.

- **제외 목록이 명시적이다** (1.5 제외 기능, 8장). 대부분의 명세서는 "포함"만 쓰고 경계가 흐려져 스코프가 무한히 늘어난다.
- **서비스 분리 기준이 원칙으로 서 있다.** 1.4 도입부의 *"혼자 판정 가능 = Core API / 남과 비교 = 매칭 서비스"* — 이 한 문장이 두 서비스의 경계를 전부 설명한다.
- **결정론을 요구사항으로 올렸다** (2.4.10, 3.5.1). 매칭 시스템에서 이게 없으면 버그 재현이 불가능하다.
- **티어 스냅샷** (1.3.14 + 2.2.6). 대기 중 티어가 바뀌어 판정이 흔들리는 문제를 선제 차단. 실무에서도 자주 놓친다.
- **멱등성이 전 계층에 일관된다** (1.5.11 → 2.6 → 3.5.2 → 4.4.1 → 5.6.7).
- **부분 실패 격리 원칙** (5.6.6, 4.2.7, 1.7.12). Discord 실패로 파티를 취소하지 않고, Push 실패로 매칭을 막지 않는다.
- **아키텍처 그림에 각주가 달려 있다.** 설계 의도를 설명하는 다이어그램은 드물다.
