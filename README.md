# platform — QueueMate API 서버

계정·파티·소셜(친구/차단/신고)을 다루는 **REST API 서버**다. 문서에서 `app:platform` 이라고
부르는 배포 단위가 이것이다. 매칭의 앞(계정)과 뒤(모집 글, 확정된 파티, 친구, 차단, 신고)를 맡는다.
**오래 남는 것(PostgreSQL)과, 지금 방에 누가 있는지처럼 금방 사라지는 것(Redis — 방 안의 일)을 같이 다룬다.**
방 안의 일은 원래 옆 서비스 `room` 의 것이었는데(`matching` docs/11 D-16) **2026-09-25 에 이 앱에 합쳤다**(소유자 결정 — `contracts/platform-api.md` P-22). 1단계로 방의 요청(`/api/v1/rooms/**`)을 이 앱(8082)이 쿠키 인증으로 받게 됐고,
2단계로 두 앱을 잇던 장치(입장권 · 방 만들기 요청 · `room_seen_at` · 두 갈래의 확정 기록)를 걷어냈다 — **글 쓰기가 방을 같이 만들고, 입장 요청이 글을 검사하고, 확정은 한 요청이다.** 방의 계약은 `contracts/platform-api.md` "방 — `rooms`" 다.

```
브라우저 ──REST /api/v1/**──▶ platform ──▶ PostgreSQL (public 하나 — 2026-09-26)
                                 │  ▲
                                 │  └── SQS ProposalConfirmed.fifo ◀── matching   (파티를 만들어라 — 아직 배선되지 않았다)
                                 │      (차단은 SQS 로 알리지 않는다 — matching 이 blocks 를 직접 읽는다)
                                 ├──── PUBLISH qm:pubsub:push:{userId} ──▶ Redis ──▶ notification ──SSE──▶ 브라우저
                                 ├──── PUBLISH qm:pubsub:board (BOARD_CHANGED · {}) ──▶ Redis ──▶ notification ──SSE──▶ 모든 연결
                                 ├──── Lua ◀─▶ Redis qm:room:{roomId}:host · :members · :confirmed · qm:user:active-room:{userId}   (방 안의 일 — 이 앱의 room 패키지가 쓴다)
                                 ├──── EXISTS 만 ◀── Redis qm:user:active-request:{userId}   (matching 이 쓴다 — D-19)
                                 ├──── 읽기만 ◀── Redis qm:gameconfig:{GAME}:{MODE} · :tier        (운영자가 seed 로 심는 공유 설정. mode · tier 검증)
                                 └──── 인가 코드 흐름 ──▶ 카카오 · 디스코드   (소셜 로그인 — 가입 · 로그인은 이것뿐이다(2026-09-26). 회원 번호와 닉네임만 받는다)
```

**계정과 인증(가입 · 로그인은 소셜로만 — 2026-09-26) · 소셜 로그인(카카오 · 디스코드) · 게임 프로필 · 차단 · 파티 모집 게시판(글 · 목록 · 게시판 신호) · 방장 확정의 기록 · 친구 · 신고가 구현돼 있다**(2026-09-21 — 빈 뼈대에서 하루 만에 들어왔다. **방 안의 일**(입장 · 나가기 · 강퇴 · 방장 확정 · 접속 확인 · 시그널)은 2026-09-25 에 `room` 을 합쳐 들어왔다. 테스트는 PostgreSQL 5433 · Redis 6380 에서 돈다).
**없는 것** — 자동 매칭 파티(`ProposalConfirmed.fifo` · `PartyClosed.fifo` — SQS 배선이 미정이다), **VALORANT · PUBG 의 전적**(그 둘의 `stats` 는 늘 `null` 이고 `verified` 를 켜는 길도 없다 — **지금은 자기신고를 믿는다**, 소유자 결정 2026-09-25). **2026-09-23 소유자 결정 셋이 붙었다** — refresh 토큰(access 15분 · refresh 7일이고 `TEMP-NO-REFRESH` 가 없어졌다 — `CLAUDE.md` §5.1 (라) · (마)) · **LoL 전적 동기화**(Riot API — `CLAUDE.md` §7) · **게시판 목록의 페이지 나누기**(커서 방식 — `CLAUDE.md` §7.1). **2026-09-24 소유자 결정 여섯이 더 붙었다** — ① **`mode` · `tier` 의 값을 `matching` 의 gameconfig(Redis)에서 읽어 검증한다**(`CLAUDE.md` §3.6 — `mode` 가 필수가 됐고, Redis 를 못 읽으면 검증만 건너뛴다) ② **모집 글을 쓸 때 전적을 긁던 것을 없앴다**(`CLAUDE.md` §7 "게임 계정 연동" — 긁는 시점이 게임 계정 저장 하나가 되고 신선도 장치가 없어졌다. P-13 의 절반을 되물린 것이다) ③ **"전적 갱신" 요청을 두었다**(`POST /api/v1/users/me/game-accounts/{game}/refresh` — **동기** · 쿨타임 2분 · 상한 30초. ②로 낡은 채 남게 된 전적을 사용자가 직접 갱신하는 길이다. P-17) ④ **게시판 목록의 정렬과 커서를 `id` 하나로 했다**(`CLAUDE.md` §7.1 — 정렬은 `id` 내림차순 = 최신순이고 커서도 글 번호 하나다. **정렬 키가 변하면 커서가 중복을 내기 때문이다.** P-14 의 개정이다) ⑤ **글 한 줄에서 `filledPositions` 를 없앴다**(`CLAUDE.md` §7.1 — 주 포지션은 "내가 주로 하는 것" 이지 "이 방에서 할 것" 이 아니라 틀린 정보였다. **docs/11 D-20 의 ③ 을 개정한다.** P-18) ⑥ **방에 방장 말고 누가 있으면 모집 글을 고칠 수 없다**(`CLAUDE.md` §7.1 — 409 `ROOM_HAS_OTHER_MEMBERS`. 조건이 바뀌는데 방 안 사람에게 알릴 길이 없다. P-19). **2026-09-25 소유자 결정 셋이 더 붙었다** — ① **게시판 목록에서 "만료 · 확정된 글은 10분만 보여 준다" 는 보존 기간을 없앴다**(`CLAUDE.md` §7.1 — 모집 중 · 확정 · 만료를 전부 `id` 내림차순으로 보여 주고 **끝난 글도 계속 남는다.** 옛 조건이 세 컬럼에 걸친 `OR` 셋이라 인덱스를 깨끗하게 타지 못했고, 끝난 글이 10분 만에 사라지면 모집이 얼마나 활발한지를 보여 주지 못한다. P-20) ② **목록 커서의 base64url 한 겹을 없애고 글 번호를 그대로 쓴다**(`CLAUDE.md` §7.1 — `cursor` · `nextCursor` 가 숫자다. **감싸도 얻는 것이 없었다**: 서명하지 않아 보안 값이 0 이고 글 번호는 `postId` 로 이미 다 나간다. P-14 의 개정이다) ③ **게시판 목록의 `game` 을 필수로 만들었다**(`CLAUDE.md` §7.1 — **게시판은 게임별로 나뉜 페이지이고 "세 게임 전부" 화면이 없다.** 안 보내면 400 이고 게임 없이 훑던 쿼리 둘이 없어졌다. P-21). 친구 · 신고 · 최근 함께한 사람(읽기)과 알림 `FRIEND_REQUEST_RECEIVED` · `FRIEND_REQUEST_ACCEPTED` 도 같은 날 들어왔다(통과 여부는 `START_HERE.md` §1 의 표) — **최근 함께한 사람은 2026-09-26 부터 채워진다**(소유자 결정 — 확정된 방이 없어질 때 파티가 닫히고 그 순간의 파티원끼리 서로를 적는다 · `contracts/platform-api.md` P-25. 그 전에는 채우는 주체가 없어 늘 빈 목록이었다).

> **지위.** 소유자가 "네가 platform 을 만들어 봐라"고 맡겼고, 문서가 "미정"으로 묶어 둔 것들을 **Claude 가 정해 구현했다. 소유자는 아직 항목별로 검토하지 않았다.** 정한 것의 원본은 **`contracts/platform-api.md`**
> (머리의 "지위" · 맨 아래 "원본에 올려야 할 것" P-1~P-26 — P-11 ~ P-26 은 소유자가 직접 정한 것이다)이다. **소유자가 정한 것은 2026-09-26 에 `matching` 의 결정 로그(docs/11)에 D-24 ~ D-36 으로 남겼다**(P-26 은 D-37 이다 · Claude 가 정한 것은 docs/11 에 없다). 소유자가 직접 정한 것은 "소유자 확정" · "소유자 지시"라고 적었다.

처음 열었으면 **`START_HERE.md`** 부터 읽는다 — 지금 어디까지 됐나, 만드는 순서, 다음에 닿기 전에 물어야 하는 것 · 소유자가 검토해야 하는 것이 거기 있다. 규칙은 `CLAUDE.md`, 이 폴더에서 정한 계약은 `contracts/platform-api.md`(방의 계약도 거기 있다)다.

## 이 서비스가 하는 일

1. **계정** — **가입 · 로그인은 소셜(카카오 · 디스코드)로만 한다**(2026-09-26 소유자 결정 — `contracts/platform-api.md` P-24. 직접 가입 · 비밀번호 로그인이 없다 — 비밀번호 관리 · 이메일 인증 같은 부담을 지지 않는다), 프로필, 게임 계정 연결. 인증 토큰을 발급한다 — access 는 쿠키(`qm_access`)로 주고받는 JWT,
   refresh 는 Redis 에 저장하는 불투명 UUID 다(`matching` docs/11 D-14). **refresh 도 붙었다**(2026-09-23 소유자 결정 — access 15분 · refresh 7일 · 재발급은 `POST /api/v1/auth/refresh` 이고 쓴 값은 그 자리에서 버린다). 서명은 RS256 이고 개인 키는 이 앱만 갖는다 — 다른 서비스는 공개 키로 검증만 한다(`CLAUDE.md` §5.1).
   access 토큰 · 소셜 가입 대기 토큰을 같은 키로 서명하고 **`token_use` 클레임으로 가른다**(입장권도 같은 키였는데 2026-09-25 에 없어졌다). 상태를 바꾸는 요청은 `Origin` 을 검사한다(`contracts/platform-api.md` "공통" · "계정"). (로그인 실패 횟수 제한은 비밀번호 로그인과 같이 2026-09-26 에 없어졌다.)
   **식별자는 사용자 번호 하나다**(`CLAUDE.md` §3.5 · `contracts/platform-api.md` P-11 · P-24). **모든 테이블의 PK 가 `bigint identity` 이고, `userId` 는 DB 가 매기는 사용자 번호다**(2026-09-22 소유자 결정) — JWT 의 `sub`(숫자를 문자열로) · 알림 채널 · 방 키 · URL · 본문이 전부 그것을 쓴다.
   보여 주는 이름은 닉네임 하나다. 2026-09-22 에는 **로그인 아이디 `loginId`** 를 따로 두었다가(중복은 409 `LOGIN_ID_TAKEN`) **2026-09-26 에 없앴다**(소유자 결정 — 쓰는 데가 없다. 친구 요청도 사용자 번호로 한다). 사용자 번호는 2026-09-19 의 "사용자 id 는 가입할 때 정한 로그인 아이디(문자열)"를 개정한 것이다 — **`matching` 의 `Block.java` 도 2026-09-26 에 그 폴더에서 `Long` 으로 바꿨다**(docs/11 D-25).
   **소셜 로그인 — 카카오 · 디스코드**(2026-09-21 소유자 지시 · 2026-09-26 부터 유일한 가입 · 로그인). 소셜로 **처음** 온 사람은 **닉네임만** 정하는 한 단계를 거치고(2026-09-26 전에는 로그인 아이디 · 닉네임이었다), 두 번째부터는 바로 로그인된다. 인가 코드 흐름을 세션 없이 직접 짰다. **가짜 제공자로만 테스트했다 — 실제 키 등록이 이제 필수다**(그것 없이는 아무도 로그인할 수 없다 · `contracts/platform-api.md` "소셜 로그인").
   **게임 프로필** — 게임 계정(**받는 칸이 게임마다 다르다** — LoL: 이름#태그 · 주 포지션(티어는 Riot) · VALORANT: 게임 닉네임 · 티어 · 주 포지션 · PUBG: 게임 닉네임 · 티어 · 서버)에 읽기 전용 `verified` · `stats`(게임사 API 에서 가져온 전적의 스냅숏)를 붙여 밖에 보여 주는 모양이다. `users/me` 와 게시판 목록의 카드가 같이 쓴다.
   **LoL 의 전적은 Riot API 에서 긁는다**(2026-09-23 소유자 결정 — **게임 계정을 연결 · 수정할 때.** 그때는 커밋된 뒤에 비동기였고 실패해도 저장은 성공이었다).
   **2026-09-27 소유자 결정 — LoL 의 `tier` 는 Riot 에서 채운다(전적과 함께). `mainPosition` 은 자기신고 그대로다**(`contracts/platform-api.md` P-26 — 처음에는 "이름#태그만 받고 `tier` · `mainPosition` 을 Riot 에서"였고, **같은 날 주 포지션 절반은 되물렸다 — 사용자가 정한다**). `PUT …/game-accounts/LOL` 의 본문은 `{gameNickname, mainPosition}`(포지션은 선택)이고 **저장하기 전에 동기로** 긁어 응답에 `tier` · `stats` 가 바로 들어 있다(`mainPosition` 은 요청 값).
   이름#태그가 Riot 에 없으면 404 `RIOT_ID_NOT_FOUND`, Riot 장애 · 시간 초과 · `RIOT_API_KEY` 없음은 503 — **둘 다 저장하지 않는다.** VALORANT · PUBG 는 지금대로 자기신고다.
   **모집 글을 쓸 때도 긁던 것은 2026-09-24 소유자 결정으로 없앴다** — 비동기라 글 쓰기 응답에 반영되지 않는데 Riot 호출 21번을 쓴다.
   **대신 같은 날 "전적 갱신" 이 붙었다**(소유자 결정 — **`POST /api/v1/users/me/game-accounts/{game}/refresh`**. **이쪽은 동기다** — 다 긁을 때까지 기다렸다가 갱신된 게임 프로필을 준다(2026-09-27 부터 LoL 의 `tier` 도 갱신한다 — `mainPosition` 은 건드리지 않는다). 같은 게임 계정은 **2분에 한 번**이고(429 + `Retry-After`) 상한은 **30초**이며, 실패하면 **503 이고 옛 전적이 남는다**).
   **그래서 전적이 갱신되는 것은 게임 계정을 다시 저장할 때와 사용자가 전적 갱신을 누를 때다**(아무도 누르지 않으면 낡은 채로 남는 것을 감수한다. **주기적으로 스스로 갱신할지는 미정이다**).
   **VALORANT · PUBG 의 `stats` 는 아직 늘 `null` 이고, `verified` 를 켜는 길(Riot 의 RSO 인증)도 없다**(`contracts/platform-api.md` "게임 프로필" · "전적을 긁는 것"). **지금은 자기신고를 믿는다**(소유자 결정 2026-09-25 — RSO 를 붙일지는 미정 그대로다).
   **자기신고 `tier`(VALORANT · PUBG) 는 값이 있으면 그 게임의 티어 사다리에 있는 이름이어야 한다**(2026-09-24 소유자 결정 — 목록의 원본은 `matching` 의 gameconfig(Redis)이고 이 앱이 그것을 읽어서 본다. `CLAUDE.md` §3.6)
2. **파티** — `matching` 이 확정한 제안(`ProposalConfirmed.fifo`)을 받아 DB 에 파티를 만들고, 확정된 파티와
   파티원을 기록한다. 파티가 닫히면 파티원끼리 "최근 함께한 사람"을 만든다.
   **게시판 파티는 확정된 방이 없어질 때 이 앱 안에서 닫는다**(2026-09-26 소유자 결정 — `contracts/platform-api.md` P-25. `parties` 가 `CLOSED` 가 되고 그 순간의 파티원끼리 서로를 적는다. 글은 `CONFIRMED` 그대로이고 알림은 내지 않는다 — `PARTY_*` 가 미정이다).
   자동 매칭 파티는 `PartyClosed.fifo` 로 알리는 것이 원안이다(보내는 쪽도 받는 쪽도 이 앱 — `matching` docs/11 D-13. 6단계에서 다시 본다). **구현된 것은 게시판 파티의 기록과 닫힘뿐이다** — SQS 쪽은 하나도 없다(아래 "만드는 순서" 6단계)
3. **파티 모집 게시판과 방** — 모집 글을 올리면 그것이 곧 파티방이다(자동 매칭 뒤에 생기는 파티방과 같은 개념의 방).
   **글 쓰기가 방을 같이 만든다**(2026-09-25 — 소유자 결정: 방을 못 만들면 글도 되돌린다). 한 요청이 글을 쓰고 트랜잭션 안에서 방 만들기 Lua 를 불러 **쓴 사람이 방장으로 곧바로 방에 들어와 있다** —
   이미 다른 방에 있으면(409 `IN_OTHER_ROOM`) · 자동 매칭 중이면(409 `ALREADY_QUEUED`) 글이 써지지 않는다. 방 만들기 요청은 따로 없다.
   이 앱이 맡는 것은 **모집 글 쓰기·수정, 게시판 목록, 차단 관계 거르기**(어느 쪽이 차단했든 그 방은 목록에 보이지 않는다), **글의 상태**(모집 중/확정/만료),
   **방 안의 일**(입장 · 나가기 · 강퇴 · 정원 5명 · 접속 확인 · 방장 확정 · 방 안 사람 목록 · 내 방 찾기 · WebRTC 시그널 · 방 알림 `ROOM_*` · `WEBRTC_SIGNAL` — `room` 패키지. 상태는 Redis 에만 있고, **방을 바꾸는 것은 Lua 를 부르는 서비스뿐이다**)이다.
   **입장권은 없다**(2026-09-25) — 입장 요청(`POST /api/v1/rooms/{roomId}/members`) 안에서 글을 먼저 본다: 차단으로 숨겨진 글은 404 `POST_NOT_FOUND`, 모집 중이 아니면 409 `POST_NOT_RECRUITING`, 그다음 방의 검사(없는 방 · 만석 · 확정된 방 · 자동 매칭 중 · 다른 방).
   **방장 확정은 한 요청이다** — `POST /api/v1/rooms/{roomId}/confirm` 이 방을 확정하고(Lua) 같은 트랜잭션에서 글을 "확정"으로 바꾸고 파티원을 기록한다(**`parties` 의 `UNIQUE (post_id)` 가 멱등을 지킨다**).
   커밋이 실패해 "확정된 방인데 글은 모집 중" 이 남으면 목록 · 단건이 확정 표시 키를 보고 그 자리에서 기록한다(자가 치유).
   **방과 글은 같이 산다**(2026-09-25 소유자 결정) — **확정 전에는** 방장이 나가도(`DELETE …/members/me`) 글을 지워도(`DELETE /api/v1/posts/{postId}`) 방과 글이 둘 다 끝난다(방은 `ROOM_CLOSED` 를 내고 입장 표시 키를 지우며, 글은 그 자리에서 `EXPIRED` 가 되고 게시판 신호가 나간다).
   **확정 뒤에는** 글이 `CONFIRMED` 로 고정되고(`DELETE` 는 409 `POST_CONFIRMED`) 방은 승계된다(D-23). 그래서 "글을 지웠는데 방에 남아 새 글이 409 `IN_OTHER_ROOM`" · "방장이 나갔는데 글이 모집 중으로 남아 새 글이 409 `ALREADY_RECRUITING`" 이 없어졌다. 코드는 지금 붙는 중이다.
   **말없이 사라진 방장(방 키의 수명이 다한 경우)만은 목록 · 단건이 옮겨 적는다** — 모집 중인 글에 방장 키(`qm:room:{roomId}:host`)가 없으면 방이 사라진 것이고 글을 만료로 바꾼다. **확정한 방은 방장이 나가도 방이 이어지고 방장 키의 값이 바뀔 수 있다**(docs/11 D-23 — 확정된 글은 만료시키지 않는다).
   **목록의 한 줄은 이 앱이 전부 조립한다**(docs/11 D-20) — 방 안에 몇 명인가, **방 안 사람들의 카드**(닉네임 · 티어 · 주 포지션 등).
   방 안의 `userId` 목록(`RoomService#states`)에 이 앱의 DB 에서 프로필을 붙인다 — 방 키에는 `userId` 만 있다.
   포지션의 출처는 **프로필의 주 포지션**이다(입장할 때 고르지 않는다). **글의 "찾는 포지션" 가운데 이미 방 안에 채워진 것을 강조하던 `filledPositions` 는 없앴다**(2026-09-24 소유자 결정 — **주 포지션은 "내가 주로 하는 것" 이지 "이 방에서 할 것" 이 아니라 틀린 정보였다.** docs/11 D-20 의 ③ 을 개정한다. `CLAUDE.md` §7.1 · P-18). **차단은 방 안의 누구와든 본다** — 방 안에 나와 차단 관계인 사람이 한 명이라도 있으면
   그 방을 목록에서 빼고 입장도 막는다. 자동 매칭이 기본 경로이고 게시판은 두 번째 경로다. 이유는 **모집의 응답성**이다 — 같이 할 사람을 직접
   확인하고 싶은 사용자가 있고, 글·메시지로 응답을 기다리는 것보다 말을 거는 쪽이 빠르다 (`matching` docs/11 D-11 · D-16).
   **목록의 한 줄은 게임마다 다른 정보를 보여 준다**(2026-09-21 소유자 지시 — 본보기는 OP.GG 의 듀오 찾기. LoL: 이름#태그 · 인증 · 포지션 · 티어 · 찾는 포지션 · 모스트 챔피언 · 승/패 · KDA · 메모, VALORANT: 모스트 요원 · 주 무기 · 헤드샷률,
   PUBG: 모드 · 티어 · 음성/목적 태그 · 서버/시점 · 평균 데미지 · K/D · 치킨률). **세 게임 모두 가로 한 줄이고, 글을 눌러 펼치지 않고 방 안 전원을 그 자리에서 다 보여 준다** — 그래서 목록 응답의 `members[]` 에 게임 프로필 전체가 실린다.
   **`roomId` 는 글의 id** 다(`recruit_posts.id` — **bigint identity.** 2026-09-22 전에는 UUID 였다. 방 키에는 숫자가 문자열로 들어간다). Redis 를 못 읽으면 목록 · 단건은 만료 판정을 하지 않고, 고치기 · 입장은 503 `ROOM_STATE_UNAVAILABLE` 이다(`contracts/platform-api.md` "모집 글 · 목록 — `posts`" · "방 — `rooms`").
   **글의 `mode` 는 필수이고 그 게임의 gameconfig 에 있는 모드여야 한다**(2026-09-24 소유자 결정 — 옛날에는 30자까지의 자유 문자열이었다. 고치기에서 빈 문자열로 비우는 길이 없어졌다. `CLAUDE.md` §3.6)
   **방에 방장 말고 누가 있으면 글을 고칠 수 없다**(2026-09-24 소유자 결정 — 409 `ROOM_HAS_OTHER_MEMBERS`. 고칠 수 있는 칸에 `mode` · `voice` · `purpose` · `conditions` 가 있는데 **`NO_VOICE` 를 보고 들어와 앉아 있는 사람에게 바뀌었다고 알려 줄 길이 없다.**
   방장 혼자면 고쳐지고, 방 키를 못 읽으면 503 이다. **막는 것은 고치기 하나다** — 지우기 · 입장 · 확정 · 조회는 그대로다. `CLAUDE.md` §7.1 · `contracts/platform-api.md` P-19)
4. **소셜** — 친구, 차단, 신고, 최근 함께한 사람. 차단 테이블(`blocks`)의 주인이다 — `matching` 이
   "차단 관계는 같은 파티가 될 수 없다"(INV-6)를 지키려고 이 테이블을 직접 읽는다. 차단은 DB 에 저장하면
   끝이고 SQS 로 따로 알리지 않는다(`BlockChanged.fifo` 폐기 — docs/11 D-12). **차단은 구현돼 있다.** DB 롤 · GRANT 는 없다 — 앱 하나가 DB 계정 하나로 붙고, `matching` 은 별도 롤 없이 `blocks` 를 읽는다(`CLAUDE.md` §3.5). **2026-09-26 에 스키마가 `public` 하나가 됐다**(소유자 결정 — P-23 · docs/11 D-34. `matching` 의 `Block.java` 에서도 `schema = "social"` 을 뺐다 — 2026-09-26 그 폴더에서).
   친구(요청 · 수락 · 거절 · 거두기 · 목록 · 끊기) · 신고(접수만) · 최근 함께한 사람(읽기)도 들어왔다(`contracts/platform-api.md` "친구 · 신고 · 최근 함께한 사람"). 친구는 상대의 사용자 번호를 정확히 알아야 요청을 보낼 수 있다 — 사람을 검색하는 API 는 만들지 않는다.
   **최근 함께한 사람은 확정된 파티가 닫힐 때 채워진다**(2026-09-26 소유자 결정 — P-25. 지금은 게시판 파티만이다 — 자동 매칭 파티는 6단계)
5. **알림 발행** — `PARTY_*`·`FRIEND_*` 7종을 Redis Pub/Sub 에 발행한다(**`FRIEND_REQUEST_RECEIVED` · `FRIEND_REQUEST_ACCEPTED` 둘의 이름과 payload 를 정했다** — `contracts/platform-api.md` "이 앱이 내는 알림". 나머지는 미정이다. 방 입장·퇴장·방 닫힘·강퇴·방장 확정
   알림은 `ROOM_MEMBER_ENTERED` 같은 새 이름으로 이 앱의 `room` 패키지가 낸다 — 2026-09-25 에 합쳤다). 봉투(`{type, eventId, occurredAt, payload}`)와 채널(`qm:pubsub:push:{userId}`)은 `matching` 의
   `PushPublisher.java` / `SharedKeys.java` 와 같다. 배달은 `notification` 이 한다.
   **게시판 채널 `qm:pubsub:board`(게임을 구분하지 않는 하나)에 "바뀌었다" 신호(`BOARD_CHANGED`, `payload` 는 `{}`)도 발행한다** — 글이 생기거나 사라지거나 상태가 바뀔 때다
   (방의 인원이 바뀔 때도 이 앱의 `room` 패키지가 발행한다). 목록을 F5 없이 갱신하려는 것이고, 신호는 "다시 받아라"일 뿐이라 받은 프런트가 이 앱의 목록을 다시 요청한다.
   `notification` 은 이 신호를 모든 연결에 그대로 보내고(`topics` 파라미터는 없앴다), 프런트가 게시판 페이지를 보고 있을 때만 묶어서 다시 요청한다 — **발행하는 이 앱은 게임을 알 필요가 없다.**
   **발행은 구현됐다**(2026-09-21 — docs/11 D-20 · D-22 · D-23 · `CLAUDE.md` §3.2 "게시판 채널". 방 쪽 발행은 `room` 을 합치며 들어왔다). **게시판은 실시간으로 바뀌어야 한다**(인원 · 새 글 — 소유자 지시)를 이것으로 지킨다

## 이 서비스가 하지 않는 일

- **매칭을 하지 않는다.** 매칭·제안·수락·확정은 `matching` 의 일이고, 매칭 Redis 키(`qm:party:*` · `qm:user:*` · `qm:proposal:*` · `qm:lock:*`)를 만지지 않는다. 예외가 없다 —
  "자동 매칭 대기와 방은 한 번에 하나만"은 키 둘로 지킨다: 활성 요청 키는 `matching` 만, 입장 표시 키
  (`qm:user:active-room:{userId}`)는 **이 앱(방 안의 일)** 만 쓰고 지우며 서로 상대 키가 있는지만 본다 — 이 앱은 활성 요청 키를 `EXISTS` 로만 본다(docs/11 D-19. 입장 표시 키의 주인은 2026-09-25 에 `room` 을 합쳐 이 앱이 됐다).
  **`qm:gameconfig:*` 만은 예외로 읽는다**(2026-09-24 소유자 결정 — `mode` · `tier` 가 있는 값인지 보려는 것이다. 운영자가 배포 때 심는 공유 설정이고 쓰는 앱이 없다 — `matching` 도 읽는 쪽이다).
  **쓰지 않고 seed 를 심지도 않으며 gameconfig 모듈(모드 설정을 정하고 해석하는 것)은 여전히 `matching` 의 것이다**(`CLAUDE.md` §3.6 · §11).
- **브라우저 연결을 들고 있지 않는다.** SSE 는 `notification` 의 일이다. 이 앱은 stateless REST 로 둔다.
- **예약을 하지 않는다.** 예약 REST(등록·조회·수정·취소, INV-9)와 짝 찾기 배치는 `app:reservation`(AWS Lambda)의
  일이다 (`matching` docs/11 D-15 — 예전에는 예약 REST 가 이 앱의 일이었다).
- 음성·텍스트 채팅을 중계하지 않는다(브라우저 직결). TURN credential 발급도 이 앱의 일이 아니다.
- 공개 사용자 탐색, 길드, 피드, 팔로우, 좋아요, 공개 채팅방을 만들지 않는다. 파티 모집 게시판은 그 예외다
  (D-11) — 게시판이 보여 주는 것은 **사람 목록이 아니라 모집 글(방) 목록**이고, 사람을 검색하고 둘러보는
  기능은 여전히 만들지 않는다. "공개 채팅방"은 파티 모집과 무관한 잡담용 공개방을 뜻한다

## 저장소 구성

`matching` 과 **같은 GitHub 저장소의 다른 브랜치**(`platform`)다. 이력이 없는 빈 브랜치에서 시작했으므로
매칭·알림 코드는 이 브랜치에 없다. 로컬에서는 `git worktree` 로 나란히 둔다.

```
queuemate/
├── matching/       matching 브랜치. 매칭 엔진. 결정 로그와 계약 사본이 여기 있다
├── notification/   notification 브랜치. 알림(SSE) 서비스
├── room/           room 브랜치. 2026-09-25 에 이 앱에 합쳐 옛 모습 그대로 남아 있다(참고만)
└── platform/       platform 브랜치 (이 폴더)
    ├── START_HERE.md   시작 안내 — 지금 어디까지 됐나 · 만드는 순서 · 다음에 닿기 전에 물어야 하는 것
    ├── CLAUDE.md       규칙
    ├── contracts/      platform-api.md — 이 폴더에서 정한 계약(경로 · 스키마 · 에러 코드 · 토큰 · 방 · 알림 · gameconfig 를 읽는 것)과 "원본에 올려야 할 것" P-1~P-26
    └── backend/        스프링 앱. matching/backend/ 와 같은 모양
                        패키지는 도메인 먼저 — common(에러 · Origin 검사 · 토큰 · 알림 봉투 · gameconfig 읽기) · account(계정 · 게임 프로필 · oauth) · social(차단 · 친구 · 신고 · 최근 함께한 사람) · party(글 · 목록 · 입장 검사 · 확정 기록 · 게시판 신호) · room(방 안의 일 — Lua 스크립트 · Redis 에만 있다)
                        마이그레이션은 db/migration/V1__schema.sql 하나다 — 스키마 public 하나 · 테이블 사이 FK 허용(2026-09-26 소유자 결정 · P-23. 그 전에는 V1 + account/ · social/ · party/ 로 V8 까지 나뉘어 있었다). 테이블의 원본이다
                        .dev-keys/ 는 앱이 만드는 개발용 JWT 키다(git 에 올리지 않는다 — 옆 서비스는 그 public.pem 으로 검증한다)
```

계약 원본(queueMate 본 저장소 `feature/frontend` 의 `contracts/`)은 이 컴퓨터에 없다. 그래서 여기서 정한 것을 `contracts/platform-api.md` 에 먼저 적었다 — 원본과 합칠 때 그 파일 맨 아래 표를 들고 간다(`CLAUDE.md` §3.1).
ERD 는 <https://claude.ai/artifact/LBngVYThyCjipLUkatC6Bq> 다.

기술 스택은 옆 서비스들과 같은 버전으로 맞춘다 — Java 21, Spring Boot 4.1.1(MVC), Gradle, PostgreSQL + Flyway.
로컬에서 띄우려면 테스트용 PostgreSQL(5433)과 Redis(6380)를 따로 띄운다 — 5432 · 6379 는 이 컴퓨터의 다른 프로젝트 것이다(`START_HERE.md` §6).
로컬 기본 포트는 `matching` 8080, `notification` 8081, 이 앱 **8082**(2026-09-21 확정)다(`room` 의 8083 은 2026-09-25 에 합쳐 없어졌다).

## 만드는 순서

자동 매칭으로 확정된 파티를 받으려면 SQS(`ProposalConfirmed.fifo`)가 필요하고, 그러려면 AWS SDK · 메시지 형식
결정 · `matching` 쪽 발행 코드까지 있어야 한다. 반면 **게시판 방은 SQS 없이 platform · notification 만으로
끝까지 돈다**(글 쓰기 = 방 만들기 → 입장 → 시그널 → 음성). 그래서 방을 먼저 만들고, 자동 매칭 파티를 나중에 같은 방에 합친다.

> **지금 상태(2026-09-25).** 순서와 달리 `room` 을 먼저 따로 만들었고(요청 아홉 가지 · 알림 · 확정한 방의 방장 넘기기 · 게시판 채널 신호 — docs/11 D-21 · D-23),
> **2026-09-25 에 이 앱에 합쳤다**(P-22 — 1단계 옮겨서 돌게 하기 · 2단계 입장권 · 방 만들기 요청 · `room_seen_at` · 두 갈래의 확정 기록을 걷어내기). 그래서 아래 표의 3~5단계는 **이 앱 하나의 일**이 됐다.
